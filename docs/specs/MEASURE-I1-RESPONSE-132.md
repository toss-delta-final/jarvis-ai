# MEASURE-I1-RESPONSE-132 — I-1 전량반환의 자원·타임아웃 실측

이슈 #132 완료 조건 1("광역 질의 부하 실측")의 근거. 로컬에 실 카탈로그를 적재하고 BE·AI 를 모두
띄워 종단으로 측정했다.

**결론 세 줄**

1. **BE 쿼리는 오늘 3s 예산을 넘지 않는다** — 필터 없는 최악이 **1.11s**(예산의 37%).
2. **진짜 부담은 응답 크기다** — 그 질의의 바디가 **13.33 MB**이고, 이를 받아 푸는 동안
   AI 이벤트루프가 멈춘다(적용 전 단일 호출 **222ms**, 20 동시 **5.4s**).
3. **더 시급한 것은 따로 있었다** — **카테고리 매핑이 성공한 턴의 후보가 0건**이다(§2.1 캡처).
   원인이 둘이다: (가) BE 의 `categoryName` 이 AI 의 `대분류 > 중분류` 경로를 못 받고,
   (나) AI 사전 2,056개 중 **1,019개가 BE 카탈로그에 아예 없다**. **(가)만 고치면 절반이 남는다.**
   자원 문제가 아니라 **검색이 조용히 비는** 문제이며, 둘 다 BE 쪽 처리로 합의됐다(§8).

## 1. 측정 환경

| | |
|---|---|
| 카탈로그 | `_sql/` 실 덤프 — `product` 7,220 / `review` 126,313 / `product_option` 24,475 / `category` 1,221 |
| DB | MariaDB 11.4 (로컬 docker, `jarvis-backend/docker-compose.yml`) |

적재 시 BE 스키마와 실데이터가 어긋나 로컬에서만 완화한 것은 §7.

## 2. 카테고리 — 매핑이 성공해도 후보가 0건이다

> 이 절은 **맨 이름**(`티셔츠`)으로 질의했을 때의 관찰이다. AI 가 실제로 보내는 값은 경로
> (`남성의류 > 티셔츠`)이므로, 프로덕션에서 무슨 일이 벌어지는지는 **§2.1 이 정본**이다.
> 아래는 그 원인을 좁혀 가는 과정의 기록으로 남긴다.

상품이 붙어 있는 깊이:

| depth | 카테고리 | 상품 |
|---|---:|---:|
| 1 (루트) | 18 | 0 |
| 2 (중분류) | 179 | 50 (데모 데이터) |
| 3 (소분류) | 1,040 | **7,220 (전량)** |

`CategoryService.resolveIdsByName` 은 **루트면 직계 자식(depth 2)으로만 확장**하고 비루트면
**그 카테고리 하나**만 쓴다. depth 2 에 실상품이 없으므로 대분류·중분류 이름은 모두 0건이다.
**라이브로 확인**했다 — `categoryName=패션의류/잡화` → `200`, 바디 26 B, **0건**(§3 표).

즉 이슈가 상정한 "대분류만 준 넓은 질의로 자원 급증"은 일어나지 않는다. 그 반대로 **조용한
zero-result** 이며, AI 는 이를 "그런 상품이 없다"와 구분할 수 없다.

**이름 중복** — depth 2·3 을 통틀어 같은 이름이 **102종 / 268개 카테고리 / 상품 2,740건(38%)**
에 걸쳐 있다. `findFirstByName` 이 첫 행만 집으므로 나머지는 조용히 빠진다. 라이브에서
`categoryName=티셔츠` 가 **10건**만 돌려줬다 — 같은 이름 카테고리 중 최대는 61건인데 그쪽이 아니었다.

> 두 가지 모두 **BE 소관**이며 #132 범위 밖이다. BE 팀과 합의해 처리 방향이 정해졌다(§8) —
> 별도 이슈는 열지 않는다. 아래 수치는 2026-08-04 측정 시점 기록이다.

### 2.1 실제 턴이 보내는 값 — 이름 체계가 서로 다르다

위 두 가지는 **증상**이고, 실제 턴을 캡처해 보니 원인은 더 앞에 있었다.
`scripts/capture_i1_wire_132.py` 가 실 LLM 으로 한 턴을 돌려 `_search_query_params` 산출물
(= BE 가 실제로 받는 값)을 그대로 떴다:

| 발화 | AI canonical | 전송된 `categoryName` | 후보 |
|---|---|---|---:|
| 가벼운 남자 반팔 티셔츠 추천해줘 | `남성의류 > 티셔츠` | `'남성의류 > 티셔츠'` | **0** |
| 선크림 하나 사려는데 | `선케어 > 선크림/선블록` | `'선케어 > 선크림/선블록'` | **0** |
| 노트북 CPU 뭐가 좋아? | (매핑 실패) | `None` | 7,245 |

카테고리 트리는 **3단계**이고, AI 사전은 그중 뒤 두 단계를 붙인 문자열이다:

```
가전/디지털        ← 1단계: 도메인            (AI 사전에 없음 — 검색에 쓰지 않는 층)
  └ PC부품         ← 2단계: 대분류   ┐
      └ CPU        ← 3단계: 중분류   ┘ AI canonical = "PC부품 > CPU"
```

- **AI**: `대분류 > 중분류` 경로 문자열. pg-catalog `categories.category` 2,056개가 전부 이 형태이며,
  시드 정의(`db/catalog/init/02_categories.sql`)가 *"확정된 canonical category(원본 "top > mid"
  leaf)만 Spring I-1 categoryName 으로 전달한다"* 고 **명시**한다 — 우연이 아니라 설계다.
  대조로 확인했다: AI 앞조각 170종 중 **166종이 BE 2단계 이름과 일치**하고 1단계와는 1종만 겹친다.
- **BE**: 맨 이름 + `parent_id`. 경로가 든 이름은 **0개**다.

**구조 자체는 어긋나 있지 않다.** 도메인 층이 AI 사전에 없는 것은 정상이다(검색에 쓰지 않는 층).
어긋나는 것은 아래 둘이고 **성격이 달라 따로 다뤄야 한다.**

**(가) 전달 통로** — I-1 의 `categoryName` 은 문자열 하나뿐이고 BE 는 그것을 `category.name` 과
정확일치로 찾는다. `남성의류 > 티셔츠` 는 그런 **이름**이 없어 매칭되지 않는다 — 값으로는 BE 의
`parent=남성의류, child=티셔츠`(상품 12건)에 정확히 대응하는데도.

**(나) 커버리지** — AI 사전 2,056개 중 BE 트리의 (부모 > 자식) 쌍에 실재하는 것은 **1,037개뿐이고
1,019개는 BE 에 아예 없다**(`PC부품 > 그래픽카드`·`메인보드`·`쿨러` — 부모가 다른 게 아니라
카테고리 자체가 부재). BE 리프 1,040개 vs AI 사전 2,056개로 **사전이 약 2배 넓다.**

> ⚠️ **(가)를 고쳐도 (나)는 남는다.** BE 가 경로를 수용하면 1,037개는 살아나지만 나머지 절반은
> 여전히 0건이다. "형식만 맞추면 해결된다"고 읽지 말 것.

**그래서 매핑이 성공할수록 결과가 없다.** 후보가 나오는 것은 매핑이 **실패**해 `categoryName` 을
아예 안 보낼 때뿐이고, 그때는 필터 없는 전량(13.33 MB)이 온다 — §6 의 "큰 응답은 드문 경로"라는
서술이 이 사실 앞에서는 약해진다. 매핑 실패가 곧 전량 응답이기 때문이다.

> 맨 이름만 보내는 것은 대안이 못 된다 — `티셔츠` 는 5개 카테고리에 걸쳐 있어 어느 하나를
> 임의로 고르게 된다(측정 시점 BE 는 상품 10건짜리를 골랐다. 가장 큰 61건도, 사용자가 원한
> 12건도 아니었다). 경로가 이미 정답을 담고 있으므로 **받는 쪽을 여는 것이 정공법**이고,
> BE 가 그렇게 하기로 합의됐다(§8).

### 2.2 해소 확인 방법

(가)와 (나)는 **다른 작업이라 하나만 끝나도 티가 안 난다.** BE 변경 뒤 아래로 각각 확인한다.

```bash
# (가) 전달 통로 — 실 LLM 으로 한 턴 돌려 전송값과 후보 수를 함께 찍는다.
uv run python scripts/capture_i1_wire_132.py
#   → 전송 categoryName='남성의류 > 티셔츠'  후보=0   이면 (가) 미해소
```

(나)는 사전과 카탈로그의 집합 비교다 — AI `categories.category` 전량과 BE 의 `(부모 > 자식)`
쌍 전량을 뽑아 차집합을 센다. 측정 시점 값은 **AI 2,056 / BE 쌍 1,215 / 교집합 1,037 / AI 전용
1,019** 였다. 교집합이 AI 사전 크기에 근접하면 (나)가 해소된 것이다.

## 3. BE I-1 종단 실측

컨테이너 안에서 `/internal/products/search` 직접 호출(`X-Internal-Token`).

| 질의 | http | 바디 | 소요 | 항목 |
|---|---:|---:|---:|---:|
| 필터 없음(최악) | 200 | **13.33 MB** | **1.112s** | 7,245 |
| `keyword=세트` | 200 | 4.99 MB | 0.256s | 2,657 |
| `categoryName=티셔츠`(리프) | 200 | 18.7 KB | 0.031s | 10 |
| 리프 + 가격범위 | 200 | 10.7 KB | 0.018s | 6 |
| `categoryName=패션의류/잡화`(대분류) | 200 | 26 B | 0.019s | **0** |

**3s 예산(§2.9 c) 안이다.** 최악이 1.11s 로 37%를 쓴다. 재시도까지 겹치면 6s 예산 중 2.2s.

### ⚠️ 초기 진단 정정 — `group by` 는 문제가 아니었다

JPQL 텍스트(`group by p`)만 보고 "엔티티 전체 컬럼이 그룹 키가 되어 TEXT 때문에 임시테이블+
filesort 가 생긴다(4.15s, PK 그룹 대비 33배)"고 적었으나 **틀렸다.** MariaDB general log 로
Hibernate 가 실제로 보내는 SQL 을 확인한 결과:

```sql
... from product p1_0 left join review r1_0 on ... group by p1_0.id
```

**PK 하나로 그룹핑한다.** Hibernate 6.6 이 엔티티 그룹핑을 식별자로 최적화한다. 직접 손으로 옮겨
쓴 SQL 로 잰 4.15s 는 실행되지 않는 쿼리의 비용이었다. 1.11s 의 대부분은 GROUP BY 가 아니라
**JPA 엔티티 하이드레이션 + 13 MB JSON 직렬화·전송**이다.

> 교훈: ORM 이 만드는 SQL 은 **생성물을 봐야** 안다. JPQL 을 읽고 재현한 SQL 로 성능을 진단하면
> 존재하지 않는 병목에 이슈를 낸다. (`docs/lessons.md` 에 등재)

## 4. AI측 수신·파싱 비용 — 실 응답 13.33 MB 기준

`scripts/measure_i1_parse_132.py --body-file <실응답>` — `httpx.MockTransport` 로 HTTP 경계만
대역을 세우고 `spring_client.search_products`(= `resp.json()` + N× `SpringProduct.model_validate`)를
프로덕션 코드 그대로 통과시킨다. `gap` 은 10ms 주기 하트비트가 밀린 시간 = **이벤트루프가 막혀
같은 워커의 다른 SSE 스트림이 멈춘 시간**.

| 동시 | 소요(전) | **루프정지(전)** | 소요(후) | **루프정지(후)** |
|---:|---:|---:|---:|---:|
| 1 | 231.6ms | **221.6ms** | 220.8ms | **56.5ms** (−74%) |
| 5 | 1,002ms | **992ms** | 985ms | **424ms** (−57%) |
| 20 | 5,387ms | **5,377ms** | 5,001ms | **2,435ms** (−55%) |

적용 전에는 **루프 정지가 소요와 거의 같았다** — 파싱 전 구간이 끊김 없는 단일 블로킹이었다는 뜻이다.
`to_thread` 이관 후 총 소요는 그대로이고 **정지만 줄었다**. 의도한 결과다: 이 작업은 파싱을 빠르게
만드는 게 아니라 **남의 요청을 막지 않게** 하는 것이다.

**다만 0 이 되지는 않는다.** CPython 은 GIL 때문에 CPU 바운드 작업이 스레드에 있어도 이벤트루프가
GIL 을 기다린다(`json.loads` 는 C, pydantic-core 는 Rust 라 부분적으로만 놓는다). 절반~1/4 로
줄어드는 것이 이 구조에서 가능한 범위이고, 더 줄이려면 별도 프로세스나 스트리밍 파서가 필요하다 —
현 규모에서 그 복잡도를 살 이유는 없다.

## 5. 한 턴이 I-1 을 몇 번 부르는가 — 증폭 실측

위 표의 "동시" 칸이 현실에서 몇이 되는지는 따로 재야 안다. `scripts/measure_i1_fanout_132.py` 가
`stream_recommendation` 을 실 BE 에 붙여 돌리며 `search_products` 호출 수와 **동시 최대치**를 센다
(decompose 산출은 손으로 주입하고 rerank 만 스크립트가 답한다 — LLM 없이 결정적).

코드상 상한은 `fanout_max × (1 + auto_rounds + probes)` = 5 × 8 = **호출 40 / 동시 20**이다.
실측은 그보다 낮다:

| 턴 유형 | I-1 호출 | 동시 최대 | 소요 | 루프정지 최대 |
|---|---:|---:|---:|---:|
| 결과가 넉넉한 턴 | 5 | 5 | 146ms | 98ms |
| 0건 — 자동완화(ratingMin) + probe | 15 | 5 | 205ms | 41ms |
| **0건 — probe 동시 최대(price·brand·color)** | **20** | **15** | 267ms | 138ms |

- **fan-out 은 leg 수만큼 동시**다(5 = `category_fanout_max`). 이슈가 본 그대로다.
- **완화칩 probe 가 진짜 증폭원이다** — `asyncio.gather` 로 동시에 나가고 각 probe 가 다시 leg
  수만큼 fan-out 한다. 동시 15 = probe 3축(price·brand·color) × leg 5.
- 상한 40/20 에 닿으려면 완화 가능한 축이 4개 **동시에** 남아 있어야 하는데, 자동 완화가
  ratingMin 을 선점하면 그 축이 probe 후보에서 빠진다 — 그래서 실측 최악이 20/15 다.

즉 이슈의 "leg 수만큼"은 과소평가였지만(실제 3배), 제가 초기에 말한 "40회/20 동시"는 상한이지
도달값이 아니었다. **근거는 실측값 20/15 를 쓴다.**

## 6. 도달 가능성 — 오늘의 최악

두 축을 곱해야 실제 위험이 나온다.

- 응답이 큰 질의(13.33 MB)는 **카테고리 필터가 없는** 경우인데, 그 경로는 `category_legs` 가 비어
  **단일 호출**이다 → 1 동시 = **56ms 정지**
- 동시가 큰 턴(15)은 **리프 카테고리 fan-out + 완화 probe** 인데, 리프 응답은 수 KB 라
  파싱 부담이 거의 없다 → 실측 루프정지 **138ms**

**둘이 겹치지 않는다** — 큰 응답과 높은 동시성이 같은 턴에서 만나지 않는 것이 현재 구조다.
그래서 오늘의 최악은 100ms 대이지 초 단위가 아니다. 다만 그 분리는 **보장이 아니라 우연**이다.

⚠️ **게다가 그 우연은 §2.1 이 드러낸 고장에 기대고 있다.** "카테고리 필터가 없는 경우는 드물다"는
전제가 성립하려면 카테고리 매핑이 대개 성공해야 하는데, 지금은 매핑이 **성공하면 0건**이고
**실패해야** 후보가 온다 — 즉 13.33 MB 전량 응답은 드문 경로가 아니라 **매핑 실패 때마다 타는
경로**다. BE 가 경로 수용으로 고치면(§8) 그때는 leg 하나가 수백~수천 건을 받기 시작하므로
두 축이 곧바로 겹친다. 그때 값이 §4 표의 20 동시 행(적용 전 5.4초)이다.

즉 지금 아픈 곳을 고친 게 아니라 **상한이 없던 자리에 상한을 둔 것**이고, 그 상한은 카테고리
매핑이 정상화될 때 비로소 제 몫을 한다.

## 7. BE 스키마 ↔ 실데이터 불일치 (적재 중 발견)

로컬 적재를 위해 완화한 것들. **실서버라면 그대로 적재가 실패한다.**
처리 방향은 §8 에 합의된 대로다(브랜드 없는 상품 제외 · 내용 없는 리뷰는 빈 문자열).

| 대상 | BE 스키마 | 실데이터 | 로컬 조치 |
|---|---|---|---|
| `product.brand_id` | NOT NULL | **661건 NULL** | NULL 허용 |
| `review.content` | NOT NULL | **34,842건(27.6%) NULL** | NULL 허용 |
| `created_at`/`updated_at` | NOT NULL, 기본값 없음(JPA 가 채움) | 덤프에 컬럼 없음 | `DEFAULT CURRENT_TIMESTAMP` |
| `category` UNIQUE | `name` 단독 | 같은 이름 102종 반복 | `(parent_id, name)` — `_sql/README` 요구사항 |

`_sql/mariadb/00_schema_patch.sql` 은 `DROP INDEX name` 이라 쓰여 있으나 실제 인덱스명은
`uk_category_name` 이라 그대로는 실패한다.

## 8. 처방과 후속

**AI(이번 이슈에서 처리)**

- 개수 상한은 두지 않는다 — 전량 반환은 BE 합의이고, 응답에 `ORDER BY` 가 없어 앞에서 자르면
  뒤쪽 관련 상품이 임베딩 재정렬 기회를 잃는다. 완화칩 `estCount` 가 응답 길이라 캡은 그 값을
  조용히 천장에 붙인다(api-spec C-15 가 경고한 실패를 AI 쪽으로 옮기는 셈).
- **파싱을 `asyncio.to_thread` 로** — 루프 정지 −74%(단일) / −55%(20 동시).
- **`asyncio.wait_for` 총시간 가드** — httpx 3s 는 청크 간격 상한이라 총 수신 시간을 못 막는다.
  예산은 config 가 이미 기동 검증에 쓰는 `spring_timeout_s × (재시도+1)` 을 그대로 집행한다.

**BE(측정 중 발견 — 전부 BE 팀과 합의되어 별도 이슈를 열지 않는다)**

| 발견 | 처리 |
|---|---|
| (가) `categoryName` 이 AI canonical(`대분류 > 중분류`)을 못 받아 매핑 성공 시 0건(§2.1·§6) | BE 가 경로 형태를 **수용하도록 수정**하기로 합의 |
| (나) AI 사전 2,056개 중 **1,019개가 BE 카탈로그에 부재**(§2.1) | **AI 사전을 기준**으로 BE 카탈로그를 다시 적재하기로 합의 |
| 이름 중복 시 한쪽만 잡히던 문제 | BE 에서 **해소** |
| `product.brand_id` NOT NULL vs 661건 NULL(§7) | 브랜드 없는 상품은 **적재 대상에서 제외**하기로 합의 |
| `review.content` NOT NULL vs 34,842건 NULL(§7) | 내용 없는 리뷰는 **빈 문자열(`''`)로 적재**해 별점만 살린다 |

성능은 급하지 않다 — 1.11s 는 예산 안이다. 다만 카탈로그가 몇 배 커지면 13 MB 바디가 먼저 문제가 된다.

> §2·§7 의 수치는 **2026-08-04 측정 시점 기록**이다. 위 합의가 반영되면 그 시점의 관측과 달라지므로,
> 재측정 없이 현재 동작의 근거로 인용하지 말 것.
