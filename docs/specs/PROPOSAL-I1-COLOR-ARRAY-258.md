# PROPOSAL-I1-COLOR-ARRAY-258 — I-1 `color` 배열 계약 BE 실측 확인 기록

이슈 #258 B 파트(I-1 색상 질의 확장) 계약의 BE 실측 확인 기록. 애초 이 문서는 BE 송부용
계약 변경 제안문으로 시작했으나, **2026-08-08 `toss-delta-final/jarvis-backend` main 을
직접 확인한 결과 계약은 이미 확정·배포돼 있었다** — 새로 협의할 변경이 아니라
`docs/api-spec.md` 사본만 갱신이 안 된 drift 였다(같은 유형 선례: v0.23.1 "사본 등재 —
신설 협의가 아니다", v0.20.4 "사본의 미반영 표시 해제", v0.15.27 "사본 drift 정정"). 근거:

- `InternalProductController.search` 시그니처가 이미 `List<String> color` 다 — 머지 커밋
  `1e0ce150`(2026-08-04, "I-1 색상 필터를 3갈래로 + options 응답 추가").
- BE 자체 계약 문서 `docs/backend/05-llm-contract.md` §I-1 에 **"`color?` 리스트 —
  2026-08-03 개정"**, **"2026-08-03 LLM팀 실측 합의"**, **"동의어 확장은 LLM 팀 소관이고
  BE는 받은 값들을 OR로 본다"** 로 등재.
- 운영 배포 완료(2026-08-08 사용자 확인).

`docs/api-spec.md` §4.6 은 이 실측에 맞춰 이미 동기화했다(v0.28.4, `color: string[] | null`).
**이 문서는 이제 그 근거·판단을 남긴 기록이다** — 남은 것은 새 계약 협의가 아니라 §7 롤아웃
순서(운영 pg-catalog 시드 적재 → AI 플래그 on → 재측정)뿐이다. 아래 §1·§2 는 drift 정정
전 사본이 담고 있던 계약을 이력으로 남긴 것이다.

## 1. 정정 전 사본 계약 (참고, 현재는 §4.6 v0.28.4 으로 대체됨)

`docs/api-spec.md` §4.6 (I-1 `GET /internal/products/search`, v0.15.22 실측 정합) 기준:

| 파라미터 | 타입 | 동작 |
|---|---|---|
| `color` | `string \| null` | 색상 조건. BE 가 `attributes` LIKE 로 필터. decompose 가 색상 언급 시 추출·전송(값 1개) |

즉 AI 가 사용자 발화에서 색상 표기를 하나 뽑아 그대로 전송하고, BE 는 그 문자열 하나로
`attributes` 를 LIKE 매칭한다 — 동의어(예: `남색`으로 검색했는데 상품은 `네이비`로 등록)는
원리적으로 못 잡는다.

## 2. 확정된 계약

`color` 는 `string[] | null` 이고, **`brandName` 방법 D**(§4.6, v0.15.23)와 **동일 규약**
이다 — 반복 파라미터로 전량 전송:

```
GET .../internal/products/search?color=네이비&color=남색&color=곤색
```

BE 는 값들을 정규식 alternation 하나로 합쳐 `regexp_instr` 로 **부분 일치 OR** 매칭한다
(§6 Q2, §4.6 BE 실측 확인 결과). 단일 값이면 지금과 동일하게 값 1개만 보낸다(하위 호환, §5).

AI 쪽에서는 `app.pipelines.color_synonyms.expand_color`(이미 구현·테스트됨, `#258` A 파트
PR #273)가 사용자가 말한 색상 표기 하나를 승인된 동의어 묶음(예: `남색` → `[네이비, 남색,
곤색]`)으로 펼친 뒤, 그 리스트를 `color` 반복 파라미터로 전송한다. **계약은 이미 확정·배포돼
있지만, `color_synonym_expansion_enabled`/`color_synonym_array_contract_ready` 는 여전히
둘 다 `False` 로 고정돼 있다** — 운영 pg-catalog 에 색상 동의어 시드가 아직 적재되지
않아서다(§7 롤아웃 순서 참고, 기동 가드가 두 플래그의 불일치는 막지만 시드 적재 여부는
보지 않는다). BE 는 새 파싱 패턴을 배우지 않았다 — `brandName` 에서 이미 검증된 반복
파라미터 → `IN`/`OR` 규약을 그대로 재사용했다.

## 3. 왜 필요한가

`color_synonyms` 사전(2026-08-07 실측, 로컬 pg-catalog)이 색상 축의 실제 분포를 보여준다:

- 색상 표기 distinct **789종**, canonical 배정 599, 임베딩 782, `doc_count` 합 10,657.
- 분포가 극단적으로 치우쳐 있다 — 같은 색을 가리키는 표기 사이에 문서 수가 수십~수백 배
  차이 난다:

| 앵커(외래어 표기) | doc_count | 동의어(고유어/한자어 표기) | doc_count | 배율 |
|---|---:|---|---:|---:|
| 블랙 | 2,358 | 검정 | 11 | ×214 |
| 네이비 | 632 | 남색 | 8 | ×79 |
| 레드 | 209 | 빨강 | 7 | ×30 |
| 화이트 | 869 | 흰색 | 5 | ×174 |

셀러가 상품 등록 시 압도적으로 외래어 표기(`블랙`·`네이비`·`레드`)를 쓰지만, 구매자 발화는
고유어(`검정`·`남색`·`빨강`)로도 흔히 들어온다 — `color` 가 단일 문자열인 한, 이 두 어휘
집합의 교차는 AI 쪽에서 흡수할 수 없다. 문자열 단일 비교로는 원리적으로 못 푸는 문제다.

**라이브 I-1 union 재측정은 이번엔 하지 않았다** — I-17(Spring) 이 2026-08-07 실측에서
`scripts/check_spring_connection.py` `All connection attempts failed` 로 도달 불가라, BE
호출이 필요한 측정을 오늘 재현할 수 없었다. 대신 **2026-08-04 PR #273 실측**(라이브 BE 가
살아 있던 시점)의 union 이득 수치를 인용한다 — 측정 시점이 다르다는 점을 명시한다. **이
2026-08-04 실측은 BE 가 부분 일치를 배포한 바로 그날 잰 값이다**(§2·§6 Q6 — BE 배포 커밋도
2026-08-04) — 즉 이 수치는 이미 BE 부분 일치가 적용된 상태에서 잰 것이지, 정확 일치만 되던
구 동작 기준이 아니다. 46행 승인 집합으로는 **아직 재측정하지 않았다**(아래 §8 도 같은
단서를 반복한다):

| 조건 | 단일 값 | 동의어 union | 배율 |
|---|---:|---:|---:|
| `남색` | 159 | 1,145 | ×7 |
| `검정` | 649 | 3,625 | ×6 |
| `빨강` | 106 | 845 | ×8 |
| `흰색` | 998 | 3,447 | ×3 |

동의어를 union 하면 후보 집합이 3~8배 늘어난다 — 지금은 이 대부분을 그냥 놓치고 있다는 뜻이다.

### BE 부분 일치와의 역할 분담

BE 가 `attributes` 값에 부분 일치를 적용하므로(§6 Q2), **수식어 결합** 표기(`다크그레이`·
`라이트그레이`·`멜란지그레이`류 — 공유 어근 `그레이` 를 포함)는 **이미 BE 가 커버한다**.
`그레이` 로 검색하면 `다크그레이` 상품도 부분 일치로 함께 잡힌다(BE 실측 75건, §4.6 노트).

부분 일치로 **원리적으로 불가능한 것은 이종 표기 대응**이다 — `남색`↔`네이비`, `검정`↔
`블랙` 처럼 **공유 문자가 0** 인 쌍은 어떤 부분 일치 규칙으로도 서로를 매칭할 수 없다.
**이번에 승인한 46행이 정확히 그 집합이다**(§8) — 검수 당시 수식어 결합(`다크그린` 류)·
복합색(`화이트+네이비`)을 `pending_review` 로 남긴 판단은 BE 실측을 모른 채 내린 것이었지만,
결과적으로 **BE 부분 일치 동작과 상보적**이었다: BE 는 "같은 어근의 변형"을 잡고, AI 사전은
"다른 어근의 동의어"를 잡는다 — 겹치는 범위가 거의 없어 둘 다 필요하다.

## 4. 대안 비교와 탈락 이유

**(a) 콤마 구분 단일 문자열** (`color=네이비,남색,곤색`) — 값 안에 구분자로 쓸 문자가 실제
표기에 이미 등장한다. `color_synonyms` 정본에서 확인한 예: `화이트/실버`(doc_count 3),
`퍼플/보라`(11), `블랙/로즈골드`(1) — 전부 셀러가 실제로 등록한 복합색 표기다. `/` 를
구분자로 실제 표기가 쓰고 있으니, `,` 를 구분자로 골라도 언젠가 셀러가 콤마를 쓰는 표기가
나오면 파싱이 모호해진다(값 vs 구분자 충돌). **탈락** — 파싱 규약을 BE·AI 양쪽이 영구히
맞춰야 하고, 실 데이터가 이미 구분자 후보 문자를 오염시키고 있다.

**(b) BE DB 정규 색상 컬럼** — BE 가 `product` 에 정규화된 색상 컬럼을 신설하고 셀러 등록
시 표준 표기를 강제하는 방식. 셀러 입력 UX 변경(강제)과 기존 크롤 카탈로그 재적재 유지
부담이 BE 쪽에 영구히 남는다. **탈락** — 이 사전의 소유권은 AI 쪽 질의 확장 문제이지 BE
카탈로그 스키마 문제가 아니다(CLAUDE.md "AI Postgres 에는 AI 생성물만" 원칙과도 대칭).

**(c) AI 측 다중 호출 fan-out** (동의어 개수만큼 I-1 을 여러 번 호출해 합집합) — 왕복이
동의어 묶음 크기만큼(N배) 늘어난다. AI→Spring 전 구간 타임아웃이 3s(CLAUDE.md)인 hot path
에서 묶음이 3~4개만 돼도 예산을 초과하거나 극단적으로 잠식한다. **탈락**.

**(d) 런타임 벡터 유사도/LLM 확장** — 질의 시점에 임베딩 최근접이나 LLM 호출로 동의어를
그때그때 추정하는 방식. `docs/lessons.md`(2026-08-04 항목, #258)가 이미 실측으로 정리한
대로 **임베딩 우선 군집은 의미가 다른 색을 섞는다**(`남색→블루`, `다크그린→다크그레이`류
오배정) — 정밀도가 부족하고, 매 질의마다 LLM 을 태우면 hot path 예산을 또 잠식한다.
**탈락** — 그래서 #258 A 파트가 이미 "사람 검수를 거친 사전 배치 구축 + 런타임은 조회만"
구조를 택했다(오프라인 구축, `app.pipelines.color_synonym_seed.build`).

## 5. 하위 호환

- 값 1개만 보내면 지금과 동일 동작 — `color=네이비` 는 여전히 유효하다.
- `color` 미전송 시 색상 필터 없음(현행과 동일).
- FE 영향 없음 — `color` 는 AI→Spring internal 레인 파라미터이고 FE 는 이 경로를 모른다.

## 6. BE 실측 확인 결과

이 문서는 애초 아래 6개 항목을 BE 에 O/X 로 물으려 했다. **2026-08-08 jarvis-backend main 을
직접 확인한 결과 전부 이미 확정·배포돼 있었다** — 질문이 아니라 답으로 다시 정리한다(도입부
근거 참고).

### Q1. 와이어 형식 → **반복 파라미터 확정**

`color=네이비&color=남색&color=곤색`. `brandName` 방법 D(§4.6 v0.15.23)와 **동일
메커니즘**이고, **AI 쪽 코드 변경은 0** 이다 —
`app.services.spring_client._search_query_params` 가 이미 `params["color"]` 에 리스트를
넣고 httpx 가 반복 파라미터로 직렬화한다(`brandName` 도 같은 방식).

### Q2. 매칭 의미 → **OR 확정, 부분 일치**

값들 사이 OR. BE 는 정규식 alternation 하나로 합쳐 `regexp_instr` 로 본다(JPQL 이 리스트
동적 OR 을 표현하지 못해서) — `brandName`(`WHERE brand IN (...)`)과 구현은 다르지만 의미는
같다. 정확 일치가 아니라 **부분 일치**라 `그레이` 가 `다크그레이` 를 잡는다(BE 실측 75건,
§3 「BE 부분 일치와의 역할 분담」).

### Q3. 값 개수 상한 → **없음**

BE 쪽 개수 상한이 없다. 우리 승인 묶음은 최대 5(`옐로우`: `옐로우 노랑 노랑색 노란색
황색`) — 여유가 있다.

### Q4. 미전송 / 빈 값 → **필터 없음**

`color` 미전송 = 색상 필터 없음. BE 테스트 `blankColorsYieldNullPattern` 로 고정돼 있다.

### Q5. 값 정규화 주체 → **BE**

BE 가 입력값·저장값 양쪽을 trim + 소문자화해 비교한다. AI 는 카탈로그 실재 표기를 원문
그대로 보내면 된다 — 별도 정규화가 필요 없다.

### Q6. 배포 시점 → **완료**

2026-08-04 머지(`1e0ce150`), 운영 배포 완료(2026-08-08 사용자 확인). 남은 것은 배포가
아니라 **AI 쪽 운영 준비**(§7 롤아웃 순서 ②~④)다.

## 7. 롤아웃 순서

1. ~~`docs/api-spec.md` §4.6 개정~~ **완료**(v0.28.4, 2026-08-08). **정본 순서**: I-1 의
   API 표면 정본은 **BE Notion**(판정규칙 v0.15.5 — API 표면=Notion, 타입=DDL)이고
   `docs/api-spec.md` 는 그 사본이다 — Notion 정본은 BE 가 2026-08-03 LLM팀 실측 합의로
   이미 개정했고, 이번 v0.28.4 은 그 동기화다(신규 개정이 아니다).
2. **운영 pg-catalog 에 색상 동의어 시드 적재** — `db/catalog/init/05_color_synonyms_seed.sql`
   (`color_synonyms` 테이블 자체가 없으면 `db/catalog/init/03_color_synonyms.sql` 선행 적용).
   PR #273(2026-08-04)이 만든 이 init 스크립트는 **빈 볼륨에서만** 자동 실행되므로, 운영
   pg-catalog 에는 테이블·시드가 없을 가능성이 높다 — 이게 안 되면 플래그를 켜도 확장
   이득은 0 이다(검색 자체는 죽지 않는다 — `spring_client` 가 `except Exception` 으로 원문
   단수 `color` 로 degrade 한다).
3. **`color_synonym_array_contract_ready=true` + `color_synonym_expansion_enabled=true`
   동시 on** — 기동 가드(`app/core/config.py::_require_color_synonym_array_contract_gate`)가
   둘 중 하나만 켜는 것을 거부한다. **이 문서의 api-spec 사본 동기화는 두 플래그 기본값을
   켜지 않는다** — 두 플래그가 `.github/workflows/deploy.yml` 의 env 목록에 없어 **운영이
   코드 기본값을 그대로 쓴다**(확인함). 즉 여기서 기본값을 바꾸면 그대로 운영 동작 변경이
   되므로, ②(운영 DB 시드 적재)가 먼저 끝난 뒤 별도 단계로 켠다.
4. **라이브 I-1 union 재측정 + 골든셋 색상 케이스** — §3 의 2026-08-04 수치는 그때 46행
   승인 집합 기준으로 갱신한다.

## 8. 남은 검수

정본 789행 중 승인(`approved`) **46행**(앵커 15 + 동의어 31, `db/catalog/seed/
color_synonyms_review.json`), 나머지 743행은 `pending_review`. 이번 승인 46행은 "한글
고유어/한자어 ↔ 외래어 표기의 1:1 자명 대응"만 골랐다 — 수식어 결합(예: `다크그린`),
복합색(`화이트+네이비`), 미상 토큰은 전부 보류했다(§3 「BE 부분 일치와의 역할 분담」이
그 판단의 사후 근거다). 승인 확대는 이 문서와 독립적인 별도 검수 작업이다.

**§3 의 union 이득 수치는 2026-08-04 시점의 묶음 정의로 잰 것이고, 이번에 확정한 46행 승인
집합으로는 재측정하지 않았다**(Spring 도달 불가, §3). 다만 46행 묶음이 각 색상의 지배적
표기(앵커)를 포함한다는 것은 재측정 없이도 정본에서 바로 확인 가능한 사실이다 — 예를 들어
`남색`(doc_count 8) 묶음에는 그 색의 지배적 표기인 `네이비`(632)가 들어 있다. 실제 이득
배율의 재측정은 §7 롤아웃 순서 ④(AI 플래그 on 후) 라이브 I-1 로 진행한다.
