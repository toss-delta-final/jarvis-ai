# MEASURE-OPTION-COLOR-454 — 옵션 단위 재고 부재에서 지금 줄일 수 있는 피해

이슈 [#454](https://github.com/toss-delta-final/jarvis-ai/issues/454)
`[bug] 옵션 단위 재고를 몰라 "그 색만 품절"인 상품을 추천한다 — 색상 명시 턴에서 담기 실패`.
**이 문서·이 PR 은 #454 를 닫지 않는다**(`Part of #454`) — 근본 해결(옵션 단위 재고)은 BE 의
`product_stock` 신설을 기다려야 하고, 그 대응은 [#508](https://github.com/toss-delta-final/jarvis-ai/issues/508)
이 맡는다(§4). 여기서 재는 것은 **BE 없이 지금 손댈 수 있는 것 하나** — 색상 이형 표기(사용자
"검정" ↔ 판매자 "블랙") 때문에 옵션 되물음 좁히기가 못 좁히는 몫과, 승인된 색상 동의어 사전을
연결하면 얼마나 나아지는지다.

**결론 세 줄**

1. **표기 불일치가 진짜 문제다** — 라이브 I-1 실측(§1)에서 속성(`attributes.색상`)은 외래어
   (블랙·그레이·옐로우), 옵션명(`product_option.name`)은 고유어(검정·회색·노랑)로 갈린다.
   승인된 색상 동의어 사전(#258/#505)을 옵션 되물음 좁히기에 연결하면 고유어 발화의 좁힘률이
   **2.7% → 54.9%(+52.2%p)** 로 뛴다(§2, `scripts/measure_option_color_miss_454.py` 실행 재현,
   2026-08-10) — 사용자는 "검정 셔츠"라 말하고 판매자는 "블랙"이라 적는 그 간극을 메운다.
2. **AI 는 "그 색은 없다/품절이다"라고 단정할 수 없다** — 옵션명은 판매자 자유 입력
   `varchar(100)` 이고, 승인 사전(90개) 밖 표기(영문·약어·미승인 색명)와 사이즈·SKU 코드를
   AI 가 구별할 수 없다(§3). 그래서 이 PR 은 "찾지 못했어요"로만 안내하고 "없다"고 말하지
   않는다 — 승인 사전 안으로 정확히 좁혀지는 표본(고지 대상)이 색상 조건 턴의 **3.3%** 뿐이라는
   사실 자체가 그 한계의 크기다.
3. **#508(옵션 단위 재고 도입)이 할 일을 이 PR 이 미리 하지 않는다** — 품절 옵션 제외·
   `optionCount` 기준 변경·`CART_STOCK_INSUFFICIENT` 승격은 전부 #508 의 확정 계약이고,
   이 PR 은 그 계약이 오기 전까지 문구가 사용자에게 하는 약속을 최소한으로 지킨다(§4).

## 1. 라이브 I-1 실측

`GET /internal/products/search?keyword=셔츠&color=블랙`(로컬 BE `http://localhost:8080`,
2026-08-10) → 200, 163건.

- 항목 키: `attributes, brandName, categoryName, name, optionCount, options, price, productId,
  rating, reviewCount, summary` — **`stock` 키 없음**(api-spec §4.6 「주의」의 서술이 라이브에서도
  유효하다).
- `options` 는 최대 20개로 절단된 문자열 배열, `optionCount` 는 절단 전 전체 개수.
- 실례 `productId=26368525` → `optionCount=161`, `options` 20개(절단)는
  `['연핑크 / M', '검정 / XS', '베이지 / 3XL', '코발트 / S', '카키 / S', '초록 / XXL', ...]`.
  같은 상품의 `attributes.색상` 은
  `["화이트","그레이","블랙","네이비","옐로우","핑크","레드","와인","민트","오렌지","퍼플","블루","베이지","카키","그린"]`.

  → **속성은 외래어 표기, 옵션명은 고유어 표기.** 이 표기 불일치가 이 PR 이 고치는 것이다 —
  사용자가 조건으로 "검정"이라 말해도(BE 색상 매칭은 `attributes.색상` 을 보므로 이미 상품
  후보에는 들어온다), I-2 400 이 돌려주는 옵션명("검정 / XS")과의 되물음 좁히기는 승인 사전
  없이는 표기가 우연히 같을 때만 좁혀진다.

## 2. 카탈로그 실측 — 동의어 적용 전/후 좁힘률

로컬 미러 MariaDB `jarvis`(ON_SALE 6,310건 / 옵션 21,373행) 기준. 옵션 개수 분포: 1–5개 2,316 ·
6–10개 537 · 11–20개 270 · 21–50개 126 · 51–100개 37 · 100개+ 6(최대 161, 평균 6.5).

사전은 **코드가 실제로 적재하는 것 그대로** — `app.pipelines.color_synonyms.get_synonym_map`
(승인 행만, 90개 항목). 예: `검정 → ['블랙','검정','흑색','검정색']`,
`남색 → ['네이비','남색','곤색']`, `빨강 → ['레드','빨강','빨강색','붉은색','연지','홍색/적색']`
(2026-08-10 라이브 조회로 재확인 — 아래 「재현 방법」 명령 참조).

옵션 보유 ON_SALE 상품 3,292건(전체 ON_SALE 6,310건 중). (상품 × 색상) 4,439쌍(BE 색상 매칭
근사 성립, 아래 재현 방법 참조) 기준:

| 사용자 발화 표기 | 오늘 좁힘 | 동의어 등가 적용 시 | 개선 |
|---|---:|---:|---:|
| 고유어(검정·흰색·회색·빨강·파랑·노랑·초록·보라·남색·분홍) | 120 (**2.7%**) | 2,436 (**54.9%**) | **+2,316 (+52.2%p)** |
| 외래어(블랙·화이트·그레이·레드·블루·옐로우·그린·퍼플·네이비·핑크) | 2,268 (51.1%) | 2,436 (54.9%) | +168 (+3.8%p) |

**두 행이 같은 54.9%로 수렴하는 게 요점이다** — 사전이 두 표기를 같은 것으로 만든다(같은
캐노니컬 묶음이라 "검정"·"블랙" 어느 쪽으로 말해도 등가 확장 결과가 같다, 구성상 보장된다).
**이득은 고유어 발화 쪽에 몰려 있다**(사용자는 "검정 셔츠"라 말하고 판매자는 "블랙"이라 적는다).

좁혀지지 않고 남는 45.1%(2,003쌍)의 내역:

| | 건수 | 비율 |
|---|---:|---:|
| 옵션명에 색상 축이 **실재**(세그먼트가 승인 사전 키와 정확 일치) — **고지 대상**(§2-B) | 148 | **3.3%** |
| 옵션명에 색상 축이 **없음**(사이즈·SKU 코드만) — **문구 불변** | 1,855 | 41.8% |

**고지 대상이 3.3%로 작다는 것 자체가 산출물이다** — 승인 사전이 90개뿐이라 "이 옵션명이 색을
적고 있다"고 확신할 수 있는 경우가 그만큼 적다. §3 이 이 한계를 더 설명한다.

### 재현 방법

`scripts/measure_option_color_miss_454.py` 를 **2026-08-10 라이브 카탈로그 미러(`jarvis-mariadb`,
ON_SALE 6,310건 / 옵션 21,373행 — §2 서두와 일치)와 pg-catalog(`color_synonyms` 승인 90행)로
직접 실행해** 위 두 표를 냈다(합성 데이터 검증이 아니라 실행 결과다). 사전은
`app.pipelines.color_synonyms.get_synonym_map`, 좁힘 판정은
`app.agents.buyer.cart.options.narrow_options`(순수 함수, 실제 R1/R2 로직)를 그대로 호출한다 —
측정과 런타임이 어긋나지 않게. BE 색상 매칭(§1 인용 — `regexp_instr` 부분 일치)은 `attributes.
색상` 값이 개념의 등가 표기를 **부분 문자열로 포함**하면 성립한 것으로 근사한다 — 판매자가
"퍼플/보라"처럼 두 색을 한 값에 슬래시로 묶어 적는 사례(배열형 색상 2,151/3,292건 중 흔하다)가
있어 정확 일치로는 모수가 실제보다 작게 잡힌다(초판 스크립트는 정확 일치를 썼다가 모수가
4,439가 아니라 3,932로 덜 잡히는 걸 이 실행에서 발견하고 부분 일치로 고쳤다).

```bash
docker exec -i jarvis-mariadb sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" jarvis -N -B \
  -e "select p.id, p.status, p.stock_quantity, coalesce(p.attributes,\"\") from product p;"' \
  > products.tsv
docker exec -i jarvis-mariadb sh -c 'mariadb -uroot -p"$MARIADB_ROOT_PASSWORD" jarvis -N -B \
  -e "select o.product_id, o.name from product_option o;"' > options.tsv

uv run python scripts/measure_option_color_miss_454.py \
    --products-tsv products.tsv --options-tsv options.tsv \
    --catalog-dsn "postgresql://jarvis:jarvis@localhost:5433/catalog"
```

**주의** — 위 두 표는 2026-08-10 이 명령을 실제로 실행한 산출값이다(합성 데이터 검증이 아니다).
카탈로그·승인 사전은 계속 갱신되므로 재실행하면 숫자가 달라질 수 있다 — 그때는 이 표를
새 실행값으로 갱신할 것. 상시 실행 대상은 아니다(조사용).

## 3. AI 가 "그 색은 없다/품절이다"라고 단정할 수 없는 이유

옵션명은 판매자 자유 입력 `varchar(100)` 이다(`product_option.name`, D2). 미좁힘 표본을
조사하면 옵션명이 `S/M/L`·`250mm` 같은 사이즈 전용, `32_MIGASYM3241`·`S8376_샤론하이/280` 같은
SKU 코드, `(19)Black/S(25~26)`·`BK / 26`·`WT / 105`·`LGR / 28` 같은 영문·약어 표기로 채워져
있다. **"그 색 옵션이 없다"와 "옵션명이 색을 안 적었다"를 AI 가 구별할 수 없다.** 승인 사전
(90개) 밖의 표기 — `크림`·`모카`·`다크모스`·영문 `Black`·약어 `BK` — 는 색인데도 색으로
인식되지 않는다. 그래서 §2 의 고지 대상이 3.3%로 작다. **이건 버그가 아니라 한계다.**

옵션명 세그먼트가 색상 사전 어휘와 **정확히 일치**할 때로 좁히면 표본 정밀도가 높다:

```
발화=검정 옵션=['네이비 / 110','그린 / 100','그린 / 105','그린 / 110','베이지 / 105']
발화=흰색 옵션=['핑크 / 250','그레이 / 230','그레이 / 240','네이비 / 245','핑크 / 245']
발화=파랑 옵션=['블랙 110','블랙 100','블랙 90','블랙 95']
발화=노랑 옵션=['오렌지','퍼플(품)(절)','그레이','그린','블루']   ← 판매자가 옵션명에 "품절"을 손으로 적었다
```

마지막 줄(`퍼플(품)(절)`)은 옵션 단위 재고가 실제로 필요하다는 현장 증거다 — 판매자가 재고
컬럼이 없으니 이름에 손으로 품절을 적은 것이다. 이 우회가 필요 없어지는 것이 #508 의 목표다.

## 4. #508 과의 경계

옵션 단위 재고 도입([#508](https://github.com/toss-delta-final/jarvis-ai/issues/508), BE 가
2026-08-09 수용)이 도착하면 무엇이 가능해지는지 — #508 본문의 확정 계약:

| 대상 | 변경 |
|---|---|
| I-1·I-3 `optionCount` | "절단 전 전체" → **"구매 가능한 것"** 기준 |
| I-1·I-3 `options` | 품절 제외, 문자열 배열 유지 |
| I-2 `error.detail.options` | 같은 기준(구매 가능)으로 필터 |
| 전 옵션 품절 담기 | `CART_OPTION_REQUIRED` + 빈 목록이 아니라 `CART_STOCK_INSUFFICIENT` |
| I-2 `availableStock` · I-18 `maxQuantity` | 옵션 재고 기준 |

이게 도착하면 §2-B 의 "찾지 못했어요" 문구가 실제 "품절이에요"로 **승격**될 수 있다 — 지금
"고를 수 있는 옵션은 이거예요"가 참인 이유는 재고가 상품 단위라 목록에 있는 어떤 옵션이든
담기면 성공하기 때문이고(§3 참조), #508 이 오면 그 목록 자체가 이미 "구매 가능한 것"만 걸러진
상태로 오므로 이 PR 의 문장은 **더 참이 된다**(전방 호환, 코드 변경 불필요).

**이 PR 이 일부러 미리 하지 않은 것**:

- `options`/`optionCount` 에서 품절 옵션을 AI 쪽에서 걸러내지 않는다 — 그 필터는 BE 데이터
  (`product_stock`)가 있어야 정확하고, AI 가 흉내 내면 §3 의 오탐(옵션명 오인식)이 "품절
  안내"라는 더 무거운 단정에 실린다.
- `CartStockInsufficient`(I-2 `STOCK_INSUFFICIENT`) 승격을 앞당기지 않는다 — 그 트리거는
  #508 의 BE 계약(전 옵션 품절 시 `CART_OPTION_REQUIRED` 대신 `CART_STOCK_INSUFFICIENT`)이고,
  지금 BE 는 여전히 상품 단위 재고만 본다(`product.stock_quantity`, `product_option`에 재고
  컬럼 없음).
- `app/services/spring_client.py` 의 `CartStockInsufficient` docstring("재고는 상품 단위,
  옵션별 재고 없음")을 정정하지 않는다 — #508 이 그 서술을 실제로 무효화할 때 함께 고친다
  (#508 본문 §4 "낡은 서술 정정"이 이미 맡고 있다).
- 후속 이슈를 새로 만들지 않는다 — #508 이 이미 등록돼 있고 이 PR 의 범위 밖 항목은 전부
  그 이슈로 미룬다는 서술만 여기 남긴다.
