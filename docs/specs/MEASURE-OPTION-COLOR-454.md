# MEASURE-OPTION-COLOR-454 — 색상 표기 이형 흡수, #508 도입 이후에도 남는 이유

이슈 [#454](https://github.com/toss-delta-final/jarvis-ai/issues/454)
`[bug] 옵션 단위 재고를 몰라 "그 색만 품절"인 상품을 추천한다 — 색상 명시 턴에서 담기 실패`.

**전제 정정(2026-08-10)** — 이 문서는 처음에 "BE 가 옵션별 재고를 아직 안 냈다"를 전제로
작성됐다. **틀렸다.** BE 는 **2026-08-09 에 구매자 쪽(I-1·I-3·I-2)을 전량 dev 배포**했고
(노션 「BE 협의 요청」 페이지 확인 회신 *"구매자 쪽은 끝났습니다. #454 닫으셔도 됩니다"*, BE
저장소 `origin/main` 커밋 `4845776`·`40c6a35`), 이슈 [#508](https://github.com/toss-delta-final/jarvis-ai/issues/508)
(옵션별 재고 도입 대응)을 **이 PR 에 흡수**한다. `docs/api-spec.md` §4.1·§4.6·§4.9·§4.17 이
그 계약을 반영해 개정됐다(§0 참조). 처음 이 문서가 실측한 "라이브 BE 에 `stock` 키가 없다"
(§1)는 **로컬 구버전 인스턴스**(옵션별 재고 배포 전, `product_stock` 테이블 자체가 없었다)를
찌른 관찰이었지 계약 근거가 아니었다 — §1 에 그대로 정정해 남겨뒀다.

**이 문서·이 PR 이 지금 다루는 것은 그와 별개인 문제 하나다** — 색상 이형 표기(사용자
"검정" ↔ 판매자 "블랙") 때문에 옵션 되물음 좁히기가 못 좁히는 몫과, 승인된 색상 동의어 사전을
연결하면 얼마나 나아지는지. **옵션별 재고 도입이 이 문제를 대신 풀어주지 않는다** — BE 가
명시한 한계 때문이다(§0·§4): 옵션은 상품당 한 종류뿐이라, 옵션이 **사이즈**인 상품은 색상이
상품 속성에만 있어 재고 필터가 **색상별로 걸러주지 못한다**. 그래서 이 PR 의 색상 동의어
좁히기(§2-A)는 #508 이후에도 그대로 필요하다.

## 0. #508 확정 근거 (노션 정본 + BE 저장소 `origin/main`)

|---|---|
| I-1·I-3 `options` 품절 제외 | ✅ |
| I-1·I-3 `optionCount` 구매 가능 기준 | ✅ 걸러진 목록 크기를 그대로 씀 — 두 값이 어긋날 수 없음 |
| I-2 `error.detail.options` 같은 기준 필터 | ✅ |

BE 저장소 `origin/main` 코드 확인: 커밋 `4845776 feat: 재고를 옵션 단위로 전환 (02 D33 개정)`,
커밋 `40c6a35 feat: 옵션별 재고의 계약 표면 반영 (I-1·I-3·I-2·C-2·P-2)`(2026-08-09 21:33).
`CartService.java` — `productStockRepository.findQuantity(productId, optionId)`, 주석
*"재고는 담은 옵션 단위다 (02 D33 개정 — 구 상품 단위 폐기). `detail.availableStock` 는 그
옵션의 남은 수량"*. **판매자 레인은 급하지 않다** — BE 가 옛 `stockQuantity` 도 계속 받도록
해뒀고 시한이 없다. 그건 [#524](https://github.com/toss-delta-final/jarvis-ai/issues/524)
몫이라 이 PR 은 건드리지 않는다.

**⚠️ BE 가 명시한 한계** — 옵션은 한 상품에 한 종류다. 옵션이 **색상**인 상품은 품절 색이
걸러지지만, 옵션이 **사이즈**인 상품은 색상이 상품 속성에만 있어 **색상별로 못 거른다**.
BE 원문: *"「빨간 셔츠」 요청이 전부 걸러진다고 보시면 안 됩니다."* — §4 에서 더 다룬다.

### 0.1 운영 실측 (2026-08-10) — 신 계약 실응답 확인

AI 가 §6 에 "신 계약 실응답을 한 번도 직접 못 봤다"고 남긴 한계를, 사람이 운영에서 직접 실측해
채웠다(코드는 건드리지 않았다).

**① 운영 RDS(BE MariaDB `jarvis`) — `product_stock` 실재.** BE EC2(1호기) 경유 조회:

| | |
|---|---:|
| `product_stock` 테이블 | **존재** |
| 총 행수 | **24,390** |
| 품절(`quantity=0`) | **3,170** (13.0%) |
| 옵션 있는 행(`option_id IS NOT NULL`) | **21,373** |
| `product.stock_quantity` 컬럼 | **아직 존재**(마이그레이션 2단계 보류 — 노션 서술과 일치) |

옵션 있는 행 21,373 은 로컬 미러 `product_option` 행수(§2 서두)와 **정확히 일치**한다.

**② 운영 I-1 실응답 — 품절 제외가 실제로 돈다.**
`GET /internal/products/search?keyword=셔츠&color=블랙`(운영 BE, localhost 경유) → 164건.

- 항목 키: `attributes, brandName, categoryName, name, optionCount, options, price, productId,
  rating, reviewCount, summary` — **`stock` 키 없음**(§1 「주의」의 유지 판단이 맞았다).
- **`optionCount != len(options)` 인데 `optionCount <= 20`(= 절단 아님)인 항목: 0건** — 신 계약
  ("두 값이 다르면 절단만 뜻한다", api-spec §4.6)이 실제로 성립한다.
- **결정적 대조** — §1 이 인용한 그 상품 `productId=26368525`:

| | `optionCount` |
|---|---:|
| 로컬(구 계약, 2026-08-10 오전) | **161** |
| 운영(신 계약, 같은 날) | **138** |

**23개가 품절로 제외됐다.** 옵션 목록 내용도 바뀌었다(`베이지 / 3XL` 이 빠지고 `코발트 / S`
등이 남음). **이 161→138 대조는 §2 의 실측 수치가 구 스키마(옵션별 재고 도입 전) 기준이라는
것의 직접 증거이기도 하다** — 신 계약에서는 같은 상품이라도 옵션 목록이 더 짧으므로 §2 의
절대 규모(모수 4,439쌍 등)는 이 운영 스키마에서 그대로 재현되지 않는다(상대적 패턴은 불변,
§2 전제 참조).

**아직 확인하지 못한 것** — `CART_STOCK_INSUFFICIENT` + `availableStock: 0` 동반은 운영
장바구니에 실제로 담기를 시도해야 하는 작업이라 **일부러 하지 않았다**(§6 에 남겨둔다).

**결론 세 줄**

1. **표기 불일치가 진짜 문제다** — 라이브 I-1 실측(§1, 다만 아래 정정 참조)에서 속성
   (`attributes.색상`)은 외래어(블랙·그레이·옐로우), 옵션명(`product_option.name`)은 고유어
   (검정·회색·노랑)로 갈린다. 승인된 색상 동의어 사전(#258/#505)을 옵션 되물음 좁히기에
   연결하면 고유어 발화의 좁힘률이 **2.7% → 54.9%(+52.2%p)** 로 뛴다(§2,
   `scripts/measure_option_color_miss_454.py` 실행 재현, 2026-08-10) — 사용자는 "검정 셔츠"라
   말하고 판매자는 "블랙"이라 적는 그 간극을 메운다. 이 관찰은 재고 계약과 무관하다 — #508
   이후에도 그대로 유효하다.
2. **AI 는 "그 색은 없다/품절이다"라고 단정할 수 없다** — 옵션명은 판매자 자유 입력
   `varchar(100)` 이고, 승인 사전(90개) 밖 표기(영문·약어·미승인 색명)와 사이즈·SKU 코드를
   AI 가 구별할 수 없다(§3, 재고 계약과 무관한 별개 근거). 그래서 이 PR 은 "찾지 못했어요"로만
   안내하고 "없다"고 말하지 않는다 — 승인 사전 안으로 정확히 좁혀지는 표본(고지 대상)이 색상
   조건 턴의 **3.3%** 뿐이라는 사실 자체가 그 한계의 크기다.
3. **#508 도입 이후에도 색상 축이 사이즈인 상품엔 못 미친다** — 옵션별 재고가 옵션이 색상인
   상품의 품절 색은 걸러주지만, 옵션이 사이즈인 상품은 색상이 상품 속성에만 있어 재고 필터가
   색상별로 못 거른다(§0·§4의 BE 한계 인용). 그래서 이 PR 의 색상 표기 이형 흡수는 #508 이후에도
   여전히 필요하다.

## 1. 라이브 I-1 실측 — ⚠️ 로컬 구버전 인스턴스를 잰 것(계약 근거 아님)

**정정** — 아래 실측은 로컬 `http://localhost:8080` 인스턴스를 찔러서 잰 것인데, 그 인스턴스는
**옵션별 재고 배포(2026-08-09) 이전 구버전**이었다(로컬 MariaDB 미러에 `product_stock` 테이블
자체가 없었다). 그래서 "`stock` 키 없음"을 "BE 가 옵션별 재고를 아직 안 냈다"는 계약 근거로
읽으면 **틀린다** — 실제 계약 상태의 근거는 §0 의 노션 정본 + BE `origin/main` 코드다. (신
계약에서도 `stock` 필드 자체는 여전히 안 실린다 — 다만 이유가 바뀌었다: 품절 옵션은 재고
수치를 보여주는 게 아니라 **후보에서 아예 빠지는 방식**으로 처리된다, `docs/api-spec.md` §4.6.)
아래 **표기 이형 관찰(외래어 속성 vs 고유어 옵션명)은 재고 계약과 무관하게 유효**해서 그대로
남겨뒀다 — 이 PR 이 실제로 다루는 문제가 그것이다.

`GET /internal/products/search?keyword=셔츠&color=블랙`(로컬 BE `http://localhost:8080`,
2026-08-10, 구버전 인스턴스) → 200, 163건.

- 항목 키: `attributes, brandName, categoryName, name, optionCount, options, price, productId,
  rating, reviewCount, summary` — **이 구버전 응답엔 `stock` 키가 없었다.**
- `options` 는 최대 20개로 절단된 문자열 배열, `optionCount` 는 절단 전 전체 개수.
- 실례 `productId=26368525` → `optionCount=161`, `options` 20개(절단)는
  `['연핑크 / M', '검정 / XS', '베이지 / 3XL', '코발트 / S', '카키 / S', '초록 / XXL', ...]`.
  같은 상품의 `attributes.색상` 은
  `["화이트","그레이","블랙","네이비","옐로우","핑크","레드","와인","민트","오렌지","퍼플","블루","베이지","카키","그린"]`.

  → **속성은 외래어 표기, 옵션명은 고유어 표기.** 이 표기 불일치가 이 PR 이 고치는 것이다 —
  사용자가 조건으로 "검정"이라 말해도(BE 색상 매칭은 `attributes.색상` 을 보므로 이미 상품
  후보에는 들어온다), I-2 400 이 돌려주는 옵션명("검정 / XS")과의 되물음 좁히기는 승인 사전
  없이는 표기가 우연히 같을 때만 좁혀진다.

## 2. 카탈로그 실측 — 동의어 적용 전/후 좁힘률

**전제(수치를 지어내 고치지 않는다)** — 아래 표는 **구 스키마 로컬 미러**(`product_stock` 테이블
없음 = 상품마다 옵션 전체가 항상 "존재"하는 것으로 취급, 옵션별 재고 도입 이전) 기준이다. 신
계약(§0)에서는 품절 옵션이 I-1/I-2 응답에서 아예 빠지므로 옵션 목록이 더 짧아지고, 그만큼
**절대 규모(모수·좁힘 건수)는 달라질 수 있다** — 이 미러로는 재측정하지 못했다(§6 남은 위험
참조). 다만 **표기 이형 비율 자체는 옵션명 텍스트의 성질**(판매자가 "블랙"이라 적었는지
"검정"이라 적었는지)이라 어떤 부분집합으로 재도 상대적 개선폭(고유어 발화가 크게 개선되고
외래어 발화와 수렴한다는 패턴)은 구조적으로 불변이다.

로컬 미러 MariaDB `jarvis`(ON_SALE 6,310건 / 옵션 21,373행) 기준. 옵션 개수 분포: 1–5개 2,316 ·
6–10개 537 · 11–20개 270 · 21–50개 126 · 51–100개 37 · 100개+ 6(최대 161, 평균 6.5).

사전은 **코드가 실제로 적재하는 것 그대로** — `app.pipelines.color_synonyms.get_synonym_map`
(승인 행만, 90개 항목). 예: `검정 → ['블랙','검정','흑색','검정색']`,
`남색 → ['네이비','남색','곤색']`, `빨강 → ['레드','빨강','빨강색','붉은색','연지','홍색/적색']`
(2026-08-10 라이브 조회로 재확인 — 아래 「재현 방법」 명령 참조).

옵션 보유 ON_SALE 상품 3,292건(전체 ON_SALE 6,310건 중). (상품 × 색상) 4,439쌍(BE 색상 매칭
근사 성립, 아래 재현 방법 참조) 기준:

| 사용자 발화 표기 | 오늘 좁힘 | 동의어 등가 적용 시 | 개선 |
|---|---:|---:|---:|
| 고유어(검정·흰색·회색·빨강·파랑·노랑·초록·보라·남색·분홍) | 120 (**2.7%**) | 2,436 (**54.9%**) | **+2,316 (+52.2%p)** |
| 외래어(블랙·화이트·그레이·레드·블루·옐로우·그린·퍼플·네이비·핑크) | 2,268 (51.1%) | 2,436 (54.9%) | +168 (+3.8%p) |

**두 행이 같은 54.9%로 수렴하는 게 요점이다** — 사전이 두 표기를 같은 것으로 만든다(같은
캐노니컬 묶음이라 "검정"·"블랙" 어느 쪽으로 말해도 등가 확장 결과가 같다, 구성상 보장된다).
**이득은 고유어 발화 쪽에 몰려 있다**(사용자는 "검정 셔츠"라 말하고 판매자는 "블랙"이라 적는다).

좁혀지지 않고 남는 45.1%(2,003쌍)의 내역:

| | 건수 | 비율 |
|---|---:|---:|
| 옵션명에 색상 축이 **실재**(세그먼트가 승인 사전 키와 정확 일치) — **고지 대상**(§2-B) | 148 | **3.3%** |
| 옵션명에 색상 축이 **없음**(사이즈·SKU 코드만) — **문구 불변** | 1,855 | 41.8% |

**고지 대상이 3.3%로 작다는 것 자체가 산출물이다** — 승인 사전이 90개뿐이라 "이 옵션명이 색을
적고 있다"고 확신할 수 있는 경우가 그만큼 적다. §3 이 이 한계를 더 설명한다.

### 재현 방법

`scripts/measure_option_color_miss_454.py` 를 **2026-08-10 라이브 카탈로그 미러(`jarvis-mariadb`,
ON_SALE 6,310건 / 옵션 21,373행 — §2 서두와 일치)와 pg-catalog(`color_synonyms` 승인 90행)로

## 3. AI 가 "그 색은 없다/품절이다"라고 단정할 수 없는 이유

옵션명은 판매자 자유 입력 `varchar(100)` 이다(`product_option.name`, D2). 미좁힘 표본을
조사하면 옵션명이 `S/M/L`·`250mm` 같은 사이즈 전용, `32_MIGASYM3241`·`S8376_샤론하이/280` 같은
SKU 코드, `(19)Black/S(25~26)`·`BK / 26`·`WT / 105`·`LGR / 28` 같은 영문·약어 표기로 채워져
있다. **"그 색 옵션이 없다"와 "옵션명이 색을 안 적었다"를 AI 가 구별할 수 없다.** 승인 사전
(90개) 밖의 표기 — `크림`·`모카`·`다크모스`·영문 `Black`·약어 `BK` — 는 색인데도 색으로
인식되지 않는다. 그래서 §2 의 고지 대상이 3.3%로 작다. **이건 버그가 아니라 한계다.**

옵션명 세그먼트가 색상 사전 어휘와 **정확히 일치**할 때로 좁히면 표본 정밀도가 높다:

```
발화=검정 옵션=['네이비 / 110','그린 / 100','그린 / 105','그린 / 110','베이지 / 105']
발화=흰색 옵션=['핑크 / 250','그레이 / 230','그레이 / 240','네이비 / 245','핑크 / 245']
발화=파랑 옵션=['블랙 110','블랙 100','블랙 90','블랙 95']
발화=노랑 옵션=['오렌지','퍼플(품)(절)','그레이','그린','블루']   ← 판매자가 옵션명에 "품절"을 손으로 적었다
```

마지막 줄(`퍼플(품)(절)`)은 옵션 단위 재고가 실제로 필요했다는 현장 증거다 — 판매자가 재고
컬럼이 없으니 이름에 손으로 품절을 적은 것이다. #508 배포로 이 우회는 이제 필요 없어졌다(BE 가
품절 옵션을 목록에서 직접 제외한다) — 다만 아래 §4 가 보이듯, 그 배포도 색상 표기 이형 문제
자체는 풀지 못한다.

## 4. #508 흡수 — 도입 내용과 남는 한계

옵션별 재고 도입([#508](https://github.com/toss-delta-final/jarvis-ai/issues/508))을 이 PR 에
흡수했다. §0 의 확정 계약이 실제로 바꾸는 것 — `docs/api-spec.md` §4.1·§4.6·§4.9·§4.17 개정과
동일 내용:

| 대상 | 변경 |
|---|---|
| I-1·I-3 `optionCount` | "절단 전 전체" → **"구매 가능한 것"** 기준 |
| I-1·I-3 `options` | 품절 제외, 문자열 배열 유지 |
| I-2 `error.detail.options` | 같은 기준(구매 가능)으로 필터 |
| 전 옵션 품절 담기 | `CART_OPTION_REQUIRED` + 빈 목록이 아니라 `CART_STOCK_INSUFFICIENT` |
| I-2 `availableStock` · I-18 `maxQuantity` | 옵션 재고 기준 |

**§2-B "찾지 못했어요" 문구는 바꾸지 않는다.** 얼핏 "고를 수 있는 옵션은 이거예요"가 이제
"구매 가능한 것만 필터된 목록"이니 "그 색은 품절이에요"로 단정해도 될 것 같지만, **그렇지
않다** — 단정하지 않는 근거는 애초에 "BE 가 재고를 안 줬다"가 아니라 **옵션명이 판매자 자유
입력이라 표기를 신뢰할 수 없다는 것**(§3)이었고, 그 근거는 #508 이 배포된 지금도 그대로다.
BE 가 필터해 준 목록도 옵션명 텍스트 자체는 여전히 승인 사전 밖 표기(`Black`·`BK`·`크림`
등)를 담을 수 있다 — "이 옵션 목록에 사용자가 원한 색이 없다"는 여전히 "그 색이 정말 없다"를
함의하지 않는다.

**옵션별 재고가 대신 못 푸는 것 — BE 가 명시한 한계(§0)**: 옵션은 상품당 한 종류뿐이라, 옵션이
**사이즈**인 상품은 색상이 상품 속성에만 있어 재고 필터가 **색상별로 못 거른다**(BE 원문:
*"「빨간 셔츠」 요청이 전부 걸러진다고 보시면 안 됩니다"*). 즉 옵션이 색상축인 상품에서 BE 가
품절을 걸러 남긴 목록도, 사용자가 "검정"이라 말하고 판매자가 "블랙"이라 적었으면 여전히 못
좁힌다 — **그래서 이 PR 의 색상 표기 이형 흡수(2-A·2-B)가 #508 이후에도 그대로 필요하다.**

**낡은 서술 정정** — #508 이 실제로 무효화한 옛 가정("재고는 상품 단위, 옵션별 재고 없음")은
`app/services/spring_client.py`(`CartStockInsufficient` docstring)·`app/schemas/spring.py`
(`PurchaseState` 주석)·`docs/api-spec.md`(§3.1·§4.1·§4.9)에서 이 PR 이 함께 고쳤다(그 전엔
"#508 이 오면 고친다"는 지연 주석이 붙어 있었다 — 그 지연이 끝났다).

### `evals/option_color` 하네스 — before/after (같은 카탈로그, 같은 하네스)

**교차검증** — 하네스 자체 판정(`judge()`)과 **실제 구현**(`app.services.search_service.
_is_color_unbuyable`)을 항목별로 대조했다(판정 로직을 하네스가 몰래 다르게 재구현하지
않았는지 자체 증명) — **19,536건(옵션 있는 후보, 20색 누적) 중 불일치 0건.**

| 지표 | before | after |
|---|---:|---:|
| `unbuyable_rate`(옵션 있는 후보 대비) | 2,152 / 19,536 = **11.0%** | **0 / 17,384 = 0.0%**(실측 — 필터 후 집합에 판정을 다시 태워 잔여 unbuyable 이 정말 0인지 재확인했다, 아래 항등식 참조) |

| `candidates_per_query` min/max | 2,257 / 4,170 | 2,231 / 3,907 |

**후보 감소율은 크지 않다** — 중앙값 기준 −3.6%(2,579 → 2,486.5), 색상별로도 최대 감소가

— 다만 이 수치는 **키워드 없는 전체 카탈로그 기준**이라, 이슈 배경의 `keyword=셔츠` 처럼 이미
좁혀진 검색에서는 상대적 감소율이 다를 수 있다(§2 의 "모집단이 다르다" 논의와 같은 이유 —
`keyword` 슬라이스 대조는 이번에 하지 않았다, 아래 한계 참조).

### 실측 항등식 — "필터가 의도한 것만 정확히 제거했다"는 근거

`unbuyable_rate` 가 after 에서 0%가 된 것이 "정의상 당연한 결과"로 안 읽히도록, 하네스가
**두 가지를 스스로 재확인**하고 그 결과를 `filterProof`(JSON)·표준출력에 낸다(`evals/
option_color/harness.py::measure`, 이 재확인 코드만 추가했고 판정식·필터 로직은 그대로다):

1. **판정식(before, `judge()`)이 unbuyable 로 센 개수**와 **실제 필터(`_is_color_unbuyable`)가
   실제로 제거한 개수**가 색상별로 정확히 같은지(`filterRemovalMatchesUnbuyable`) — 다르면
   "필터가 판정식 밖의 후보를 건드렸다"는 뜻이라 하네스가 **에러로 중단**한다.
2. 필터를 통과한 after 집합에 판정을 **다시** 태워 잔여 unbuyable 이 정말 0인지 재확인
   (`unbuyableRateAfterFilter`, `residualUnbuyableAfterFilter`) — 0이 아니면 역시 중단한다.

2026-08-10 실행 결과(`evals/option_color/results/after-2026-08-10.json` `filterProof`):

```
후보 합계: before 54,048 → after 51,896 (감소 2,152)
unbuyable 합계(판정식, before): 2,152
일치 여부: 2,152 == 2,152 → True   (removedEqualsUnbuyable)
필터 후 잔여 unbuyable(재확인): 0   (residualUnbuyableAfterFilter)
색상별 항등식 불일치: 0건, 필터 후 잔여 불일치: 0건
```

색상별로도 전부 일치한다(예: 검정/블랙 4,170→3,907, 감소 263 = unbuyable 263). **"후보 합계
감소분(2,152) == unbuyable 합계(2,152)"** — 필터가 판정식이 잡은 것과 정확히 같은 수만
제거했다는 실측 증거다. `unbuyableRate` 필드명은 `unbuyableRateBeforeFilter`/
`unbuyableRateAfterFilter` 로 나눠 JSON 만 봐도 before/after 가 구분되게 했다(이전엔
`aggregate.unbuyableRate` 하나뿐이라 after 실행 결과인데도 before 값 그대로처럼 읽혔다).

재현:

```bash
    --catalog-dsn "postgresql://jarvis:jarvis@localhost:5433/catalog" \

```
before/after 산출 원본: `evals/option_color/results/before-2026-08-10.json` ·
`evals/option_color/results/after-2026-08-10.json`(같은 실행에서 함께 나온다 — `measure()` 가

### 변이 시험 (§2-3)

### 한계

- **`keyword` 슬라이스 대조는 하지 않았다**(패킷 "여유 되면" — 시간상 생략). 위 수치는 무필터
  전체 카탈로그 기준이라, 좁은 검색에서의 상대적 감소율은 별도로 재야 정확하다.
- **0건 가드는 이 전량 카탈로그 측정에서 한 번도 안 떴다** — 실제 운영에서 `keyword`·
  `category` 등으로 후보가 이미 적은 검색(예: 특정 브랜드+카테고리 조합)에서는 더 자주
  개입할 수 있다. 이 하네스로는 그 좁은 케이스를 못 잰다.
- Phase 1 §6 의 한계(신 계약 실응답 미확인, 판매자 레인 범위 밖 등)는 그대로 유효하다.
