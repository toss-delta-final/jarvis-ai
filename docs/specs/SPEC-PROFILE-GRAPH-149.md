# SPEC-PROFILE-GRAPH-149 — 개인화 관계 그래프와 사용자 제어 (Personalization Relation Graph & User Control)

> 본 SPEC은 이슈 #149(계약)의 산출물이며 구현은 이슈 #150이다. `SPEC-PROFILE-001`이 소유한
> 프로필 파이프라인(reader / builder / gate) 위에, 승격된 취향을 **node·edge 투영**으로 노출하고
> 사용자가 **수정·삭제·초기화·개인화 중지**를 수행하는 계층의 동작을 EARS 수준으로 확정한다
> (**[v0.3.0]** 복구는 2026-08-07 폐기).
>
> **왜 필요한가**: 현재 취향은 편집 불가능한 마크다운 한 덩어리이고 사용자에게는 조회 창구만 있다.
> 그런데 오염된 프로필이 추천 품질을 **실제로 깎는다** — 이슈 #147의 커밋된 baseline에서
> 깨끗한 프로필 **+0.20**, 노이즈 **−0.053**, 반복 부풀림 **−0.117** nDCG@10이고, 프로필을 필터
> 생성 단계에 주입했던 구성은 게스트 대비 **−0.288**(31턴 중 29턴 필터축 오염)이었다. 즉 품질을
> 되돌릴 수 있는 유일한 주체(사용자 본인)에게 권한이 없는 상태다. 본 SPEC은 그 권한의 계약이다.

## 1. 개요 & 범위

### 1.1 목적

승격된 프로필 취향을 **사용자가 이해하고 고칠 수 있는 구조**로 노출하고, 그 수정이 **기계 재파생에
덮이지 않도록** 보장한다. 부수적으로 `SPEC-PROFILE-001` OPEN-P12(누적 상태 미구현)의 선결과제인
"자유형 한국어 fact에서 안정적 키를 결정론적으로 도출하는 방법"을 확정한다 — 그 키가 없으면
투영도 dedup도 tombstone도 성립하지 않는다.

### 1.2 In Scope

- **투영 모델**: node·edge 구조, 관계 5종의 의미와 원천, `source`/`confidence`/`evidence_count`/시각의
  소재와 노출 형태(**[v0.2.0] `evidence_count`는 내부 전용 — 와이어 미노출**, §6.1).
- **결정론적 식별·병합**: `nodeId`/`edgeKey`/`edgeId` 도출, 통제 어휘 스냅(resolver), 같은 키로
  수렴한 관측의 병합 규칙, 충돌 관계의 supersede.
- **상태 기계**: `active`(±`promoted`) / `suppressed` / `superseded` / purged의 가시성·소비 영향·복구 가능성.
- **사용자 의도 고정(pin)**: 사용자 편집이 기계 파이프라인보다 우선한다는 불변식과 그 만료 없음,
  반대 관측 누적 시의 가시적 신호(`challenged`).
- **개인화 중지 전파**: 사용 중지·수집 중지의 소비처 전수와 재개 시 복원 범위, 감쇠 정지.
- **민감정보·근거 redaction**: 쓰기 경계와 투영 경계의 역할 분담, 보존 기간.
- **저장·트랜잭션 경계**: graph DB 없이 원자성을 얻는 방법, 낙관적 동시성, 멱등 원장, 감사 저장.
- **순서 전용 불변식**: 그래프 데이터가 후보 필터에 닿지 않게 하는 기계적 집행(예외 없음 — §6.12).
- 오류 처리, 인수 기준, DoD.

  temporal KG 백엔드 기각을 **재확인**하며, 다홉 순회·그래프 추론도 구현하지 않는다(1-hop 전용).
- **EX-G4 사용자 노출용 편집 이력 API**: 유용하려면 변경 전후 **라벨 원문**이 필요하고 그것은
  api-spec §6.3 (c)의 라벨 미저장 [HARD] 규약과 충돌한다. 필요해지면 별도 계약으로 다룬다.
- **EX-G5 주문 데이터 삭제**: 전체 초기화는 주문·구매 이력을 지우지 않는다 — 그 데이터는 Spring
  소유이며 AI 표면 밖이다(§6.7).
  - **[개정 v0.2.0, 이슈 #322] 대화 전사록은 이 배제에서 빠졌다** — 전체 초기화는 이제
    `conversation_turns`(해당 사용자 행)도 물리 삭제한다(REQ-PGRAPH-061/062). v0.1.0 은 전사록을
    "개인화 데이터가 아닌 것"으로 분류해 배제했는데, 사용자가 전체 초기화를 요청한 경우까지
    붙잡고 있을 근거가 아니었다.
  - **전사록의 *보존 기간*(TTL) 설계는 여전히 배제 대상이다** — 시간 경과 삭제 정책은
    `SPEC-PROFILE-001` OPEN-P5 소관이며 본 SPEC 은 사용자 요청 트리거만 다룬다.
- **EX-G6 관리자 대행 편집**: 남의 프로필을 대신 고치는 경로를 만들지 않는다(사칭 경로 신설 금지).
- **EX-G7 프로필 export/portability**: 범위 밖.
- **EX-G8 node 단위 편집**: node는 edge의 파생물이다(§5.1). 같은 상태로 가는 쓰기 경로를 둘 만들지 않는다.
- **EX-G9 근거 원문 노출**: 대화 출처 근거의 원문은 어떤 경우에도 와이어에 싣지 않는다(§6.8).
- **EX-G10 추천 scoring 가중치 변경**: 개인화 강도 조정은 #149·#150 공통 비범위다. 본 계약은
  **통제 수단**을 만들고 강도는 건드리지 않는다.

## 3. 용어

| 용어 | 정의 |
|---|---|
| **투영(projection)** | 저장된 구조화 트리플에서 결정론적으로 파생한 node·edge 집합. 저장 모델과 다른 표현이며 별도 정본이 아니다 |
| **트리플(triple)** | `(사용자, predicate, 대상 node)`. `SPEC-PROFILE-001` §5.1 구조화 블록에 대응하는 기계 판독 형태 |
| **`edgeKey`** | `"{predicate}|{nodeId}"`. `SPEC-PROFILE-001` §5.2 `GateState.preference_key`와 **동일 개념이며 저장 위치도 하나다** |
| **개별 삭제** | 사용자가 항목 하나를 지우는 것. **[개정 v0.3.0]** 투영·요약·랭킹에서 즉시 제외되고 **원문(라벨·`evidence_refs`·근거 fact)도 같은 시점에 물리 삭제**된다. **중간 상태(`suppressed`)도 유예 창도 없고 복구 경로가 존재하지 않는다** — 되돌리기 API(I-35·`M-14`)가 2026-08-07 폐기됐다 |
| **tombstone(영구)** | 개별 삭제 뒤 남는 **최소 레코드** — `edge_key`(내용 파생 id)만 보관해 같은 취향의 재승격을 차단한다. 원문 필드는 남지 않으므로 **개인정보를 담지 않는다.** **시간 경과로 만료되지 않지만**(만료시키면 재승격으로 부활한다 — §6.3) 사용자의 명시적 전체 초기화(§6.7)는 함께 지운다 — "영구"는 *자동 만료 없음*이지 *사용자도 못 지움*이 아니다 |
| **제외(sensitive exclusion)** | 민감 주제 유래로 아예 노출되지 않는 항목. **개별 삭제와 다르다** — 카운트에도 세지 않고 사용자가 개시하지도 않는다 |
| **purge** | 물리 삭제. **[개정 v0.3.0] 트리거 3종**: (1) 사용자 요청 **개별 삭제**(§6.3 — 즉시), (2) 사용자 요청 전체 초기화(§6.7), (3) 민감 파생 보존기간(`graph_sensitive_retention_days`) 만료(§6.8). (1)에서 남는 tombstone은 purge 대상이 아니다. v0.2.0 의 "undo 창 만료"는 (1)에 흡수됐다 — **유예가 사라졌을 뿐 트리거 수는 그대로다** |
| **pin(사용자 의도 고정)** | 사용자 편집이 기계 재파생보다 우선한다는 표식. 만료되지 않는다 |
| **`graphVersion`** | 와이어에 노출하는 불투명 낙관적 동시성 토큰. 내부 단조 증가 `revision`에서 만든다 |
| **파생 멱등 키** | `profile-graph-{action}:{userId}:{scopeId}:{ifMatch}`. 클라이언트가 지정하지 않는다 |

## 5. 스키마

와이어 스키마는 api-spec §3.8·§3.9가 정본이다. 아래는 **내부 저장 모델**이며 와이어와 1:1이 아니다.
조회 응답 모델은 camelCase 공통 베이스를, inbound 변경 요청 모델은 **strict 변형**(unknown·snake_case·
collision 거부)을 상속한다. 모든 길이 상한은 **설정 주입**이며 하드코딩하지 않는다.

### 5.1 노드 — 파생물

```python
class GraphNode(BaseModel):
    """edge가 참조하는 대상. 자신을 참조하는 non-purged edge가 없으면 존재하지 않는다."""
    node_id: str                  # "{type}:{정규화 라벨}" — 안정 식별자
    type: Literal["brand", "category", "attribute", "priceBand", "ratingBand", "product", "situation"]
    label: str                    # 사람이 읽는 이름 (상한: profile_graph_label_max_chars)
    verified: bool                # 통제 어휘에 스냅됐는가 (§6.2)
    resolution: NodeResolution | None = None   # 내부 관측용 — 와이어 미노출
```

- **믿음·출처를 노드에 두지 않는다.** 같은 브랜드를 좋아하면서 특정 카테고리에서만 회피할 수 있어,
  확신도를 노드에 두면 표현할 수 없다.
- `resolution`(거리·margin·어휘 버전)은 임계 재측정 근거이므로 저장하되 **와이어에 싣지 않는다** —
  임베딩 내부값에 FE 로직이 결합되면 모델·어휘 교체가 계약 변경이 된다(`DESIGN-CATEGORY-HYBRID-59` §10).

### 5.2 엣지 — 믿음과 출처의 소재

```python
class GraphEdge(BaseModel):
    edge_key: str                 # "{predicate}|{node_id}" ≡ GateState.preference_key
    edge_id: str                  # "e_" + sha256(edge_key)[:16] — 결정론적, 재파생에 안정
    node_id: str                  # 대상 (from은 항상 사용자 자신이라 저장하지 않는다)
    predicate: Literal["prefers", "likes", "avoids", "interestedIn", "purchased"]
    status: Literal["active", "suppressed", "superseded"]
    promoted: bool                # 게이트 통과 여부 (status와 직교)
    origin: Literal["machine", "user"]
    source_latest: Literal["conversation", "purchase", "user"]
    confidence: float             # 내부 수치 — 와이어에는 3버킷만
    evidence_count: int            # 내부 전용 — 와이어 미노출 (v0.2.0, REQ-PGRAPH-006)
    evidence_by_source: dict[str, int]
    evidence_refs: list[str]      # fact key 참조 (상한: graph_evidence_refs_max)
    first_observed_at: str
    last_observed_at: str
    decay_evaluated_at: str       # 감쇠 시계 — 배치당 1회 고정 (§6.2)
    valid_from: str | None        # 승격 시각
    superseded_by: str | None     # 충돌 패자 → 승자 edge_id
    suppressed_at: str | None         # 삭제 시각 — [v0.3.0] 감사·관측용. 만료 판정 기준이 아니다(유예 없음, §6.3)
    user_intent: UserIntent | None    # pin (§6.4)
    challenge_count: int
    derived_from_sensitive: bool
    sensitive_topic: str | None   # 보존기간 판정용 — **와이어 미노출** (§6.8)
```

### 5.3 문서 — 사용자당 하나

```python
class GraphDocument(BaseModel):
    """("graph", user_id) / "v1" 에 저장되는 단일 jsonb 문서. §7.1의 원자성 근거."""
    revision: int                 # 단조 증가. 초기화로도 되돌리지 않는다
    nodes: list[GraphNode]
    edges: list[GraphEdge]
    unprojected_count: int
    truncated: bool               # [신설 v0.2.6] 이 배치 절단에서 버린 edge 가 있었나
    purged_at: str | None
    updated_at: str
```

`graphVersion`(와이어) = `"g" + str(revision)`. **[HARD] 클라이언트는 이 값을 파싱·비교하지 않는다** —
형식은 내부 구현이고 계약은 "불투명 동등성"뿐이다.

**[v0.2.0 · 개정 v0.3.0] 영구 tombstone 은 `GraphEdge` 가 아니다.** 사용자가 삭제한 edge 는 **그 시점에**
문서의 `edges` 에서 제거되고, 그 자리에 **`edge_key` 만 담는 최소 레코드**가 남는다(§6.3 REQ-PGRAPH-025). 원문 필드
(`node_id` 가 가리키는 라벨·`evidence_refs`·근거 fact)는 물리 삭제된다. 이 레코드는 재승격 차단
(REQ-PGRAPH-026)에만 쓰이므로 투영·카운트 어디에도 나타나지 않는다 — 정확한 저장 형태는 #150 이
정한다(같은 `GraphDocument` 안의 별도 리스트 / 별도 테이블 모두 §7.1 의 원자성 요건을 만족한다).

## 6. 기능 요구사항 (EARS)

> 공통 규약(HARD): 모든 튜너블(라벨 상한, edge 상한, 거리 임계·margin, 반감기, 도전 임계, 보존 기간,
> 멱등 원장 TTL, 확신도 버킷 경계)은 설정 주입이며 **하드코딩 금지**. 버킷 경계는 **계약이 아니다**.

### 6.1 투영 — 결정론

- **REQ-PGRAPH-001** 투영을 요청받으면 시스템은 저장된 **구조화 트리플**에서 node·edge를 파생해야 한다.
  프로필 마크다운 본문을 파싱해 트리플을 만들어서는 **안 된다**.
- **REQ-PGRAPH-002** 투영 경로에서 시스템은 LLM을 호출해서는 **안 된다**(요청 경로 LLM 0회 —
  `SPEC-PROFILE-001` REQ-PROF-001과 동일 정신).
- **REQ-PGRAPH-003** 같은 저장 상태에 대해 시스템은 항상 **바이트 동일한** 투영을 반환해야 한다.
  정렬은 `predicate` 고정 순서(`prefers`→`likes`→`avoids`→`interestedIn`→`purchased`) →
  `last_observed_at` 내림차순 → `edge_id` 오름차순이다. 마지막 키가
  전순서를 보장한다(정렬이 부분순서면 "결정론적"은 검증 불가능한 주장이 된다).
  - **[개정 v0.3.5, #360] 노드 정렬 규약은 삭제됐다** — api-spec v0.32.0이 `nodes[]` 배열을 폐지하고
    대상을 `edges[].object`로 인라인해 **정렬할 노드 배열 자체가 없다**. 저장 모델의
    `GraphDocument.nodes`는 남지만 그것은 와이어가 아니다.
  - **[명시 v0.3.5, #360] 투영은 문서를 다시 정렬해야 한다.** 배치 쓰기는 정렬해 저장하지만
    사용자 변경(`apply_correction`)은 새 edge를 뒤에 덧붙이고 끝나므로 **편집 직후 문서는 정렬이
    깨져 있다.** "저장된 순서를 그대로 낸다"고 구현하면 편집한 사용자에게만 순서가 어긋난다.
- **REQ-PGRAPH-004** 구조화 트리플이 없는 fact는 투영하지 않고 **개수만** `unprojected_count`로
  집계해야 한다. 내용은 어떤 형태로도 노출하지 않는다.
  - **[개정 v0.3.5, #360] 이 카운트는 와이어에 나가지 않는다** — api-spec v0.32.0이 최상위 카운트를
    전부 제거했다(「응답 필드 기준」). 저장 모델(`GraphDocument.unprojected_count`)과 서버 관측
    (로그·메트릭)에만 남는다. **내용 미노출 조항은 그대로 유효하다.**
- **REQ-PGRAPH-005** `edges`가 `profile_graph_max_edges`를 넘으면 절단하고 `truncated`를 참으로
  표시해야 한다. **페이지네이션은 도입하지 않는다** — 개인 프로필이 상한을 넘는 것은 정리·초기화
  신호이며 페이지를 넘길 대상이 아니다.
  - **[신설 v0.2.6] 절단은 쓰기 시점에도 일어나며 저장 모델이 그 사실을 기록한다.** 본 요구사항은
    §6.1(투영)에 있지만 구현은 저장 폭주 방어를 위해 절단을 **배치 쓰기 시점**으로 옮겼다
    (`profile_graph_max_edges`는 단일 jsonb의 단조 증가를 막는 상한이다). 그러면 투영이 읽는
    문서는 늘 상한 이하라 **투영만으로는 절단 여부를 복원할 수 없다** — `len(edges) == 상한`
    추정도 "우연히 딱 상한인 정상 사용자"와 구분되지 않는다. 그래서 §5.3에 `truncated: bool`을
    두고 자른 쪽이 기록한다.
  - **`truncated`의 뜻은 "상한을 넘겼다"가 아니라 "버린 게 있다"** 이다. pin만으로 상한을 넘겨
    **전부 보존한** 경우는 거짓이다 — 자르지 않았으므로. 참이면 사용자에게
    "일부만 표시됨"을 안내할 근거가 된다.
  - **[HARD, 개정 v0.3.3 / 이슈 #359] 상한은 하나가 아니라 바구니별로 나뉜다.** v0.2.2는 단일
    상한 안에서 밀려나는 **순서**(`active` → `superseded` → 자르지 않음 `suppressed`·pin)만
    정했는데, 그 구조는 자리 잠식을 막지 못한다.

    | 바구니 | 상한 | 초과 시 |
    |---|---|---|
    | pin (`user_intent` 있음) | **없음** | 넘긴 채 보존 + 경고. REQ-PGRAPH-031 [HARD]가 상한보다 앞선다 |
    | `active` (pin 아님) | `profile_graph_max_edges` | 확신도 낮은 순 폐기 |
    | `superseded` | `profile_graph_max_superseded_edges` | 확신도 낮은 순 폐기 |
    | tombstone 목록 | `profile_graph_max_tombstones` | `suppressed_at` 오래된 순 폐기 + 경고 |

    **바구니 분리 기준은 `status == "active"`** — "사용자가 만든 것이냐"로 가르면 `superseded`가
    active 바구니에 남아 잠식이 그대로 재현된다.
  - **근거(잠식)**: 단일 상한에서는 보존 우선순위가 높은 쪽이 자리를 독차지한다.
    `superseded`는 근거가 0건이어도 영구 이월되므로(§6.3) **단조 누적**되는데 `active`보다 먼저
    보존되어, `superseded` 개수가 `상한 − |pin|`에 이르면 **`active`가 하나도 남지 않는다.**
    밀려난 `active`는 투영에 안 실려 사용자가 `edgeId`를 모르고 따라서 지울 수도 없는데, 근거
    fact는 살아 있어 요약·추천에는 계속 반영된다 — **지울수록 못 지우는 게 늘어나는 되먹임**이라
    이 기능의 목적과 정반대다. (출처: 이슈 #150 코멘트 2026-08-09. 그 코멘트가 든 "사용자 삭제
    표식이 자리를 먹는다"는 절반은 #499/#358이 tombstone을 `edges` 밖 별도 목록으로 빼면서
    해소됐고, 남은 `superseded` 잠식을 여기서 닫는다.)
  - **효과**: `active edge ≤ 서로 다른 edge_key ≤ fact 수 ≤ profile_max_facts`이므로, active 상한을
    fact 상한과 같게 두면 **active 절단이 구조적으로 발동 불가**가 된다. "확률이 낮다"가 아니다.
  - **`superseded` 보호는 약해지지 않는다.** 단일 상한에서 `superseded`의 실효 예산은
    `상한 − |pin|`이었다. 분리하면 pin과 무관하게 자기 상한 전량을 받으므로 **항상 종전 이상**이다.
    `superseded`가 잘리면 같은 fact가 다음 배치에 `active`로 간주되어 **진 취향이 요약에 되살아난다**는
    비대칭(§6.1 근거)은 그대로 지켜진다 — 실현 방식이 "동률에서 이긴다"에서 "자기 예산을
    보장받는다"로 바뀌었을 뿐이다.
  - **경고는 총량 파생 임계로 낸다.** pin에 상한이 없으므로 "pin을 지키느라 남을 버렸다"는 사건
    자체가 사라진다. 남는 관심사는 문서 총량 하나뿐이라
    `len(edges) > profile_graph_max_edges + profile_graph_max_superseded_edges`일 때 경고한다 —
    다른 두 바구니가 상한에 묶여 있으므로 **초과분은 정의상 pin**이고, 새 튜너블이 필요 없다.
    "상한을 넘긴 문서"가 정리·초기화 신호라는 뜻은 그대로다.
  - **잔여 리스크**: tombstone을 폐기하면 그 취향이 부활할 수 있다. 개별 삭제가 원문을 물리
    삭제하므로 재파생할 fact가 대부분 없지만, edge의 근거 목록이 `graph_evidence_refs_max`로
    잘려 있어 **목록 밖에 남은 fact까지 지웠다고 보장할 수 없다.** 확률은 낮으나 0은 아니며,
    신경 쓰이면 `graph_evidence_refs_max`를 함께 올린다.
- **REQ-PGRAPH-006** **[신설 v0.2.0, 이슈 #322]** `evidence_count`는 **내부 전용**이어야 하며 와이어에
  노출해서는 안 된다. 확신도는 `confidence` 3버킷으로만 표현한다.
  - **[개정 v0.3.5, #360] 확신도는 3버킷조차 와이어에 나가지 않는다** — api-spec v0.32.0이 `confidence`를
    응답에서 제거했고 FE도 2026-08-09에 *"'아직 확실하지 않아요'는 사용자에게 고칠 이유가 아니라
    **지울 이유**로 읽힌다"* 며 추가 요청 없음을 회신했다. 3버킷 표현
    (`profile_graph_confidence_buckets`)은 **저장 모델 전용**으로 남는다.
  - **근거**: `profile_buffer_repeat_cap`(기본 2)이 같은 발화를 2회로 잘라 세션 버퍼에 담으므로
    (`SPEC-PROFILE-001` REQ-PROF-026, 이슈 #119) **정확한 관측 횟수를 셀 수 없다.** 반복 통제가 만든
    값을 "몇 번 말했는지"로 내보내면 사실이 아닌 수를 보여주는 것이고, 소비자가 그 수로 정렬·강조를
    만들면 반복 상한이 곧 표시 상한이 된다.
  - **내부 필드는 유지된다** — REQ-PGRAPH-015 의 병합 시 합산이 계속 이 값을 쓴다. 없앤 것은
    와이어 노출뿐이며 저장 모델(§5.2)은 무변경이다.

### 6.2 식별·병합 — OPEN-P12의 종결

- **REQ-PGRAPH-010** 노드 식별자는 **`{type}:{정규화 라벨}`** 이어야 하고, `edge_key`는
  **`{predicate}|{node_id}`**, `edge_id`는 `edge_key`의 해시여야 한다. **랜덤 식별자를 쓰면
  재파생이 tombstone을 우회하므로** 이 결정론성은 기능 요구사항이다.
- **REQ-PGRAPH-011** 델타 추출 LLM은 **키를 생성해서는 안 되고**, 타입 붙은 제안
  (`kind`·`label`·`anchorPhrase`·`polarity`·`predicateHint` + 기존 게이트 신호)만 산출해야 한다.
  키 확정은 **kind별 결정론적 resolver**가 수행한다.
  - **근거(측정)**: LLM이 라벨을 직접 확정하면 같은 발화에서 값이 흔들리고 오타까지 나온 실측이
    있다(이슈 #115). 흔들리는 키에는 누적이 성립하지 않으며, 그것이 OPEN-P12가 지적한 실패다.
- **REQ-PGRAPH-012** resolver는 `DESIGN-CATEGORY-HYBRID-59`의 패턴을 따르되 두 지점을 달리해야 한다.
  (a) 앵커는 LLM 라벨이 아니라 **발화 파생 구절**이다 — 추상 라벨은 어휘와의 문자열 겹침으로
  가짜 근접을 만든다(#59 §4.3.1). (b) **never-null을 쓰지 않고 멀면 드롭**한다 — 틀린 노드는
  측정된 품질 손실(−0.053/−0.117)을 만들고 없는 노드는 손실이 ≈0이므로, 프로필 생성 시점에는
  드롭이 항상 더 싸다.
- **REQ-PGRAPH-013** 어휘 스냅에 성공하지 못한 노드는 `verified: false`로 표시해야 하고, 설정에
  따라 **랭킹에서 제외**될 수 있어야 한다. 노출은 하되(사용자가 지울 수 있어야 한다) 신뢰하지 않는다.
- **REQ-PGRAPH-014** 밴드형 노드(`priceBand`·`ratingBand`)와 `product`는 임베딩이 아니라
  **결정론적 규칙·정확 일치**로 식별해야 한다. 숫자·식별자에 근접 탐색을 쓰지 않는다.
  - **[명확화 v0.2.5] `product`의 "일치"는 형식 일치이며 `verified`는 거짓이다.** 밴드는 라벨
    자체가 정의라(가격 30000~50000) 외부 어휘 없이 자기완결적으로 `verified: true`지만, 상품
    id는 **외부 엔티티를 가리키는 참조**라 어휘 스냅(REQ-PGRAPH-013의 축)의 대상이 아니다.
  - **쓰기 시점 존재 검증은 도입하지 않는다** — 있던 상품도 품절·판매종료로 사라지므로
    (api-spec §4.9 `purchaseState`) 쓸 때 확인해도 읽을 때 다시 틀린다. 참조 유효성은 **소비
    시점**(§3.8 투영 → Spring 조회)의 책임이다. 대조할 어휘도 없다: AI는 상품 원본을 소유하지
    않고(CLAUDE.md), pg-catalog `products`는 I-17 배치 처리분만 있어 신상품이 거짓 음성이 된다.
  - 숫자 라벨은 **정수 왕복으로 정규화**한다(`"007"` → `"7"`) — 표기 차이로 `node_id`가 갈리면
    REQ-PGRAPH-010의 결정론이 깨져 지운 취향이 부활한다.
- **REQ-PGRAPH-015** 같은 `edge_key`로 수렴한 관측을 시스템은 **결정론적 코드로** 병합해야 한다:
  관측을 `(observed_at, fact_key)` 오름차순 처리, 산술은 고정 소수점으로 반올림, 감쇠 시계는
  **배치당 1회 고정**(`decay_evaluated_at`, 관측별 현재시각 금지). 같은 관측 집합을 두 번 재생하면
  동일한 문서가 나와야 한다. **LLM을 최신성·승격·병합 판단에 쓰지 않는다**(REQ-PROF-032/033).
- **REQ-PGRAPH-016** 승격·강등은 **히스테리시스**를 가져야 한다(강등 임계는 승격 임계보다 낮다) —
  배치마다 깜빡이면 사용자에게는 항목이 나타났다 사라지는 것으로 보인다.
  - **[명확화 v0.2.4] `valid_from` 은 "지금 승격이 시작된 시각"이다.** 강등 시 `None`으로 비우고,
    재승격 시 그 시점으로 새로 찍는다. 승격이 이어지는 동안에는 갱신하지 않는다.
  - **근거**: 강등은 예외가 아니라 흔한 전이다 — 반감기 30일·강등 임계 0.4에서 **약 40일 침묵이면
    내려온다**(실측). 값을 유지하면 재승격 edge가 최초 승격 시각을 물고 가, 소비자(#150 §3.8)가
    "1월부터 관심"이라고 보여주는데 실제로는 2~7월 내내 빠져 있다가 8월에 다시 생긴 관심이 된다.
    또한 값을 유지하면 `first_observed_at`과 의미가 겹쳐 필드 하나가 중복이 된다.
  - **강등은 삭제가 아니다** — `status`(`active`)와 `promoted`는 직교하므로 edge와 근거는 그대로
    남고, 비우는 것은 "이번 승격 구간"의 시작 시각뿐이다.
- **REQ-PGRAPH-017** fact 수준 dedup은 **문자열 완전 일치를 유지**해야 하고, 의미 병합은 전부
  **edge 수준**에서 수행해야 한다. 한국어 조사·어미까지 정규화하는 방식은 정당한 취향 신호를
  잃으므로 도입하지 않는다(`SPEC-PROFILE-001` 저장 계층의 기존 경계 유지).
- **REQ-PGRAPH-018** 상충하는 관계(`likes` vs `avoids` 같은 node 대상)가 생기면 패자를
  `status: "superseded"` + `superseded_by`로 표시해야 하며 **삭제하지 않는다**.
  - **[명확화 v0.2.3]** 상충은 **`avoids` vs 임의의 긍정 predicate**(`prefers`·`likes`·`interestedIn`)이며,
    `likes` vs `avoids`는 그중 한 예시일 뿐이다. §6.2 resolver가 kind별로 다른 긍정을 만들기 때문이다
    (`priceBand`·`ratingBand`·`attribute` → `prefers`, `brand`·`category`·`product` → `likes`,
    `situation` → `interestedIn`). 구현이 예시 쌍만 등록하면 7개 kind 중 4개가 판정 밖에 남아
    **모순된 두 취향이 둘 다 `active`로 공존**하고, 요약 입력(REQ-PGRAPH-022)에 "선호한다"와
    "싫어한다"가 함께 들어간다.
  - `purchased`는 긍정에 포함하지 **않는다** — 구매 사실과 회피는 모순이 아니며(구매 후 회피는
    정상 상태), 그 원천은 대화가 아니라 질의 시점 구매 이력(api-spec §4.7 I-19)이라 회피 발언이
    이력을 덮어서는 안 된다.

### 6.3 상태 기계

- **REQ-PGRAPH-020** **[개정 v0.3.0]** 상태는 `active`(±`promoted`) / `superseded` / purged(부재)여야 한다.
  **`suppressed` 는 지속 상태에서 제거됐다** — v0.2.0 은 그것을 "undo 창 만료와 함께 purged 로 넘어가는
  유계 상태"로 두었으나, 유예가 사라져 **삭제 트랜잭션 내부의 찰나**가 됐고 어떤 읽기 경로에서도
  관측되지 않는다. 나머지의 수명은 변하지 않는다.
- **REQ-PGRAPH-021** **[개정 v0.3.5, #360]** 기본 투영은 **`active`만** 포함해야 한다. `superseded`는
  노출하지 않는다. **지운 항목을 되돌려 보여주는 조회 옵션은 없다**(구 `includeSuppressed` 는 되돌리기
  화면 전용이었고 그 화면이 사라졌다).
  - **[정정 v0.3.5] v0.3.0~v0.3.2의 "`active` + `promoted`"는 정본과 어긋난 드리프트였다.** 노션 정본
    `I-32`(✅ 확정 2026-08-09)는 *"`edges`는 `active`만 싣는다 … **요약 생성이 같은 규칙을 쓴다**"* 이고
    api-spec §3.8에도 `promoted` 조건이 없다. 그 조건을 그대로 구현하면 **투영은 `active`+`promoted`,
    요약은 `active`** 가 되어 정본이 요구한 등식이 깨지고, **화면에 안 보이는데 추천에는 쓰이는 취향**이
    생긴다 — 사용자가 `edge_id`를 알 수 없어 §3.9.2 삭제도 못 한다.
  - `promoted`는 **병합 엔진 내부의 확신도 히스테리시스 값**이다. 실측상 노출·소비를 가르는 스위치로
    배선된 적이 없다 — 읽는 곳이 `graph_merge` 안쪽 4곳(`_valid_from`·강등 마진)뿐이고 밖에서 필터로
    쓰는 소비처가 0건이다. 승격 개념 자체는 REQ-PGRAPH-016의 게이트·감쇠 조항이 계속 소유한다.
- **REQ-PGRAPH-022** **[개정 v0.3.0]** 삭제된 edge 와 `superseded` edge 는 요약 생성 입력과
  랭킹(rerank 주입·홈 프로필 벡터)에서 **즉시 제외**되어야 한다. 삭제분은 원문이 남지 않으므로
  제외가 아니라 부재로 실현된다.
- **REQ-PGRAPH-023** [HARD] 삭제가 실효하려면 consolidation이 **그래프를 입력으로 읽어야** 한다.
  fact 목록을 그대로 읽는 현행 경로를 유지하면 다음 배치가 삭제된 취향을 요약에 다시 써넣어
  **삭제 기능이 겉모습만 남는다**. 이것은 선택이 아니라 선결 조건이다.
- **REQ-PGRAPH-024** `purchased` edge의 억제는 **재구매 dedup(결정 14-F)에 영향을 주지 않아야** 한다 —
  dedup은 프로필이 아니라 질의 시점 구매 이력(api-spec §4.7)을 읽는다. 계약·SPEC 양쪽에 명시한다.

#### 즉시 물리 삭제와 영구 tombstone [v0.2.0 신설 · 재작성 v0.3.0, 이슈 #322 → #499]

> 구 계약(v0.1.0)은 개별 삭제를 억제로만 처리하고 원문을 무기한 보관했다. **사용자가 "지웠다"고
> 믿는 문장의 원문을 계속 들고 있을 이유가 없다**(데이터 최소화). v0.2.0 은 원문을 남긴 명분이던
> 복구 가능성을 undo 창(`graph_undo_window_s`, 기본 5분)으로 옮겼는데, **되돌리기 API(I-35·`M-14`)가
> 2026-08-07 정본에서 폐기되면서 그 창이 지킬 대상이 사라졌다.** 되돌릴 방법이 없는데 5분을
> 기다리면 얻는 것 없이 보관 기간만 생긴다 — **삭제를 요청 시점의 물리 삭제로 되돌린다.**

- **REQ-PGRAPH-025** [HARD] **[재정의 v0.3.0]** 사용자가 edge 를 삭제하면 시스템은 **그 요청을
  처리하는 시점에 원문을 물리 삭제해야** 한다 — `GraphEdge`의 라벨 참조·`evidence_refs`와 그 refs가
  가리키는 근거 fact를 포함한다. 남는 것은 `edge_key`(또는 그 해시)뿐인 **최소 tombstone**이며,
  이것은 시간 경과로 만료되지 않는다. **유예 창도 `suppressed` 중간 상태도 두지 않는다.**
- **REQ-PGRAPH-026** [HARD] consolidation은 영구 tombstone 집합의 `edge_key`에 대해 **재승격을
  금지해야** 한다.
  - **근거(실측)**: 세션 버퍼 flush 는 `profile_idle_sweep_interval_s`(기본 60초) 주기 스케줄러로
    돈다(이슈 #79). tombstone 을 만료시키거나 조회하지 않으면 **삭제 직후 flush 가 돌면서 같은
    발화가 재승격돼 방금 지운 취향이 1분 만에 부활한다.** **[v0.3.0] undo 폐기로 이 조항의 중요도가
    올라갔다** — 유예 창이 없어져 삭제와 다음 flush 사이의 간격이 더 짧아졌다.
  - 이 조항은 **REQ-PGRAPH-023의 대체가 아니라 강화**다. 023은 "consolidation 이 그래프를 입력으로
    읽어야 삭제가 실효한다"인데, 원문 물리 삭제 후에는 **읽을 edge 자체가 없다** — 그래서 읽을
    대상이 tombstone 집합으로 하나 더 늘어난다. 둘 다 필요하며 중복 조항이 아니다.
- **REQ-PGRAPH-027** ⛔ **폐기 v0.3.0** — "논리적 만료가 물리 삭제 실행보다 우선한다"는 조항이었다.
  **유예 창이 없어져 만료 판정 자체가 사라졌고**(삭제는 요청 처리와 같은 트랜잭션에서 끝난다),
  따라서 만료 판정과 스윕 실행 사이의 레이스도 존재하지 않는다. **번호는 재사용하지 않는다.**
  부수 효과로 **#150 에서 undo purge 스윕이 통째로 불필요**해졌다.
- **REQ-PGRAPH-028** [HARD] **[범위 축소 v0.3.0]** purge 된 edge 를 대상으로 하는 재전송은
  **`404`** 여야 하며, purge 시점에 해당 edge 의 원장 항목을 무효화해야 한다.
  - **[v0.3.0] 적용 대상이 좁아졌다** — 구 조항은 undo 만료 purge 를 겨냥했으나, purge 트리거는
    여전히 **전체 초기화(§6.7)와 민감 파생 보존기간 만료(§6.8)** 가 남는다. 원장 TTL
    (`graph_idempotency_ttl_h`, 시간 단위)이 그 purge 시점보다 길 수 있다는 사실은 **그대로**이므로
    구멍도 그대로다 — 초기화로 사라진 edge 를 향한 옛 요청이 원장에 히트해 성공을 재생할 수 있다.
  - **[v0.3.0] 개별 삭제 자체에는 이 조항이 걸리지 않는다.** 같은 `If-Match` 재전송은 파생 키가
    같으므로 **원문이 없어도 `200` + `replayed: true`** 가 정답이다(api-spec §3.9.2) — 중복 클릭·
    네트워크 재시도를 오류로 만들지 않기 위해서다. 새로 조회한 뒤의 삭제는 `If-Match` 가 달라
    파생 키도 다르고 대상 edge 도 없으므로 `404` 이며, 이는 이 조항이 아니라 정상 경로다.
- **REQ-PGRAPH-029** **[축소 v0.3.0]** 지운 취향의 재등장은 **사용자의 명시적 재입력**으로만
  일어나야 한다. 기계 재파생은 어느 경우에도 해제 사유가 아니다. (구 조항의 "undo 창 이내의 명시적
  restore" 분기는 그 경로가 폐기돼 삭제됐다.)

### 6.4 사용자 의도 고정(pin) — 기능이 연극이 되지 않게 하는 조항

- **REQ-PGRAPH-030** 사용자 변경은 `origin: "user"` · 최상급 확신도 · `user_intent` 설정을 동반해야 한다
  (결정 4-A 보강 6).
- **REQ-PGRAPH-031** [HARD] `user_intent`가 있는 동안 기계 파이프라인은 `evidence_count`·
  `evidence_by_source`·`last_observed_at`·`challenge_count`만 갱신할 수 있고,
  `status`·`predicate`·`promoted`·`confidence`를 **변경해서는 안 된다**. (관측 기록은 계속한다 —
  사용자 편집이 시스템을 눈멀게 만들면 나중에 아무 근거도 제시할 수 없다.)
- **REQ-PGRAPH-032** [HARD] pin은 **만료되지 않아야 한다**(`expires_at`은 항상 없음). 만료를 두면
  사용자의 수정이 조용히 되돌려지고, 그것이 바로 이 기능이 존재하는 이유를 무효화한다.
  - **[구분 명시 v0.2.0 · 개정 v0.3.0] REQ-PGRAPH-032(pin 만료 없음)와 개별 삭제(§6.3 REQ-PGRAPH-025~029)는
    서로 다른 것을 만료시킨다.** pin 이 만료되지 않는다는 것은 *사용자 의도*(사용자가 확정한
    edge 의 상태·관계·확신도)를 **기계가 조용히 되돌리지 못한다**는 보장이다. **[v0.3.0] 개별 삭제가
    없애는 것은 *원문*뿐이며 tombstone 은 남아** REQ-PGRAPH-032 가 지키는 사용자 의도 불변을
    **삭제 방향으로** 계속 지킨다(REQ-PGRAPH-026 의 재승격 금지가 그 집행이다). **pin 이 걸린 edge 를
    사용자가 삭제하면 원문이 즉시 물리 삭제되는 것이 맞는 동작이다** — pin 은 "기계가 덮어쓰지
    못한다"이지 "사용자 자신도 못 지운다"가 아니다. REQ-PGRAPH-035 가 최신성 불변식에 대해 같은 오독 방지 문장을 남긴 것과 같은 이유로
    이 문장을 SPEC 에 박아 둔다.
- **REQ-PGRAPH-033** pin 이후 반대 관측이 `graph_pin_challenge_count`에 도달하면 `challenged`를
  참으로 표시해야 하며 **상태는 바꾸지 않아야** 한다. 취향 변화의 반영은 **명시적 사용자 동작**으로만
  일어난다. 설정값 `0`은 이 신호를 끈다.
- **REQ-PGRAPH-034** 수정(correct)은 **원자적 1회 변경**이어야 한다 — 구 edge 억제와 대상 edge
  고정이 한 revision·한 감사 행으로 처리된다. 두 번의 호출로 나누면 중간 상태와 충돌 창이 둘 생긴다.
- **REQ-PGRAPH-035** 우선순위 비교는 `(origin 클래스, last_observed_at, confidence, edge_id)`
  순서여야 한다 — 클래스가 먼저이고 최신성은 클래스 **안에서** 적용된다. 둘 다 결정론적 코드이므로
  REQ-PROF-033(LLM 최신성 위임 금지)은 유지된다. **리뷰어가 pin을 그 불변식의 예외로 오독하지
  않도록 이 문장을 SPEC에 남긴다.**

### 6.5 낙관적 동시성 · 멱등

- **REQ-PGRAPH-040** 변경 요청은 `If-Match` 선행조건을 요구해야 하며(개인화 중지 토글만 선택),
  불일치 시 `409 PROFILE_VERSION_CONFLICT`와 **최신 `graphVersion`을 함께** 반환해야 한다.
- **REQ-PGRAPH-041** 버전 단위는 **사용자당 그래프 전체**여야 한다. 쓰기 측(consolidation)이 이미
  전체를 재작성하므로 per-edge 버전은 같이 움직이며 세분화의 이득이 없다.
- **REQ-PGRAPH-042** `revision`은 단조 증가해야 하고 **초기화로도 되돌리지 않아야** 한다 —
  재사용하면 같은 `If-Match`가 서로 다른 상태를 가리킨다.
- **REQ-PGRAPH-043** 재전송 판정은 **파생 키**(`profile-graph-{action}:{userId}:{scopeId}:{ifMatch}`)로
  해야 하며, 원장에 있으면 **최초 응답 본문을 그대로** + 재전송 표식으로 반환해야 한다.
  클라이언트 지정 멱등 헤더는 도입하지 않는다.
  - 근거: 네트워크 재시도는 같은 선행조건을 지참하므로 `If-Match`가 이미 완전한 자연 키다. 원장이
    없으면 재시도가 `409`를 받는데, 최초 응답이 호출자에게 도달하지 않은 상황에서 그것은 틀린 답이다.
- **REQ-PGRAPH-044** 멱등 원장 보존 기간은 감사 로그 보존 기간보다 **길지 않아야** 한다 —
  재전송이 언제나 최초 응답을 찾을 수 있어야 한다.

### 6.6 개인화 중지(opt-out)

- **REQ-PGRAPH-050** 중지 플래그는 **전용 저장 위치**를 가져야 한다. 요약 항목에 두면 초기화가
  그것을 지워 **중지가 조용히 풀리고**, 그래프 문서에 두면 지연 크리티컬 reader가 조회를 두 번 해야 해
  `SPEC-PROFILE-001` REQ-PROF-001(단일 get)이 깨진다.
- **REQ-PGRAPH-051** 중지 시 시스템은 **사용을 중단**해야 한다: rerank 주입 없음(회원 프롬프트가
  게스트와 바이트 동일해진다 — 이슈 #119의 안전 속성), 홈 랭킹의 프로필 벡터 항 제거(api-spec §3.7
  `NO_PROFILE`), 마이페이지 마크다운 `null`.
- **REQ-PGRAPH-052** 중지 시 시스템은 **수집을 중단**해야 한다: 세션 버퍼 적재, 델타 추출,
  consolidation·요약 임베딩, **그리고 "기억해" hot-path**. 전역 중지가 개별 명시 요청보다 우선한다.
- **REQ-PGRAPH-053** 수집을 중단해도 세션 finalizer는 버퍼 정리와 처리 완료 표시를 **계속해야** 한다 —
  그러지 않으면 세션 라이프사이클이 멈춘다(`SPEC-PROFILE-001` 트리거 계약 유지).
- **REQ-PGRAPH-054** 중지 중에도 투영 조회와 모든 정리 동작(수정·삭제·초기화)이 **허용되어야** 한다.
  보존된 데이터를 지우려고 개인화를 다시 켜야 하는 상황을 만들지 않는다. 따라서 **중지 여부가 어떤
  요청의 실패로도 추론되지 않아야** 하며 전용 오류 코드를 두지 않는다.
- **REQ-PGRAPH-055** 중지 기간에는 **감쇠가 진행되지 않아야** 한다(누적 오프셋을 차감). 없으면 장기
  중지가 프로필을 조용히 침식해 "데이터는 보존된다"가 거짓이 된다.
- **REQ-PGRAPH-056** 중지 기간의 발화는 **소급 반영하지 않아야** 한다 — 전사록에서 백필하면
  "수집 중지"를 사후에 위반한다. 이는 누락이 아니라 규칙이다. 구매 소스가 구현되면 동일 원칙으로
  중지 종료 시점 이후만 스캔한다.
- **REQ-PGRAPH-057** 재개 시 보존된 `active` edge·fact·pin·요약이 그대로 복원되어야 한다.
  **[v0.3.0]** 중지 전에 삭제된 항목은 원문이 없으므로 재개로 되살아나지 않는다(tombstone 유지).

### 6.7 전체 초기화

- **REQ-PGRAPH-060** 초기화는 판별자(`scope`)를 **필수**로 요구해야 한다 — 파괴 범위를 호출자가
  명시적으로 이름 붙이게 한다.
- **REQ-PGRAPH-061** 초기화 대상: 그래프 node·edge, fact 항목, 요약(마크다운 **및** 임베딩),
  **영구 tombstone**(§6.3 — 초기화는 재파생 차단 표식도 함께 지운다), 미처리 세션 버퍼, 누적 게이트 상태,
  **[개정 v0.2.0] 대화 전사록(`conversation_turns` 중 해당 `user_id`의 행 전체)**.
  물리 삭제이며 복구 불가다.
- **REQ-PGRAPH-062** [HARD] 초기화는 **변경 감사 로그를 보존해야** 한다. 감사는 *초기화가
  일어났다는 기록*이라 함께 지우면 파괴 동작이 추적 불가가 된다. 감사 행은 원문·라벨을 담지 않고
  지문(peppered HMAC)만 남기므로(§6.9 REQ-PGRAPH-081) 사용자 데이터를 붙잡고 있는 것이 아니다.
  - **[개정 v0.2.0, 이슈 #322 — v0.1.0 은 전사록도 보존 대상이었다]** 대화 전사록은 **삭제 대상으로
    옮긴다.** 근거는 `SPEC-PROFILE-001` REQ-PROF-034 가 **이미 한 번 채택한 논거의 연장**이다 —
    *"금지 대상은 기계가 조용히 지우는 것이고 사용자 자신의 삭제권은 별개다"*. "전사록을 보존한다"의
    대상은 기계·운영이지 **사용자가 명시적으로 전체 초기화를 요청한 경우까지 붙잡고 있으라는 뜻이
    아니다.** 보존 원칙의 *예외*가 아니라 **적용 범위 한정**이며, 새 원칙을 만드는 것이 아니다.
    이 개정으로 §10 OPEN-G6 가 **해소**된다.
  - **전사록 자연 만료(TTL)와는 별개 트리거다** — 그쪽은 시간 경과로 지우는 보존 기간 정책
    (`SPEC-PROFILE-001` OPEN-P5, 미확정)이고 본 조항은 사용자의 명시적 요청으로 지운다. 서로 다른
    사건이 같은 데이터를 지울 수 있을 뿐, 둘 중 하나가 없어도 다른 하나는 성립한다. **본 조항은
    TTL 자체를 정하지 않는다.**
  - **세션 종료(api-spec §3.5 I-20)는 여전히 전사록을 지우지 않는다** — 로그아웃·비활동 종료는
    사용자의 삭제 요청이 아니다. 두 경로를 혼동하지 않는다.
  - **FE 문구**: 전사록까지 포함되면서 이 동작은 "내 데이터를 모두 삭제"에 훨씬 가까워졌다.
    v0.1.0 의 *"'모든 데이터 삭제'로 표시하면 사실과 다르다"* 는 **전사록이 남는다는 전제 위에
    있었으므로 더 이상 성립하지 않는다.** 남는 것은 감사 로그(운영 메타데이터)뿐이다. 최종 문구는
    FE 소유(api-spec C-25).
- **REQ-PGRAPH-063** 초기화는 개인화 중지 상태를 **변경해서는 안 된다** — 두 제어는 독립이다.

### 6.8 민감정보 · 근거 redaction

> **계약이 무엇을 약속하는지 정확히 고른다.** 하드 PII(주민번호·전화·이메일·카드번호)는 형식이
> 고정돼 결정론적으로 탐지되지만, **민감 *주제* 판정은 완전하지 않다** — `"당뇨"`는 잡아도
> `"혈당 관리 중"`은 놓칠 수 있다. 그래서 약속은 "민감정보를 모두 골라낸다"가 아니라
> **"골라내기에 실패해도 근거 원문은 응답·로그·trace에 나가지 않는다"** 이며, 방어선을 판정
> 정확도에 걸지 않는다. 앞의 문장은 픽스처로 검증 가능하고 뒤의 문장은 반증 사례를 영원히 찾을 수 있다.

- **REQ-PGRAPH-070** 민감 주제 목록은 **모듈 상수**로 단일 출처를 가져야 한다(판매자 미들웨어의
  기존 선례와 동일 규율 — 규칙 상수는 설정이 아니라 모듈이 소유). 범위: 건강·임신·종교·정치·
  성적지향·인종/출신·범죄경력·생체·미성년 지표·정밀위치·금융수단.
- **REQ-PGRAPH-071** 하드 PII 패턴에 히트한 발화는 **저장 전에 전량 폐기**해야 한다(파생 취향도
  만들지 않는다 — 신호가 전화번호인 선호에는 커머스 가치가 없다).
- **REQ-PGRAPH-072** 민감 주제 히트 시 **원인 텍스트를 저장하지 않고** 파생 커머스 속성만
  `derived_from_sensitive: true`로 남겨야 한다(PRD의 "당뇨 → 무설탕 선호" 규칙의 이행).
  파생 속성이 없으면 아무것도 저장하지 않는다.
- **REQ-PGRAPH-073** [HARD] "기억해" hot-path도 **같은 쓰기 경계를 통과해야** 한다. 현재 이 경로는
  발화 원문을 절단만 해서 게이트·스캔 없이 저장하며, **주민번호·전화번호·질병 진술이 저장소에
  들어가는 가장 유력한 경로**다. 이 변경은 선택 사항이 아니다.
- **REQ-PGRAPH-074** [HARD] 투영에서 대화 출처 근거의 **원문은 항상 제공하지 않아야** 한다
  (api-spec §6.3 (b) "사용자 입력 원문은 폐기한다. 원문은 대화 저장소에만 존재한다"의 이행).
  이 규칙은 민감 판정 결과와 **무관하게** 적용된다 — 실제 방어선이 여기다.
- **REQ-PGRAPH-075** [HARD] 민감 주제 라벨은 어떤 형태로도 와이어에 노출해서는 안 된다(불리언만).
  "이 취향은 건강 정보에서 파생됨"은 그 자체로 건강 정보 공개다.
- **REQ-PGRAPH-076** [HARD] 민감 제외분은 **어떤 카운트에도 포함하지 않아야** 하며 placeholder도
  두지 않아야 한다. 사용자 삭제 개수에 섞으면 **그 카운트가 곧 유출**이다.
- **REQ-PGRAPH-077** `derived_from_sensitive` edge와 그 근거는 `graph_sensitive_retention_days` 경과
  후 **물리 삭제**해야 한다.

    "유일하고 좁은 예외"로 되돌아간다. v0.2.0 은 **REQ-PGRAPH-025(개별 삭제 undo 창 만료)** 를

### 6.10 인증 · 신원 결합

- **REQ-PGRAPH-090** **[개정 v0.2.0, 이슈 #322]** 투영 조회 대상 `{userId}`는 **Spring이 자기 로그인
  세션에서 도출한 값**이어야 하며, 시스템은 **서비스 토큰만** 자격 증명으로 인정해야 한다 —
  즉 REQ-PGRAPH-091과 **동일 규칙**이다. 프로필이 없는 회원은 빈 그래프로 정상 `200`이다.
  - **v0.1.0 은 "토큰 `sub`에서만 도출, 게스트는 빈 그래프 200, 판매자 스코프는 403"이었다.**
    조회가 레인 (a) 스트림 티켓을 재사용한다는 전제였는데, **마이페이지에서는 그 티켓을 발급받을
    수 없다**(api-spec CH-1b 는 `sessionId` 필수). 티켓 클레임(`sub`·`sub_type`·`role`)이 사라지므로
    게스트·판매자 분기도 함께 사라진다 — 그 주체들은 Spring 회원 로그인 세션이 없어 이 경로에
    도달하지 않는다. 결정 19("신원은 토큰 클레임에서만")는 **레인 (a) 표면에 대해 그대로 유효**하며,
    본 표면은 레인 (b)로 옮겨졌으므로 §3.5.1(session-claim)과 같은 규율을 따른다.
  - 🔴 **확인 필요**: 게스트에게도 그래프 화면을 노출해야 한다면 `guest.id`(UUID 문자열)를 BIGINT
    `{userId}`로 표현할 수 없어 계약을 다시 열어야 한다(api-spec C-20 (4)).
- **REQ-PGRAPH-091** 변경 경로에서 시스템은 **서비스 토큰만** 자격 증명으로 인정하고 사용자 JWT를
  대체 수단으로 받아서는 안 된다. 대상 `{userId}`는 Spring이 자기 로그인 세션에서 도출한 값이라는
  전제를 계약이 [HARD]로 명시한다(api-spec C-20). **[v0.2.0] 조회(REQ-PGRAPH-090)에도 동일 적용된다.**
- **REQ-PGRAPH-092** edge 조회는 `(userId, edgeId)`로 **스코프**되어야 하고, 남의 edge와 미존재를
  **구분하지 않고 동일 응답**(`404`)을 반환해야 한다. 403을 반환하려면 남의 데이터 존재를 확인하는
  비스코프 조회가 필요해지고, 그것은 막으려는 열거 오라클을 스스로 만드는 일이다.

### 6.11 캐시·투영 무효화

- **REQ-PGRAPH-100** 변경은 AI 측 소비 경로에 **즉시 반영**되어야 한다. 중지 플래그는 기본 캐시를
  두지 않으며(즉시성 약속), 이중 방어로 요약 항목의 사용 가능 표식도 함께 내려 stale read가
  안전하게 열화하도록 한다.
- **REQ-PGRAPH-101** **[개정 v0.3.0]** 홈 추천 결과 캐시(`p5:home:{memberId}` · TTL 10분)는
  **Spring 소유라 AI가 무효화할 수 없다.** 계약은 Spring이 **수정·삭제·초기화·중지 4지점 모두에서**
  해당 회원 캐시를 무효화해야 한다고 명시한다(api-spec C-27). 구 조항은 **중지 1곳만** 적었는데,
  **지운 취향으로 만든 추천이 홈에 10분 남는 것이 중지 미반영보다 나쁘다** — 끈 것은 "반영 중"이라
  설명할 여지라도 있지만 지웠다고 말해놓고 계속 쓰는 것은 약속 위반이다.
  **🟢 [v0.3.0] BE 가 4지점 전부에 구현했다**(`jarvis-backend#132`) — AI 단독 달성 불가라는 성격은
  그대로이나 **차단 요소는 아니다.**

## 7. 저장 · 트랜잭션 경계 (graph DB 없이)

### 7.1 단일 문서가 강제되는 이유

이슈 본문은 "transaction 경계를 정의한다"고 하여 경계가 존재함을 전제하지만, **현행 인프라에는
다중 항목 원자성이 없다** — per-user advisory 잠금은 별도 연결 풀에서 잡히고 store의 트랜잭션과
결합되지 않아 각 쓰기가 자기 트랜잭션이다. 따라서:

- 그래프는 **사용자당 jsonb 문서 1개**(`("graph", user_id)` / `"v1"`)로 저장한다. 사용자당 N개
  항목으로 쪼개는 설계는 전부 찢어진 쓰기 상태를 만든다.
- pg-profile에 명시 테이블 **3개**를 추가한다: **변경 감사**(`profile_graph_audit`),
  **멱등 원장**(`profile_graph_idempotency`), **개인화 중지 플래그**(`profile_personalization_state`).
  - **[개정 v0.3.2 / 구현 #358]** v0.3.0까지는 "감사 겸 저널" 하나로 적었으나 **그대로 두면
    [HARD]를 어긴다.** REQ-PGRAPH-043은 원장이 "최초 응답 본문을 그대로" 들게 하는데, api-spec
    §3.9.1 PATCH 응답의 `edge.to`는 `"brand:소니"` — **라벨 원문**이다. 감사와 한 행에 합치면
    REQ-PGRAPH-081(라벨 원문 금지)을 어긴다. 또 초기화가 원장을 무효화할 때(REQ-PGRAPH-028)
    같은 행을 지우면 감사까지 사라져 REQ-PGRAPH-062와 충돌한다. 보존 기간도 서로 다르다
    (REQ-PGRAPH-044).
  - **[개정 v0.3.5 / 구현 #360] 원장 payload는 투영된 edge를 그대로 든다.** v0.3.2는 *"원장 payload에도
    라벨을 담지 않고, 재생 시 라벨은 현재 문서에서 다시 읽어 조립한다"* 고 적었으나 **그 재조립이
    성립하지 않는 창이 있다** — 수정 성공 뒤 그 edge를 삭제하고, 원래 `If-Match`로 온 네트워크
    재시도가 원장 TTL(`graph_idempotency_ttl_h`, 기본 24시간) 안에 도착하면 **문서에 대상이 없어
    최초 응답을 만들 수 없다.** REQ-PGRAPH-043의 "최초 응답 본문을 그대로"는 재구성이 아니라
    **보관**을 요구한다. 라벨을 원장에 두는 것은 바로 위 문단이 테이블 분리를 정당화하며 이미
    전제한 것이고(*"원장이 드는 응답 본문에 라벨 원문이 섞여 감사와 한 행에 둘 수 없다"*),
    REQ-PGRAPH-081의 라벨 원문 금지는 **감사 테이블 조항**이다. 노출 면적도 늘지 않는다 — 같은
    pg-profile이고, 초기화가 원장을 무효화하며(REQ-PGRAPH-028), TTL이 감사 보존보다 짧다
    (REQ-PGRAPH-044).
  - **[신설 v0.3.3 / 이슈 #359]** `profile_personalization_state`는 `enabled`·`disabled_at` 외에
    **중지 구간 목록**(`disabled_spans`, jsonb `[{from, to}, …]`)을 갖는다. REQ-PGRAPH-055(중지 기간
    감쇠 정지)를 집행하려면 배치가 "언제부터 언제까지 시간이 흐르지 않은 것으로 볼지"를 알아야
    하는데, 그 정보를 **그래프 문서에 두면 안 된다** — 중지·재개가 문서를 고치면 §3.9.5 응답의
    `graphVersion`·감사 before/after·멱등 원장 payload가 전부 거짓이 되고(그 경로는 "그래프 문서는
    안 바뀐다"를 전제로 같은 값을 싣는다), 그래프 잠금까지 잡아야 해 §7.2의 "락을 두 개 쥐지
    않는다"도 깨진다. 플래그 테이블은 락 없는 단일 행이라 둘 다 피한다.
    구간 수는 `graph_decay_pause_spans_max`로 제한하고, 넘으면 **가장 오래된 두 구간을 그 둘을
    포함하는 하나로 병합**한다(결정론적, 로그). 병합은 중지 시간을 과대계상하는 쪽이라 안전하다.
- fact 항목은 **증거 저장소로 유지**하고 값에 필드만 더한다 — fact 쪽 스키마 마이그레이션은 없다.

### 7.2 변경별 경계

| 변경 | 경계 |
|---|---|
| 수정·삭제 | per-user 잠금 → **재전송이면 최초 응답 재생** → 대상 부재면 `404` → 원장 claim → 문서 read-modify-write(`revision` compare-and-set) → 문서 쓰기 → 감사 기록 → 원장 완료 |
| 전체 초기화 | per-user 잠금 → 저널 기록 → 문서 교체(`revision` 유지·증가) → fact·요약·버퍼 삭제 → **전사록 삭제(`conversation_turns` where `user_id`)** → 저널 완료 |
| 개인화 중지 | 플래그 테이블 단일 행 upsert(**락 없음**) + 요약 항목 사용 표식 하향(**요약 잠금 아래**). **[v0.3.3]** 재개(`enabled=true`)는 같은 upsert 안에서 `disabled_at → now` 구간을 `disabled_spans`에 덧붙인다 — **그래프 문서는 여전히 건드리지 않는다** |

**[개정 v0.3.2 / 구현 #358]** 위 표에서 셋을 정밀화했다.

- **"복구"가 빠졌다** — I-35 폐기(v0.3.0)로 액션은 4종이다.
- **재전송 판정이 `404` 판정보다 앞이다.** 삭제가 성공하면 그 edge는 문서에서 사라지므로,
  뒤집으면 정상적인 네트워크 재시도가 전부 `404`를 받는다 — api-spec §3.9.2가 ⚠️로 경고한 그
  혼동이며, 구현 중 테스트가 실제로 잡았다. 그리고 `404`·`409`·no-op은 claim을 **되돌려** 감사
  행을 남기지 않는다(REQ-PGRAPH-080). 감사·원장 완료는 **문서 쓰기 성공 뒤에만** 기록한다 —
  그 반대면 감사가 거짓이 되고 원장이 일어나지 않은 일의 응답을 재생한다.
- **개인화 중지는 "같은 잠금 아래"가 아니다.** 그래프 락과 요약 락을 동시에 쥐면 advisory 풀에서
  커넥션을 둘 점유해 구매자 hot-path(`append_session_ctx`)가 3초 타임아웃으로 죽는다
  (`store.py::_graph_locks` 실측 주석). 플래그는 사용자당 단일 행 upsert라 그 자체로 원자적이라
  락이 필요 없고, 요약 표식만 **기존 요약 잠금** 아래에서 내린다. 두 쓰기 사이의 정합성은 잠금이
  아니라 `revision`·요약 `seq` CAS가 담당한다.

저널을 **선행 기록**하는 것이 크래시 복구의 근거다 — 기존 이벤트 멱등 테이블의
`PROCESSING`/`COMPLETED` 패턴을 그대로 따른다.

### 7.3 기존 데이터의 이행

- 그래프는 **다음 배치부터 누적**된다.
- **과거 데이터로 그래프를 복원할 수 없다** — 델타 추출이 산출한 현저성·명시성·반복 신호는 승격
  판정 직후 버려지고 저장소에는 fact 문자열과 생성 시각만 남는다.
- 부트스트랩은 출처를 보존하지 못하는 **정의된 best-effort 투영**이며 "그 그래프"가 아니다.
  계약과 사용자 화면 모두 이를 그렇게 취급해야 한다.

  확인됐다(`BE-NEGOTIATION-GRAPH-357` §0·§1). 잔여(브랜드 미상 4행·표기 변형 3건·하위 라인 9건)는
  **우리 사전에서 흡수할 차기 DB 정리 대상이지 협의 항목이 아니다.** 요청 경로를 쓰기 주체로 만드는
  관찰 사전 축적안도 그래서 채택하지 않는다.
- **OPEN-G3 (미검증 노드의 랭킹 기본 정책)**: `verified: false` 노드를 랭킹에서 제외하는 기본값은
  대부분의 브랜드 신호를 함께 잃을 수 있고, 포함하면 측정된 노이즈 손실을 받는다. 평가 하니스
  실행으로 결정할 사안이며 문서가 단정하지 않는다.
- **OPEN-G4 (`attribute` 축 허용 목록)**: 속성 축의 원천(카테고리 속성 스키마)을 AI가 조회할 수
  있는지 확인되지 않았다. 불가하면 색상 등 좁은 축으로 축소된다 — #150 착수 시 코드로 확인한다.
- **OPEN-G5 (즉시성과 개인화 공백의 교환)**: 삭제 즉시 반영을 위해 다음 consolidation까지 요약 사용을

- **~~OPEN-G6 (전사록 보존과의 비대칭)~~ — 🟢 해소 (v0.2.0, 이슈 #322)**: 지적은 "§6.8의 민감 파생

    그 구축은 별도 이슈로 남긴다. **항목은 열린 채로 유지한다.**

## 11. 비기능 요구사항

### 지연 · 예산

- 투영 조회는 문서 단일 조회 + 결정론적 파생이며 **LLM 0회**다. 변경은 잠금 + 문서 재작성 1회 +
  저널 2회 쓰기다.
- api-spec의 예산(조회 2s / 변경 3s)은 **제안이며 실측이 아니다** — 코드가 없으므로 측정도 없다.
  그래서 api-spec §2.9 (c) 기준표(실측·확정값의 자리)에 행을 추가하지 않았다.

### 설정 주입 (하드코딩 금지)

`profile_graph_max_edges` · **`profile_graph_max_superseded_edges`** · **`profile_graph_max_tombstones`** ·
`profile_graph_label_max_chars` · `profile_graph_confidence_buckets` ·
`graph_node_distance_max` · `graph_node_override_margin` · `graph_pin_challenge_count` ·
`graph_demote_margin` · `graph_decay_half_life_days` · **`graph_decay_pause_spans_max`** ·
`graph_evidence_refs_max` ·
`graph_sensitive_retention_days` · `graph_audit_retention_days` · `graph_idempotency_ttl_h` ·
`graph_require_verified_for_ranking` · `graph_seed_legs_max` · `graph_optout_cache_ttl_s`.
승격 임계는 **기존 게이트 임계를 재사용**한다 — 두 번째 임계 키를 만들지 않는다.

- **[신설 v0.3.3 / #359] 절단 상한 3종** — `profile_graph_max_edges`(active)·
  `profile_graph_max_superseded_edges`·`profile_graph_max_tombstones`(REQ-PGRAPH-005).
  `profile_graph_max_edges`는 **키 이름을 유지하되 뜻이 `active` 전용으로 좁아졌다** — 개명하면
  운영 env·문서가 갈라지는데 얻는 것이 없다. **active 상한은 `profile_max_facts`와 같은 값으로
  둔다**: 그래야 `active ≤ fact 수 ≤ 상한`이 성립해 active 절단이 발동 불가가 된다(REQ-PGRAPH-005).
- **[신설 v0.3.3 / #359] `graph_decay_pause_spans_max`** — 중지 구간 목록의 최대 길이(§7.1).
  넘으면 가장 오래된 두 구간을 병합한다. 감쇠 정지 자체를 끄는 스위치가 아니다.

- **`graph_undo_window_s` ⛔ 폐기 v0.3.0** — v0.2.0 이 "개별 삭제 후 원문을 보관하는 유예(기본 300초)"로
  신설했으나, **되돌리기 API 폐기로 보관할 이유가 사라져 키 자체를 없앤다**(§6.3 REQ-PGRAPH-025).
  코드에 도입된 적이 없어 제거 비용은 0이다.
- **tombstone 영구성은 튜너블이 아니다** — 만료 설정을 두면 REQ-PGRAPH-026 이 무력화돼 지운
  취향이 부활하므로, "끌 수 있는 안전장치"로 만들지 않는다.
- **[v0.3.0] `graph_idempotency_ttl_h` 와 유예 창의 대소 전제는 사라졌다** — 그 창이 없다.
  다만 **REQ-PGRAPH-028 은 남는다**: 원장 TTL 이 초기화·민감 만료 purge 시점보다 길 수 있어,
  사라진 edge 를 향한 옛 요청이 원장에 히트할 여지가 그대로다. **두 값의 대소로 정확성을 맞추려는
  설정은 여전히 금지**한다(운영자가 값을 바꾸면 조용히 깨지는 불변식을 만든다).
- **`graph_decay_half_life_days`**(v0.1.1 추가, 이슈 #356) — §6 공통 규약이 튜너블로 열거한
  "반감기"에 대응하는 키인데 목록에서 누락돼 있었다. 장식이 아니라 **REQ-PGRAPH-016의 전제**다:
  게이트가 `salience ≥ profile_gate_threshold`인 관측만 저장하므로, 감쇠가 없으면 `confidence`가
  승격 임계 아래로 내려갈 수 없어 **강등이 구조적으로 도달 불가**해지고 히스테리시스가 형식만
  만족된다. 위 tombstone 영구성과 혼동하지 않는다 — 감쇠는 `promoted` 를 내리는 것이고
  tombstone 은 `status` 라 서로 직교한다.

### 안전·일관성 불변식 (must-hold)

- 투영은 LLM 0회·결정론적이며 정렬은 전순서다(REQ-PGRAPH-002·003).
- 같은 트리플은 항상 같은 식별자이며 중복 node·edge는 구조적으로 불가능하다(REQ-PGRAPH-010).
- 사용자 편집은 기계 재파생에 덮이지 않고 그 보장은 만료되지 않는다(REQ-PGRAPH-031·032).
- **[개정 v0.3.0]** 개별 삭제는 **요청 시점에 원문을 남기지 않으며 복구 경로가 없고**, 지운 취향은
  tombstone 때문에 재승격되지 않는다(REQ-PGRAPH-025·026). **사라지는 것은 원문이지 사용자 의도가
  아니다** — tombstone 이 그 의도를 삭제 방향으로 계속 집행한다(REQ-PGRAPH-032 구분 문장).
- 사용자 요청 삭제는 기계 자동 삭제 금지의 적용 범위 밖이며 **항상 감사된다**(REQ-PGRAPH-062·080).
- 근거 원문·민감 주제 라벨·프로필 마크다운 본문·모델 식별자는 와이어에 나가지 않으며, 이 보장은
  **민감 판정 성공 여부와 무관하다**(REQ-PGRAPH-074·075).
- 민감 제외분은 어떤 카운트에도 세지 않는다(REQ-PGRAPH-076).
- 그래프 데이터는 후보 필터에 닿지 않는다(INV-PGRAPH-ORDER).
- 개인화 중지는 사용과 수집을 동시에 멈추고, 중지 중에도 정리 동작은 허용되며, 중지 여부가 실패로
  추론되지 않는다(REQ-PGRAPH-051·052·054).
