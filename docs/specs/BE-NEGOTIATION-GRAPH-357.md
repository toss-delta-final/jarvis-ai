## 1. C-28 — 브랜드 통제 어휘 (해소 — 협의 항목에서 내린다)

**BE에 보낼 요청은 0건이다.** 아래는 이제 「협의 진행 중」이 아니라 **「해소 경과 기록」**이다.

### 1.1 왜 이 항목이 있었나 — 원래 문제

브랜드 노드가 통제 어휘에 스냅되지 않으면 표기 변형(`헤지스` vs `HEZIS` 류)이 그래프 노드를
여러 개로 쪼갠다. 사용자가 "헤지스 싫어"로 하나를 지워도 나머지 표기가 살아남아 tombstone을
우회하고, 지운 취향이 다른 표기로 되살아난 것처럼 보인다. 이것이 C-28을 협의 항목으로 올린
원래 이유다.

### 1.2 문제가 실재했다는 근거 — 2026-08-04 시드 스냅샷(역사)

**2026-08-04 시드 스냅샷 기준**(정규화 규칙·재현 명령은 §8.3)으로 문제가 실재했음을 확인했다:

| 지표 | 값(2026-08-04 시드) |
|---|---|
| brand 테이블 행 수 | 2,368 |
| 동일 실체 그룹(별칭 묶음) / 관여 brand 행 / 관여 상품 | 123 / 261 (11.0%) / 1,415 (21.6%) |

또한 **자동 병합이 위험하다는 반례**도 확인했다 — `카스`/`카스(cas)`는 이름만 보면 같은 브랜드
같지만, 상품을 열어보니 하나는 계측기 브랜드(체감온도계·혈압계), 하나는 CAS 디지털 온습도계로
**실제로 다른 브랜드였다**(§8.3). 정규화 규칙만으로 자동 병합했다면 오병합이 났을 사례다. **이
역사적 실측이 "왜 이 작업이 필요했나"의 근거이며, 지금은 현재 상태가 아니다** — 이후 BE 정리로
대부분 해소됐다(§1.3).

### 1.3 어떻게 해소됐나 — BE 정리 + 오늘 재검증

BE가 8/5~8/7에 걸쳐 정리해 브랜드가 **2,368행 → 2,143행**이 됐다. 도착한 것 4건(전부
`.orca/drops/`, 저장소 밖 · 커밋 금지):

1. **8/7 브랜드 병합 결과**(`브랜드병합-결과.md`) — 106행 병합 / `brand_id` 110건 삭제.
2. **8/5 정리 대응표**(`브랜드병합-대응표-20260805.md`, 사후 복원) — 34건 감소.
3. **브랜드 아님 후보목록**(`브랜드아님-후보목록.md`) — 자리표시자 14 + 거래형태 13 + 판매자코드
   14 = **41건 · 상품 249개**. 오탐 3건(`노브랜드`=이마트 PB · `참조은산업` · `애구애구 OEM`)은

## 2. C-27 — 개인화 중지·초기화 시 Spring 캐시 무효화 (축소 — 구현 시 한 줄 요청)

### 2.1 현황 실측 — `jarvis-backend` 코드 직접 확인

**BE repo(`~/inte-final/jarvis-backend`, head `eed93d0`, 읽기 전용)를 직접 읽어 확인했다.**
대상: `HomeRecommendationService`(`src/main/java/com/jarvis/recommendation/`).

1. **캐시 키는 `p5:home:{memberId}` — 회원 id 단독이다.**
   ```java
   private static final Duration CACHE_TTL = Duration.ofMinutes(10);
   private static final String CACHE_KEY_PREFIX = "p5:home:";
   ```
   → **우리 `api-spec` §4.11이 틀렸다.** 사본은 캐시 키를 *"회원 id + 카탈로그 버전 + 알고리즘
   버전"*이라고 적고 있는데 **구현에는 회원 id밖에 없다.** 사본 드리프트로 기록한다(§9.6 diff,
   §2.6-(a)).
2. **`writeCache()` 호출 지점은 코드 전체에 딱 한 곳이고, 개인화 성공 분기에만 있다.** 인기상품
   대체(`fallback()`)는 **캐시에 쓰지 않는다.**
   → **개인화 「재개」는 무효화가 필요 없다.** 껐다 켜면 캐시가 비어 있어 즉시 개인화가 돌아온다.
   ⚠️ **직전 개정에서 "재개도 트리거 3개 중 하나"라고 적었던 것은 틀렸다 — 이번에 뺀다.** 이건
   BE에 물으려던 확인 질문("fallback이 회원 키에 저장되나요?")의 답이기도 하다 — 코드에 답이
   있었으므로 **질문 자체를 삭제한다.**
3. **무효화 코드는 없다** — `HomeRecommendationService` 안에 `redisTemplate.delete(...)` 호출이
   0건이다. 단 `StringRedisTemplate`은 이 서비스에 **이미 주입돼 있다**(필드 선언 확인).
4. **BE에 개인화 중지·그래프 관련 구현이 0건이다** — `personalization`·`graphVersion` 전체
   검색 0건. 즉 기존 코드를 고치는 게 아니라 **M-15·M-16을 새로 만들 때 같이 넣는 것**이다.
   (§3.1에서 확인한 AI 쪽 `internal/profile` HTTP 표면 0건과 같은 결과이지만, AI 쪽은 내부 모델
   계층은 이미 착수돼 있다 — §3.1 참조.)

**「AI 단독 불가」의 메커니즘은 그대로 유지된다** — `recommend()`의 첫 문장이 `readCache()`이고
히트하면 그대로 반환한다. 캐시가 히트하는 한 Spring이 I-22를 호출하지 않으므로, 저희 쪽 코드가
실행될 기회 자체가 없다. 이것이 이 항목이 AI 단독으로 달성 불가한 유일한 이유다.

### 2.2 영향 범위 — 문제는 2가지로 좁혀진다

| 사용자 행동 | 캐시로 인한 문제 | 무효화 필요 |
|---|---|---|
| 개인화 중지(I-37 / M-16) | 최대 10분간 개인화 홈 유지 | **예** |
| 전체 초기화(I-36 / M-15) | 지운 취향 기반 추천이 최대 10분 유지 | **예** |
| 개인화 재개 | 없음 — `fallback()`은 캐시되지 않는다(§2.1-2) | 아니오 |
| 개별 수정·삭제(I-33/I-34) | 없음 — 다음 consolidation 전엔 랭킹 미반영(`SPEC-PROFILE-GRAPH-149` OPEN-G5) | 아니오 |

**"무엇을 요구하지 않는지"가 요청의 신뢰도를 만든다.** 재개는 캐시에 아무것도 안 쓰이니 비울 게
없고, 개별 수정·삭제는 캐시를 비워도 다음 프로필 요약 갱신 전까지는 같은 추천이 나온다 —
두 경우 다 무효화를 걸어도 실질 효과가 없다. 그래서 R-27-1 요청은 **중지·초기화 2곳**으로만 좁힌다
(직전 개정까지의 "항목 삭제도 넣어 달라"는 요청은 철회 — §2.5).

### 2.3 옵션 비교 — 축소

무효화가 **가능하다는 것이 코드로 확인**됐으므로(§2.1-3, `StringRedisTemplate` 기 주입) TTL
단축·FE 캐시 우회·사용자 고지 같은 대안은 더 이상 주된 선택지가 아니다.

| 옵션 | 소유 | 상태 |
|---|---|---|
| **A. Spring이 중지·초기화 시점에 `p5:home:{memberId}` 삭제** | Spring | **사실상 확정** — Redis 키 삭제 한 줄, `StringRedisTemplate` 이미 주입됨 |
| B~D(TTL 단축·FE 우회 재요청·무효화 없음+고지) | — | A가 확정적이라 더 이상 논하지 않는다. **A가 "무효화 불가"로 판명될 경우의 폴백으로만** 한 문단 남긴다: 그때는 D(무효화 없음 + 고지)가 최후 대안이며, 문구 초안은 §2.7에 보존한다(삭제하지 않음 — 회신이 뒤집힐 수 있다) |

**AI가 할 수 있는 대안은 여전히 없다** — §2.1의 메커니즘 때문에 AI 소유 옵션은 처음부터 없었다.

### 2.4 추천안

**A를 확정한다.** 코드 실측으로 A의 비용이 "Redis 키 삭제 한 줄"임이 드러났고, 필요 지점도
2곳(중지·초기화)으로 좁혀졌다. 이제 확약이 아니라 **구현 시 한 줄을 부탁하는 요청**이다.

### 2.5 BE에 보낼 요청문 — 짧아졌다

> **C-27 — 개인화 중지·초기화 시 홈 캐시 무효화**
>
> 개인화를 껐는데 홈 추천이 최대 10분간 그대로 보이는 문제입니다. 캐시가 히트하면 Spring이
> 저희를 호출하지 않아 저희 쪽에서는 손을 쓸 수 없습니다.
>
> 코드를 보니(`HomeRecommendationService`) 캐시 키가 `p5:home:{memberId}`라 **회원 단건
> 삭제로 해결됩니다.** `StringRedisTemplate`도 이미 주입돼 있어서, 마이페이지 개인화 중지
> (M-16)·전체 초기화(M-15)를 구현하실 때 **성공 후 `redisTemplate.delete("p5:home:" +
> memberId)` 한 줄**만 넣어주시면 됩니다.
>
> - **개인화 재개는 불필요합니다** — 인기상품 대체 결과는 캐시에 쓰이지 않아(`writeCache`가
>   개인화 성공 분기에만 있음) 다시 켜면 바로 개인화가 돌아옵니다. 확인했습니다.
> - **개별 취향 수정·삭제도 불필요합니다** — 다음 배치 전엔 랭킹에 반영되지 않습니다.
>
> 별건으로 `api-spec` §4.11의 캐시 키 서술("회원 id + 카탈로그 버전 + 알고리즘 버전")이 실제
> 구현과 달라 **저희 사본을 정정하겠습니다.** 겸해서 **I-22의 `catalogVersion`이 실제 캐시 키에
> 쓰이지 않는 것이 확인됐으니 폐기 제안(C-18)을 확정해도 될지** 회신 부탁드립니다.

**해소된 옛 요청**: R-27-2(fallback이 회원 키로 캐시되는지) — 코드로 자답됨(캐시하지 않음).
R-27-3(C-18과 함께 다뤄 달라는 요청) — C-18 자체가 이미 해소돼(§5.5) 더 이상 유효하지 않다.
직전 개정의 "항목 삭제도 무효화 대상에 넣어 달라"는 요청도 철회한다 — §2.2에서 확인했듯 실질
효과가 없다.

## 4. C-21 — `If-Match`/`graphVersion` 통과 규약 (여전히 회신 대기)

### 4.1 현황 실측

- v0.26.0에서 **난이도가 내려갔다** — `409` 응답의 `graphVersion`이 봉투 밖 형제 필드에서
  `error.detail.graphVersion` 안으로 들어와, Spring은 **`error` 객체를 통째로** FE에 전달하면 된다
  (§2.5 확장 규칙, 필드를 옮겨 담는 재구성이 불필요).
- `If-Match` 형식 규약(api-spec §3.9 preamble): `If-Match: "g42"`와 `If-Match: g42`는 동등, `*`·약한
  태그(`W/"g42"`)·누락·빈 값은 `400 BAD_REQUEST`.
- AI 측 구현은 §3.1과 동일하게 **0**이므로, 지금 확약을 받아 두는 것이 리드타임상 유리하다.
- **[신설, §6 연계] 되돌리기 API(M-14 · I-35)가 노션 정본에서 폐기됨에 따라, C-21의 확약 대상
  경로 수는 실질적으로 5개(수정·삭제·초기화·중지·조회)로 줄어들 여지가 있다** — 다만 그 결정은
  §6의 "결정 1(즉시 삭제)"이 최종 수용된 뒤 api-spec 쪽에서 정리할 사안이라 이번 개정 대상에는
  포함하지 않는다.

### 4.2 옵션 비교

C-21은 "옵션"이 아니라 "Spring이 값을 변형 없이 통과시키는가"라는 예/아니오 확약 사안이라, 실패
모드별로 표를 만드는 것이 더 유용하다.

| 실패 모드 | 무엇이 깨지나 | 흔한 원인 |
|---|---|---|
| (a) `ETag`/`If-Match` 재따옴표 | `"g42"` → `"\"g42\""`처럼 값 자체가 오염돼 AI 쪽 CAS 비교가 항상 실패 | 프록시 계층이 헤더 값을 문자열로 다시 인코딩 |
| (b) 게이트웨이·WAF가 조건부 헤더 삭제 | `If-Match`가 아예 AI에 도달하지 않아 §3.9.5 optional 경로로 오분류되거나 400 | 표준 헤더가 아닌 커스텀 캐싱 규칙 |
| (c) 게이트웨이가 `409`를 다른 상태로 재작성 | FE가 충돌을 못 보고 낙관적 동시성이 무력화(C-22 연계) | 상태코드 정규화 미들웨어 |
| (d) **Spring이 AI 오류 응답을 자기 `{success,data}` 봉투로 재포장** | 다른 internal API는 `{success,data}` 봉투인데 AI 오류는 `{error:{...}}`라(§2.5) 재포장되면 FE가 `error.detail.graphVersion`을 찾지 못한다 | internal 클라이언트 공통 응답 파서가 무조건 봉투를 씌움 |

**(d)가 가장 흔한 실패 모드로 예상된다** — 다른 5개 internal API(I-2·I-18·I-19 등)가 전부
`{success,data}` 봉투라 공통 파서가 그 가정을 갖기 쉽다.

### 4.3 추천안

네 실패 모드 전부를 요청문에 **명시적 배제 요청**으로 넣는다 — 특히 (d)는 "그런 일이 없을 것"이
아니라 "AI 오류 응답은 봉투를 씌우지 말고 그대로 전달해 달라"는 구체 요청으로 못박는다.

### 4.4 BE에 보낼 요청문

> **R-21-1 (차단)** — FE→Spring 요청의 `If-Match` 값을 **변형 없이**(재따옴표·재인용·자체 생성 금지)

> **R-21-3** — 게이트웨이·WAF가 `If-Match`/`ETag` 계열 조건부 헤더를 삭제하거나 `409` 상태코드를

## 6. 노션 「♻️ 취향 관리 API 10개 — 고쳐야 할 것 정리 (되돌리기 폐기 여파)」 대응

이 절은 #357 범위를 넘지 않도록 **"우리 답 + 사본 영향"만** 적는다. 실제 `docs/api-spec.md` 개정은
하지 않았다(§5.5의 되돌리기 드리프트와 마찬가지로 §9에도 이 항목의 diff는 싣지 않는다 — 사용자
승인 후 별건으로 처리).

### 6.1 사실

- **되돌리기 API 2종(M-14 · I-35)이 폐기됐다.** 우리 `api-spec §3.9.3`(I-35 복구)은 그대로 살아
  있고, §3.8의 `includeSuppressed` · `suppressed` · `suppressedAt` · `suppressedCount`도 전부
  남아 있다 → **사본 동기화 대상**(§5.5 표에 등재).
- 상대 문서가 AI 팀에 질문 3개를 했다. §6.2가 그 답이다.
- **B-1은 우리 C-27과 같은 발견이며**, 상대가 코드 근거(`p5:home:{회원id}` · TTL 10분)를 정확히
  짚었다. 그리고 **C-27의 적용 범위를 M-13 · M-15까지 넓히자**고 제안했다 — 이는 §2.2의 트리거
  3종과 정합한다(우리도 독립적으로 같은 결론에 도달했다).

### 6.2 우리 답 3건

1. **재삭제를 404 대신 200 + `replayed: true`로 유지 가능한가 → 가능하다.**
   현행 §3.9 멱등 규약이 이미 그렇게 설계돼 있다 — 판정 키가 edge 존재 여부가 아니라 **파생 키**
   (`profile-graph-{action}:{userId}:{scopeId}:{ifMatch}`)다. 같은 `If-Match` 재전송(중복 클릭·
   네트워크 재시도)은 200 `replayed`, 새로 조회한 뒤의 재삭제는 `If-Match`가 달라 404 — 경계도
   자연스럽다.
2. **타임아웃 — Spring 4s를 제안한다.** 근거: (a) 우리 3s는 **실측이 아니라 제안치**이며 §3.8·
   §3.9가 "예산(제안, 실측 아님)"으로 명시하고 구현이 없어 아직 잴 수 없다, (b) 쓰기 경로라
   잠금·트랜잭션·감사 기록이 들어가 2s는 여유가 없다, (c) AI 예산을 줄이면 **우리가 `504
   UPSTREAM_TIMEOUT`을 낼 기회 자체가 줄어** 장애 진단이 어려워진다. 구현 후 실측해 재조정 전제.
3. **취향 추출 배치 주기 → 주기 배치가 아니라 세션 종료 트리거다.**
   `run_session_context_sweep`이 `profile_idle_sweep_interval_s`(기본 **60초**)로 돌지만 그건
   **대상 스캔**이고, 실제 발동은 **I-20(로그아웃) 즉시** 또는 `profile_session_idle_timeout_s`
   (기본 **600초**) 무활동이다. 따라서 상대 문서의 B-3(배치 중 저장이 409로 튕김) 위험은 낮다 —
   `graphVersion`은 "5분마다 주기적으로"가 아니라 **그 사용자가 대화를 끝냈을 때** 올라간다. 다만
   0은 아니므로 **FE 자동 재조회 + 1회 재시도** 규칙은 계약에 넣자고 제안한다.

### 6.3 결정 3건에 대한 우리 의견

- **결정 1 (A) 즉시 삭제 — 동의.** 되돌릴 방법이 없는데 5분 숨겨두면 얻는 게 없다.
  ⚠️ **단 재파생 차단 표식(tombstone)은 반드시 유지해야 한다** — 상대 문서도 "손대지 않는다"로
  적었다. 없으면 다음 배치가 지운 취향을 되살린다. **이 기능의 핵심이라는 것을 강조한다.**
- **결정 2 항목 삭제 확인창 — 필요하다.** 되돌릴 수 없는 삭제가 됐다.
- **결정 3 `If-Match` 필수 유지 — 동의.** 근거 문장만 교체한다 — 되돌리기가 없어져 **실수의 대가가
  오히려 커졌으므로**, 낙관적 동시성 검증을 계속 필수로 두는 것이 이전보다 더 중요해졌다.

```python
    s = re.sub(r"[\s\-_.·]", "", s)
    s = re.sub(r"[()\[\]{}]", "", s)
    return s
```

같은 정규화 규칙을 적용한다:

```python
def base(s):
    s = unicodedata.normalize("NFKC", s).strip()
    s = re.sub(r"[（(\[].*?[)）\]]", "", s).strip()   # 괄호 안 제거
    ko = re.findall(r"[가-힣]+", s)
    if ko and re.search(r"[A-Za-z]", s):
        s = "".join(ko)                                # 한/영 혼재면 한글부만
    return re.sub(r"[\s\-_.·]", "", s).lower()
```
