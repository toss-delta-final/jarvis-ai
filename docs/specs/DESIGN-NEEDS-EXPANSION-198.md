# DESIGN — 목적·상황형 발화의 상품 전개 (이슈 #198)

작성일: 2026-07-30 · 브랜치: `feat/198-shopping-list-expansion`
개정: 2026-08-01 **#217** — 전개 트리거를 marker 열거에서 **매핑 실패**로, 배선을 교체에서
**합집합**으로 (§4·§4.0·§4.4·§4.5·§6·§9·§10·§13, 브랜치 `feat/217-expansion-trigger-on-mapping-failure`)

## 1. 목적

`"집들이 선물로 뭐 사갈까"` 같은 **목적·상황형 발화**를 **구체 상품 목록**으로 전개한다.

이 단계는 정본 `SPEC-RECOMMEND-001` 에 **`shopping_list` 분해**로 이미 명세돼 있으나(§5.1
`shopping_list: list[ShoppingItem] | None`·`class ShoppingItem`+`priority`, `REQ-REC-002` 상황
키워드 → Case 3, 결정 14-E/14-H) **코드에는 0건**이다(`grep shopping_list|ShoppingItem` → 0).
#59 가 `DESIGN-CATEGORY-HYBRID-59.md` §6 에서 "Case 3 기능은 비범위, 별도 이슈 소관"으로 명시
유예한 부분이다. `RouteDecision.case` 는 그 자리에 `[폐기] 미사용` 주석과 함께 죽어 있다.

파이프라인에서의 위치 — **①이 이 문서의 소관**이고, ②·③은 이미 구현·검증돼 있다:

```
①  목적 → 상품 목록      "집들이 선물" → 디퓨저 / 식기 세트 / 핸드워시 세트     ← 본 문서
②  상품명 → canonical    "디퓨저" → 인테리어소품 > 디퓨저                    ← #115(PR #188)
③  카테고리별 검색·병합   fan-out gather → dedup → merge_cap → rerank         ← #59
```

## 2. 문제 — 프롬프트로는 해결되지 않음 (실측)

현재 ①은 `decompose` 프롬프트 문장 하나가 전부다. 강제력이 없고, 파싱(`_parse_category_queries`)은
"문자열인가·공백만은 아닌가·개수가 상한 이내인가"만 보므로 **전개 실패를 코드가 인지하지 못한다.**

실측 (실 LLM `fast` tier, 발화별 3회):

| 발화 | 전개 성공 | 실패 시 산출 |
|---|---|---|
| 집들이 선물로 뭐 사갈까 | **0/3** | `['집들이 선물']` |
| 부모님 환갑 선물 | 2/3 | `['환갑 선물 아이템']` / `[]` |
| 자취 시작할 때 필요한거 | 1~3/3 | `['자취 시작 키트']` |
| 돌잔치 답례품 뭐가 좋을까 | **0/3** | `['돌잔치 답례품']` |
| 캠핑 처음 가는데 뭐 사야해 | **0/3** | `['캠핑 용품']` |
| 이사 갈 때 필요한 것들 | 1/3 | `['이사 준비 물건 목록']` |

프롬프트 개선 2종을 시도했고 **둘 다 실패**했다:

1. **규칙 강화** — 추상 분류("목적·상황형") 대신 판정 기준("가게에서 집어올 수 있는 물건인가") +
   금지 규칙(목적 표현을 query 로 쓰지 말 것) + "예시에 없어도 2개 이상 전개" → **18회 중 3회**만
   전개. 예시에서 뺀 발화는 오히려 퇴행
2. **예시 확대** — 유형별 7줄로 확대 → `집들이` 0/3→2/3 개선이나 `자취` **3/3→1/3 퇴행**.
   프롬프트가 길어져 기존 성공 케이스의 주의가 희석. 예시 없는 발화는 여전히 0~1/3

**원인**: `fast` tier(`gpt-5-nano` + `reasoning_effort=minimal`) 한 호출에 intent·filters·cart·
attributes 가 함께 얹혀 있어 "무엇을 살지 떠올리기"라는 **생성·추론 작업 여력이 없다.** 작업의
성격을 잘못 배치한 것이다.

> **단, "프롬프트로는 아무것도 못 한다"는 아니다** — §4.1 에서 `case` 정의(설명이 **아예 없던** 필드)를
> 채우자 전개율이 함께 올랐다(`집들이 선물` 0/3 → 3/3). 즉 실패한 것은 **이미 규칙이 빽빽한 절에
> 지시를 더 얹는 방식**이고, **비어 있던 곳을 채우는 것**은 효과가 있었다. 그럼에도 `부모님 환갑
> 선물` 이 `case=[3,3,3]`(전개 필요를 정확히 인지)인데 `legs=[1,1,1]`(전개 실패)로 남으므로,
> **프롬프트만으로 신뢰성을 확보할 수는 없다**는 결론은 유효하다 — 전용 호출이 필요하다.

## 3. 아키텍처 결정 — 방식 A(전용 LLM 전개) + 주입형 seam

**전개를 `decompose` 에서 분리해 조건부 전용 호출로 만든다.** 감지는 코드가(결정적), 생성은 LLM 이
(단일 작업) 담당한다.

```
decompose (지금 그대로 — 프롬프트도 현행 유지)
   ↓
[코드] 기존 매핑(DESIGN-59 §4.3~§4.5)을 먼저 태운다          ← #217 로 순서 변경
   ↓
[코드] 전개 필요 감지(§4) — 매핑 실패를 본다, 프롬프트 운에 맡기지 않는다
   ↓ (해당될 때만)
[LLM 1회] 전개 전용 프롬프트(§5) — "이 목적에 살 만한 구체 상품 N개"
   ↓
그 상품명들을 leg query 로 넣고 같은 매핑에 태운 뒤 **원 결과에 합집합**(§6)
```

> **#217 이전**에는 감지가 매핑보다 **앞**이었고(marker 열거), 전개 결과가 원 legs 를 **교체**했다.
> 감지의 성격은 그대로다 — **코드가 결정적으로 판정하고 LLM 에게 묻지 않는다**(§4.1).

### 3.1 대안 비교 — B(카탈로그 기반)·C(사전/캐시)

| | A. LLM 전개 | B. 카탈로그 기반 | C. 사전/캐시 |
|---|---|---|---|
| 기제 | 발화 → LLM → 상품명 | 발화 임베딩 → **상품** 최근접 → 그 카테고리 | 목적 표현 → 저장된 상품 목록 |
| LLM 호출 | +1(조건부) | 0 | 0 |
| 결정성 | 낮음 | 높음 | 높음 |
| 세상 지식 | **있음** | 없음 | 사람이 넣은 만큼 |
| 재고 근거 | 없음 | **있음** | 없음 |
| 새 표현 | 가능 | 가능(품질 미지) | 불가 |

**B 기각 — 단, 조건부 재검토.** 이유 셋:
1. **실측 불가** — `products` 테이블이 0행이다(임베딩 미시드). I-17 배치가 Spring 가동을 전제해
   지금 측정할 수 없다.
2. **100개 표본으로는 판정 불가** — `scripts/load_sample_100.py` 로 100개를 적재할 수 있으나,
   나올 수 있는 카테고리가 최대 100종(사전은 2056종)이라 음성이든 양성이든 근거가 되지 않는다.
3. **구조적 한계 — 규모 확장으로 해결되지 않는다.** `"집들이 선물"` 이라는 문구는 어떤 상품
   설명에도 없다. 상품이 10만 개가 돼도 `"선물세트"` 가 들어간 상품으로 쏠릴 뿐이며, 이는
   `categories` 2056개에서 이미 관측한 현상과 같은 구조다(`집들이 선물` → `출산/돌기념품 >
   출산선물/기념품` 0.2904). **`목적 → 상품` 도약은 카탈로그 텍스트에 없는 지식이다.**

> **B 재검토 조건(체크 가능):** (1) `products` 임베딩이 실 규모로 시드됨 **그리고** (2) I-17
> enrichment 의 `extras.tags` 에 **용도·상황 태그**(예 `"집들이 선물"`·`"선물포장"`)가 포함됨.
> (2)가 충족되면 B 의 약점이 데이터 쪽에서 메워져 A 를 대체할 수 있다. 그때까지 B 는 **A 의 보조**
> 용도(A 가 낸 상품명이 실제 재고에 있는지 검증, 판매량 반영)로만 후보로 남긴다.

**C 는 A 의 대안이 아니라 위에 얹는 층.** 첫 요청은 A 로 전개하고 결과를 캐시해, 같은 목적 표현이
다시 오면 캐시 히트로 즉시·무료·결정적으로 응답한다 — A 의 지연·비결정성이 두 번째 요청부터
사라진다. **본 문서 범위는 A 까지**이고 C 는 후속(§12).

### 3.2 주입형 seam — 나중에 갈아끼울 수 있게

전개 단계는 **주입형 콜러블**로 둔다. 저장소 공통 패턴이며(`embed`·`search_top_k`·`exact_lookup`·
`select_category` 전부 주입형), 이 덕에 #115 에서 `select_category` 를 조건부 배선하는 것이 한 줄
변경이었다. 같은 방식으로 A→B 교체나 C 추가가 **주입 한 줄**이 된다.

```python
async def expand_needs(utterance, *, llm, settings, expand: ExpandFn = _llm_expand) -> list[str]: ...
# A: 기본값(_llm_expand)   B: expand=_catalog_expand   C: expand=_cached(_llm_expand)
```

## 4. 감지 — 언제 전개하나 (코드, 결정적) · **#217 로 개정**

`decompose` 산출을 **미리 맞히지 않는다.** 매핑을 **해보고 실패했을 때** 전개한다.
**LLM 에게 "전개했니?"를 묻지 않는다.**

```
초판(#198):  감지(marker 열거) → 전개 → 매핑
개정(#217):  매핑 → 실패 → 전개 → 재매핑 → 원 결과에 합집합
```

- **D1 신호 없음** — 신호 leg(`raw_category or query`, §4.3)이 하나도 없다 → 전개.
  구조적 판정이라 매핑 결과와 무관하다 — **legs 가 비면 매핑할 것이 없어 실패 신호가 나오지
  않으므로** 이 규칙만은 매핑보다 앞에 남는다.
- **D2 매핑 실패** — `map_categories` 가 canonical 을 못 낸 leg 이 하나라도 있다 → 전개.
  판정은 **#115 §4.5 의 거리·마진**이 이미 하고 있어 새 판정식을 만들지 않는다.

| 실패 경로 | 이벤트 | 트리거 | 이유 |
|---|---|:-:|---|
| ① 거리컷 드롭 | `category_distance_rejected` | O | 맞는 칸이 taxonomy 에 없다 |
| ② 택일 null | `category_select_null` | O | 후보 top-k 중 맞는 것 없음 = 같은 의미 |
| ③ 조회 예외 | `category_leg_search_failed`·`category_embed_failed` | **X** | 인프라 장애 |
| ④ 히트 0건 | `category_unmapped` | **X** | `categories` 미시드 — 전개해도 같은 빈 DB 를 다시 본다 |

③ 을 섞으면 pg 순간 장애가 LLM 전개를 부른다. PR #188 이 `error_type` 으로 "인프라 장애 vs 코드
버그"를 가른 것과 같은 원칙 — **원인이 내용이 아닌 실패는 내용 기반 처방을 부르면 안 된다.**

### 4.0 초판의 marker 열거를 폐기한 이유 (#217)

초판 D2(`utterance_copy`)·D3(`purpose_marker`)는 leg query 가 **목적 marker 로 endswith 하는지**로
판정했다(`["선물","답례품","준비물","용품","아이템","키트","물품","추천","것","거"]`). 열거라서 목록에
없는 표현은 통과한다 — `재료` 류가 대표 사례이고 §15.3 이 기록한 미검출(`아이디어`·`제품`·`필수품`)도
같은 원인이다.

```
"김밥 재료"    → 채소 > 파/마늘/양념채소     0.3027  마진 0.0054  → 드롭 → 무필터
"감자탕 재료"  → 냉장/냉동식품 > 국/탕/찌개  0.3177  마진 0.0213  → 드롭 → 무필터
```

**`재료` 를 marker 에 추가하는 처방은 실측으로 기각됐다** — `재료` 로 끝나는 표현 6건 중 4건이 이미
정답 매핑이라 넣으면 오탐 4 / 회수 2 로 손해가 크다(이슈 #217 본문). `세트`·`모음`·`구성품` 을 하나씩
추가해도 같은 함정이 반복된다. **marker 를 완전히 삭제해도 손실이 거의 없다**는 것이 §4.5 ⑤ 의
결론이다.

### 4.1 `case` — 프롬프트에 정의를 넣어 신뢰 가능하게 만들되, 감지는 코드가 한다

`REQ-REC-002` 는 `decompose` 가 `case`(1 상품명 / 2 구조화 필터 / 3 상황)를 파생하도록 요구한다.
`case == 3` 이면 전개가 필요하다는 뜻이므로 자연스러운 감지 신호처럼 보인다. 실측 결과는 **두
단계**로 나뉜다.

**(1) 정의 없이는 노이즈였다.** 종전 프롬프트는 JSON 스키마에 `"case": 1 | 2 | 3` 만 있고 **1/2/3 이
무슨 뜻인지 어디에도 설명이 없었다**(규칙 절 0줄). LLM 이 뜻을 모른 채 숫자를 채우고 있었다.

**(2) 정의를 넣자 신뢰 가능해졌다.** 발화 8종 × 3회 (`fast` tier):

| 발화 | 기대 | 정의 전 | 정의 후 |
|---|---|---|---|
| 청바지 | 1 | `[1, 3, 1]` ❌ | `[1, 1, 1]` ✅ |
| 무선 이어폰 추천해줘 | 1 | `[2, 1, 2]` | `[2, 2, 3]` ⚠️ 잔여 |
| 5만원 이하 아무거나 | 2 | `[1, 2, 2]` | `[2, 2, 2]` ✅ |
| **집들이 선물로 뭐 사갈까** | 3 | `[1, 1, 1]` ❌ | `[3, 3, 3]` ✅ |
| 부모님 환갑 선물 | 3 | `[3, 1, 3]` | `[3, 3, 3]` ✅ |
| 자취 시작할 때 필요한거 | 3 | `[3, 1, 1]` | `[3, 3, 3]` ✅ |
| 돌잔치 답례품 뭐가 좋을까 | 3 | `[3, 1, 2]` | `[3, 3, 3]` ✅ |
| 발이 너무 시려워서 해결하고 싶어 | 3 | `[3, 3, 1]` | `[3, 3, 3]` ✅ |

**Case 3 판정이 5발화 × 3회 = 15/15 정확·전부 일관**이 됐다.

**부수효과 — 전개율까지 개선됐다.** `categoryQueries` 절은 손대지 않았는데도:

```
집들이 선물:   legs 0/3(발화 복사)  →  [3, 3, 3]  (구체 상품 3개)
돌잔치 답례품:  legs 0/3            →  [1, 3, 3]
발이 시려워:   legs 0/3            →  [2, 0, 0]
```

정의에 넣은 **"'선물'·'준비물'·'필요한 것' 같은 말은 물건 이름이 아니므로 1이 아니라 3"** 이라는
문장이 `categoryQueries` 산출에도 작용했다 — LLM 이 "집들이 선물은 물건이 아니다"를 알게 되니 그것을
상품명으로 쓰지 않게 됐다.

> **§2 의 프롬프트 실패와 왜 반대 결과인가**: §2 는 이미 규칙 10줄이 붙은 `categoryQueries` 절에
> 지시를 **더** 넣어 희석이 일어났다(`자취` 3/3→1/3). 이번은 **설명이 아예 없던 필드에 정의를 준**
> 것이다 — 정보량 0→1 과 10→13 의 차이다. 프롬프트는 "길게 쓰면 나아진다"가 아니라 **"비어 있는
> 곳을 채우면 나아진다"** 는 교훈.

**그럼에도 감지는 코드(§4)가 한다.** 이유 둘:

1. **잔여 오탐** — `"무선 이어폰 추천해줘"` 가 1회 `case=3` 으로 나왔다. `case == 3` 만으로 감지하면
   그 회차에 불필요한 전개 호출이 붙는다. §4 의 규칙은 결과를 직접 보므로 이 오탐이 없다 —
   `'무선 이어폰'` 은 `음향가전 > 블루투스 이어폰` 0.1955 로 **매핑에 성공**하므로 트리거되지 않는다
   (#217 이후. 초판에서는 marker 미해당이 근거였다).
2. **선언과 결과는 여전히 어긋난다** — `"부모님 환갑 선물"` 은 `case=[3,3,3]` 인데 `legs=[1,1,1]` 로
   3/3 전개 실패다. 즉 `case` 는 "전개가 **필요하다**"는 선언이고 우리가 감지할 것은 "전개가 **안
   됐다**"는 사실이다. 후자는 결과를 봐야 알 수 있다.

**결정**:
- **`case` 정의를 프롬프트에 넣는다**(본 브랜치 포함) — 그 자체로 전개율 개선이고, 정본
  `REQ-REC-002` 를 형식이 아니라 실질로 만족시킨다. 회귀 방지 테스트를 함께 둔다.
- **전개 트리거는 D1 + 매핑 실패**(§4) — 결정적이고 오탐이 없다. `case` 를 트리거로 쓰지 않는다.
  (#217 개정 전에는 D1~D3 였다.)
- **단, `case` 는 게이트로 쓴다** — `case != 3` 이면 어떤 규칙도 발동하지 않는다(§4.2, PR #203 리뷰
  반영). 트리거와 게이트는 요구되는 신뢰도가 다르다 — 게이트는 case 1/2 **배제**에만 쓰인다.
- **`case` 는 관측 로그(§10)에도 남긴다** — 하류 Case 3 분기(#168 `groups`·#163 `budget`)의 근거로
  축적한다.

### 4.2 `case == 3` 게이트 — D1 이 case 2 를 삼키는 것을 막는다 (PR #203 리뷰)

D1(`no_legs`)은 **두 가지 서로 다른 상황을 구분하지 못한다**:

```
"5만원 이하 아무거나"   case 2 — 의도적으로 카테고리 무관   → categoryQueries = []
"부모님 환갑 선물"      case 3 — 전개 실패                → categoryQueries = []
```

**처방이 정반대다** — case 2 는 좁히면 **안 되고**(무필터 전체 검색, #22 가 테스트로 고정·#162 가
개선할 경로), case 3 은 좁혀야 한다. leg 유무만 보면 둘이 같아 보인다.

이대로 두면 전개 프롬프트가 `"하나뿐이면 다시 생각해 최소 2개를 채우세요"` 로 **항상 ≥2개를
만들도록** 강제하므로, 목적이 전혀 없는 입력에도 그럴듯한 상품명을 지어낸다. 그것이 legs 를 교체하면
`filters.category` 가 채워져 **"카테고리 무관·가격만 필터"라는 사용자 의도가 파괴**된다. §4 의 "미검출은
종전 동작이라 손해가 없다"는 전개 호출이 **실패**할 때만 성립하는 안전장치이고, "애초에 전개하면 안
되는 상황인데 호출이 성공하는" 경우는 보호하지 못한다.

**해결 — `case != 3` 이면 어떤 규칙도 발동하지 않는다(전 규칙 게이트).**

> **§4.1 과 모순이 아니다** — 거기서 기각한 것은 `case` 를 **트리거**로 쓰는 것이다(`case == 3` 이면
> 전개하라). 트리거는 "전개가 **안 됐다**"는 사실을 맞혀야 하는데 `case` 는 "전개가 **필요하다**"는
> 선언이라 부적합했다. 반면 **게이트**(`case != 3` 이면 전개하지 마라)는 case 1/2 를 **배제**하는 데만
> 쓰이고, 그 판정은 실측이 뒷받침한다 — `"5만원 이하 아무거나"` 3/3 `case=2`, `"청바지"` 3/3 `case=1`.
> 요구되는 신뢰도가 다르다.

**왜 D1 만이 아니라 전 규칙인가** (자체 점검에서 정정): 초안은 "D2·D3 는 목적 marker 가 이미
판별하니 게이트 불필요"였는데, **case 2 발화의 leg 이 marker 로 끝나는 경로가 남는다** —
`"평점 높은 거 보여줘"` → `['평점 높은 거']` 는 `'거'` 로 끝나 D3 가 발동하고, `"인기 많은 거
추천해줘"` 도 같다. D1 만 막으면 리뷰가 지적한 회귀가 닫히지 않는다.

> **#217 이후에도 이 논거는 유효하고, 오히려 강해졌다.** 매핑 실패가 트리거이므로 marker 대신
> **거리·마진**이 case 2 leg 을 걸어들인다 — `'평점 높은 거'` 는 `게임 > PC게임` 0.3420 / 마진 0.0171
> 로 **매핑 실패** 판정이다. 게이트가 없으면 무필터 의도가 지어낸 상품 목록으로 좁혀진다.
> case 2 leg 은 taxonomy 에 맞는 칸이 없는 것이 정상이라, 매핑 실패는 case 2 에서 **구조적으로**
> 발생한다.

`case` 잔여 오탐(`"무선 이어폰 추천해줘"` 1회 `case=3`)을 근거로 게이트 확대를 주저했으나, 그 오탐은
**과다 보고**(1이어야 하는데 3)라 게이트를 **통과**시킨다 — 게이트가 막는 방향과 무관하다. 그리고
목적형 실측은 5발화 × 3회 = **15/15 `case=3`** 이라 게이트로 잃는 것이 없다.

**결정 근거는 실패 방향의 비대칭성이다**:

```
게이트가 과하게 막으면:  목적 표현 leg 이 남음 → 하류 거리컷이 드롭 → 무필터 검색   (안전)
게이트가 없어서 새면:    지어낸 카테고리로 검색이 좁혀짐                          (유해)
```

- **트레이드오프**: LLM 이 `case` 필드를 아예 빼면 파싱 기본값 `2` 로 떨어져(`decompose.py`)
  목적형인데도 전개가 막힐 수 있다. 안전한 방향의 실패(= 종전 동작)이고 `case` 는 정의 추가 후
  15/15 로 안정적이라 수용한다.
- **관측**: 게이트에 막힌 턴은 `needs_expansion_triggered` 가 남지 않는다. 대신 `decompose_case`
  로그(`case`·`legs`·`leg_queries`, §10)로 "case≠3 인데 leg 이 목적 표현" 조합을 사후 집계할 수
  있어 게이트 과잉을 감지할 수 있다.

### 4.3 신호 판정에 `raw_category` 포함 (PR #203 리뷰)

"신호 있는 leg" 판정은 저장소 규약대로 **`raw_category or query`** 로 본다 —
`decompose._parse_category_queries`(`q.raw_category or q.query`)·graph 멀티턴 승계 판정
(`not any(q.raw_category or q.query ...)`)과 동일하다.

스키마상 `category` 는 채우고 `query=null` 인 leg 이 나올 수 있는데(각각 독립 `string|null`), 그건
**이미 올바른 카테고리 신호**다. `query` 만 보면 D1 이 오탐해 정상 분류된 leg 을 지어낸 상품 목록으로
통째로 교체한다(`"무선 이어폰 추천해줘"` → `[{category:"음향가전", query:null}]` 이 그 예).

> **#217 개정** — 초판에서는 이 절이 D2·D3 의 텍스트 판정 대상(`query` 만)을 함께 규정했으나, 두
> 규칙이 삭제되면서 그 부분은 무의미해졌다. 남는 것은 **D1 의 신호 판정**이고 규약은 그대로다.
> raw 만 있는 leg 은 이제 **매핑에 태워진다** — `raw` 앵커로 조회돼 canonical 을 내거나(성공) 실패
> 판정을 받는다(DESIGN-59 §4.3 query 우선·raw 폴백). 즉 초판이 "판정 대상이 아니라 보수적으로
> 전개를 막는다"고 했던 leg 이, 이제는 **결과로 판정된다** — 열거를 결과 판정으로 바꾼 이 개정의
> 취지와 같은 방향이다.

> **OPEN-5** `"무선 이어폰 추천해줘"` 가 `case=2`(기대 1)로 나오는 Case 1/2 혼동은 남아 있다. 전개
> 감지에 영향이 없어 이번 범위에서는 다루지 않는다 — 하류 분기가 Case 1/2 를 구분해 쓰기 시작할 때
> 정의를 다듬는다.

> **OPEN-1 — #217 로 해소.** D3 marker 목록 튜닝은 목록 자체가 삭제되어 소멸했다(§4.0).

### 4.4 배선 전제 — 합집합이라 트리거가 안전해졌다

개정 전에는 전개가 legs 를 **교체**했으므로 오탐 1건이 정상 leg 을 통째로 파괴했다. 그래서 감지가
"재현율보다 정밀도"여야 했다. **§6 이 합집합으로 바뀌면서 그 제약이 사라진다** — 전개가 빗나가도
원 leg 이 남는다. 그럼에도 트리거를 매핑 실패로 좁게 두는 이유는 §4.5 ③ 이다: 전개된 짧은 단어가
**가짜 근접으로 오분류**되어 검색을 오염시키므로, 전개는 필요할 때만 한다.

`선물`·`준비물`·`키트` 류는 **카탈로그에 해당 칸이 없어 매핑도 실패**하므로 marker 를 지워도 그대로
잡힌다. marker 가 추가로 잡는 것은 결국 **이미 정확히 매핑되는 것을 더 쪼개는 것**이라 설정값·판정
갈래·관측 차원을 두 벌 유지할 근거로는 약하다.

특히 `용품` 은 **역효과 marker** 다 — 카테고리명에 `용품` 이 흔해(`캠핑용품`·`수예용품`·`훈련용품`)
`용품` 으로 끝나면 오히려 매핑이 잘 된다(실측 6건 중 5건 성공). 목적 표현을 잡으라고 넣은 marker 가
매핑 잘 되는 것만 골라내고 있었다.

> **포기하는 것**: `돌잔치 답례품`·`캠핑 용품` 은 카테고리 1개로 유지된다(현행과 동일). 관측
> 로그(§10)에 실패 사유·거리·마진이 쌓이므로, 운영 후 "답례품·용품류도 펼쳐야 한다"는 판단이 서면
> 근거를 갖고 되살린다. 지금 실측은 그 필요를 보여주지 않는다(OPEN-7).

## 5. 전개 호출

- **입력**: 발화 원문(+ 감지 사유). 프로필·멀티턴 맥락은 넘기지 않는다(단일 작업 유지).
- **출력**: 구체 상품명 문자열 배열. `{"items": ["디퓨저", "식기 세트", ...]}`
- **프롬프트 원칙**(단일 작업이라 짧게 유지):
  - "가게에서 그 이름으로 **집어올 수 있는 물건**"만
  - 목적 표현(`선물`·`준비물`·`아이템`·`용품`)을 그대로 되풀이 금지
  - 가격·평가 수식어 금지(§DESIGN-59 §6.0 과 동일 규약 — 거리컷 통과를 위해)
  - 개수는 `2` 이상 `category_fanout_max` 이하
- **tier**: 기본 `fast`. **단일 작업이면 `fast` 로도 되는지 실측 후 확정**하고, 미달이면 `smart`
  또는 effort 상향으로 승격한다(§9 config). ⚠️ §2 의 실패는 "fast tier 라서"가 아니라 "한 호출에
  6가지 작업이 얹혀서"였으므로, 전용 호출의 `fast` 성능은 별개 측정 대상이다.
- **상한·타임아웃**: 턴당 1회. `spring_timeout_s`(3s) 와 같은 급의 상한을 두고 초과 시 §7 degrade.

## 6. 결과 배선 — **#217 로 교체 → 합집합**

- 전개된 상품명 각각을 `CategoryQuery(raw_category=None, query=<상품명>)` 로 만들어 **재매핑**하고,
  그 결과를 원 매핑 결과에 **더한다**.

```
category_legs = dedup_truncate(원 매핑 legs + 전개 매핑 legs, category_fanout_max)
```

- **순서는 원 leg 먼저** — `fanout_max` 절단 시 사용자가 명시한 카테고리가 살아남는다.
- `legs[0]`(조건 칩·멀티턴 승계의 대표 카테고리, DESIGN-59 §7)이 **안정적으로 유지된다.** 종전 교체
  배선은 대표 카테고리가 전개 상품으로 바뀌었다.
- dedup 은 canonical 기준이라 같은 칸으로 수렴한 전개 leg 은 자동 병합된다.
- `raw_category=None` 인 이유: DESIGN-59 §4.3.1 이 **query 우선**이라 raw 는 폴백일 뿐이고, LLM
  창작 라벨은 표기 불일치·가짜 근접으로 해가 더 크다(anchor=raw 채택 12건 중 11건 오분류).
- 개수 상한은 `category_fanout_max`(5) **재사용** — 새 튜너블을 만들지 않는다. 매핑·검색 단계가
  이미 그 상한으로 절단하므로 별도 값을 두면 두 상한이 어긋난다.
- 이후 경로는 **완전히 기존 그대로**다(DESIGN-59 §4.3 앵커 → §4 거리컷 → §4.4 택일 → §6 fan-out).

**교체를 폐기한 이유** — 부분 실패 시 사용자가 명시한 카테고리를 잃었다:

```
"이사 가는데 냉장고랑 필요한 것들"   legs = ["냉장고", "이사 필요한 것들"]
  냉장고         → 냉장고 > 일반 냉장고  0.09  성공
  이사 필요한 것들 → (멀다)              0.31  실패 → 전개 대상
  전개 ["행거","수납 박스","커튼"] → 각각 매핑

  종전(교체):   [행거, 수납박스, 커튼]           ← 사용자가 명시한 냉장고 유실
  개정(합집합): [냉장고, 행거, 수납박스, 커튼]     ← 보존
```

합집합은 §4.5 ③ 의 전개 오염(`구기자`→스포츠)에 대한 방어이기도 하다 — 전개가 빗나가도 원 leg 이
남으므로 **최악이 "쓸데없는 leg 몇 개 추가"** 로 제한된다.

### 6.1 흐름과 재전개 금지

```
decompose
  ↓  (승계 가드 else 안쪽 — 리파인 턴은 여기 오지 않는다)
map_categories(원 legs)  →  legs + unresolved
  ↓  case == 3 이고 (신호 leg 없음 OR unresolved 있음)
expand_needs(발화)  →  상품명 목록
  ↓  (실패하면 빈 리스트 → 아래 스킵, 원 결과 유지)
map_categories(전개 legs)  →  legs2
  ↓
dedup_truncate(legs + legs2, category_fanout_max)
```

- **전개는 턴당 1회.** 재매핑이 또 실패해도 재전개하지 않는다(무한 루프 방지).
- D1 경로는 첫 매핑에 앵커가 없어 임베딩·pg 왕복이 발생하지 않는다(낭비 없음).

**매핑이 턴에 2회 불리므로, 늘어난 호출이 어떤 예산도 배수로 만들지 않는지 리소스별로 따진다**
(PR 리뷰 — 처음에는 pg 커넥션만 따지고 LLM 예산을 놓쳤다):

| 리소스 | 배수가 되나 | 근거 |
|---|:-:|---|
| pg 커넥션 | X | 두 호출이 **순차**라 동시 앵커 수는 그대로 — `pool >= 2 × fanout_max` 전제 유지 |
| **택일 LLM 호출** | **막았다** | `category_select_max_calls` 는 **턴당** 상한인데 매핑 내부에서는 호출 단위로 적용된다. 그대로 두면 2배(기본 2→4)로 깨지므로 **호출부가 남은 예산을 넘긴다**(아래) |
| 임베딩·pg 왕복 | O(의도) | 1회 추가는 이 설계가 감수하는 비용이다(§8) |
| 전개 LLM 호출 | X | 턴당 1회 상한 |

```python
# graph — 첫 매핑이 쓴 몫을 빼고 넘긴다. 0 이면 매퍼가 택일을 건너뛰고 임베딩 top-1 을 쓴다.
expanded = await _map_or_empty(
    ..., select_max_calls=max(0, settings.category_select_max_calls - mapping.select_calls)
)
```

`CategoryMapping.select_calls` 는 **시도 수**다 — 실패한 택일도 비용이 발생하므로(관측 기록도 호출
**전**에 한다) 결과를 보고 세면 실패분이 예산에서 빠져 두 번째 매핑이 상한을 넘겨 쓴다.

> **매핑을 부르는 새 경로를 만들 때 이 배선을 빠뜨리면 상한이 조용히 배수로 깨진다.** 회귀 고정:
> `test_fanout.py::test_select_budget_is_shared_across_both_mapping_calls`,
> `test_category_mapping.py::test_select_max_calls_override_caps_select`·
> `test_select_calls_reports_attempted_budget`.

### 6.2 `map_categories` 반환형

실패 사실을 상류에 노출해야 한다. 종전 반환 `list[tuple[str, str|None]]` 로는 "드롭됨"과 "신호 없음"이
구분되지 않는다.

```python
@dataclass
class CategoryMapping:
    legs: list[tuple[str, str | None]]   # 종전 반환값
    unresolved: list[str]                # §4 ①② 로 canonical 을 못 낸 leg 의 앵커 텍스트
    select_calls: int = 0                # 이 호출이 **시도한** §4.4 택일 수 (턴당 예산 공유용, §6.1)
```

`unresolved` 가 텍스트를 담는 이유는 **관측**이다 — 전개 자체는 발화 원문으로 하므로(§5) 값이 트리거
판정에 쓰이지는 않지만, 어떤 leg 이 왜 실패했는지가 로그에 남아야 임계를 재튜닝할 수 있다(§10).

`select_calls` 는 **호출부가 두 번째 매핑에 남은 예산을 넘기기 위한 것**이다(§6.1) — `map_categories`
안에는 턴 단위 카운터가 없어서, 상한을 턴당으로 지키려면 소비량이 밖으로 나와야 한다.

## 7. 실패 degrade — 후퇴 없음 보장

전개 호출이 실패하면 **`decompose` 원래 산출을 그대로 쓴다**(= 현행 동작). 전개는 **개선 시도**이며
실패가 기존 경로를 악화시켜서는 안 된다.

| 상황 | 처리 |
|---|---|
| LLM 오류·타임아웃·JSON 파싱 실패 | **원 매핑 결과** 유지 + `needs_expansion_failed` |
| 결과가 `2개 미만` | 전개 실패로 간주, 원 매핑 결과 유지(1개면 발화 복사로 되돌아간다) |
| `llm` 미구성 | 감지도 하지 않는다(호출 자체 스킵) + `needs_expansion_skipped` |
| 전개는 성공, **재매핑이 전부 실패** | 원 매핑 결과 유지(합집합에 더할 것이 없을 뿐) |
| 원 leg 도 전개 leg 도 전부 거리컷에 걸림 | 기존 canonical-or-null → 무필터 + `semanticQuery`(DESIGN-59 §4) |
| 첫 매핑 **호출 자체가 예외** | `category_map_failed` → 빈 legs·빈 `unresolved` → **전개도 하지 않는다**(§7.1) |

### 7.1 매핑 호출이 예외로 죽으면 전개도 꺼진다 (#217 PR 리뷰)

`_map_or_empty` 가 매퍼 **호출 자체의 예외**를 `CategoryMapping()`(legs·`unresolved` 모두 빈 값)으로
흡수하므로, `case == 3` 이어도 D1(신호는 있으니 해당 없음)·D2(`unresolved` 비어 해당 없음) 어디에도
걸리지 않아 전개가 발동하지 않는다. #217 로 **전개 가용성이 매핑 호출 성공에 종속되면서** 생긴
성질이라 명시한다.

여기서 말하는 예외는 **§5 의 leg 단위 실패와 다른 층**이다:

```
1층 (함수 안에서 격리)  임베딩 타임아웃·pg 경합·히트 0건 · 택일 단계 오류 · **조립 루프 오류**
                       → map_categories 가 정상 반환하되 실패분만 드롭. 다른 leg 은 살아남는다.
2층 (호출 자체가 깨짐)  시그니처 불일치·설정 접근 오류
                       → 함수가 아무 결과도 못 내고 예외 전파. 여기가 §7.1 의 대상.
```

> **조립 루프도 1층으로 내렸다**(PR 리뷰) — 종전에는 `result`/`unresolved` 조립 루프가 어떤 try 에도
> 감싸이지 않아 거기서 버그가 나면 **이미 DB 검증된 exact 매치와 채택 canonical 까지** 버려졌다.
> PR #188 이 택일 단계를 감쌀 때 든 논거와 같은 노출이다. 덤으로 `select_calls` 회계가 살아남아
> §6.1 의 턴당 예산이 **결합에 기대지 않고** 지켜진다 — 종전에는 "같은 예외가 `unresolved` 도 비워
> 두 번째 매핑이 안 일어나므로 안전"이라는 우연한 결합이 유일한 방어였고, 전개 트리거를 다른
> 신호로 바꾸는 순간 깨질 자리였다. 회귀 고정:
> `test_category_mapping.py::test_assembly_failure_keeps_confirmed_legs`.

**결과적 손실은 없다.** 전개가 낸 상품명도 결국 **같은 매퍼**를 타야 canonical 이 되는데 그 매퍼가
죽어 있다. 종전 배선(전개 먼저 → 매핑 1회)에서도 매핑 예외는 `category_legs = []` 로 떨어져 최종
상태가 **무필터로 동일**했고, 차이는 종전이 어차피 버려질 LLM 전개 호출을 한 번 더 썼다는 것뿐이다 —
이 변경은 실패 모드에서 **비용만 줄인다**.

2층 예외는 성격상 **입력과 무관**하다(인자 이름이 안 맞으면 어떤 leg 으로 불러도 죽는다). 따라서
"원 leg 에서는 죽고 전개 leg 에서는 살아나는" 경우는 사실상 성립하지 않는다 — 그런 경우에만 종전
배선이 유리했을 것이다.

회귀 고정: `test_fanout.py::test_mapper_exception_skips_expansion_and_degrades_to_unfiltered`.
종전 매퍼 예외 테스트는 전부 `case=2` 라 §4.2 게이트에 먼저 막혀 이 조합을 검증하지 못했다.

즉 **최악의 경우가 "지금과 동일"** 이다. **#217 이후로는 이 보장이 더 강해졌다** — 합집합이라
전개가 어떻게 실패하든 **원 leg 을 잃는 경로가 구조적으로 없다**(종전 교체 배선은 전개 호출이
"성공"하되 내용이 엉뚱할 때 원 leg 을 잃었다).

## 8. 지연 예산 (중요 제약) · **#217 로 정정**

전개는 추천 그래프가 **첫 SSE 프레임을 내기 전에** 끝나므로, 추가 호출이 **그 턴의 모든 이벤트를
그만큼 늦춘다.**

```
decompose → _prepare_recommendation(매핑·감지·전개·재매핑)   ← 여기가 늦어진다
          → conditions            (첫 SSE 프레임, recommendation/graph.py)
          → search → rerank
          → token                 (첫 텍스트 — rerank 뒤다)
          → push → products.ready → done
```

> **초판 서술 정정(#217)** — 초판 §8 은 *"`token` 스트림은 별개 경로라 영향 없음 … 첫 토큰은 안 늦고
> 상품 카드가 늦는다"* 라고 적었으나 **추천 턴에서는 성립하지 않는다.** 추천 턴의 `token` 은 근거
> 문구이고 **rerank 뒤**에 나온다 — 전개보다 한참 하류다. "`token` 이 별개 경로"인 것은 응답을 바로
> 흘리는 general intent 얘기인데, 전개는 recommend intent 에서만 돌므로 그 위안이 적용되지 않는다.
> #217 이 매핑 왕복을 하나 더 붙이는 지점이 정확히 이 앞이라 서술을 바로잡는다.

- **정상 경로(매핑 성공)는 추가 지연 0** — 매핑 횟수가 종전과 같은 1회다. 전개가 발동한 턴에만
  `임베딩·pg 왕복 1회 + LLM 1회`가 더해진다(#217 §6.1).
- 즉 비용은 **목적형 발화에 국한**되지만, 그 턴에서는 **첫 프레임부터** 늦는다. `conditions` 는
  조건 칩이라 사용자가 "반응이 시작됐다"고 느끼는 지점이므로, 체감 지연으로 잡을 때 이 값을 본다.
- `llm_call_limit` 은 `2` → **조건부 3** 으로 재해석한다. 정본은 이미 이 문을 열어뒀다 — 결정 14-E
  가 "정확히 2회"를 **config 상한**(기본 2, Case 3 묶음 병렬 시 예 최대 4)으로 완화했다.
- C(캐시, §12)가 붙으면 두 번째 요청부터 LLM 지연이 사라진다(임베딩·pg 왕복은 남는다).
- **측정 지점**: `#141` 트레이싱의 `server_first_event_ms`(SSE 첫 프레임)가 이 지연을 직접 담는다.

## 10. 관측(로그/메트릭)

- `needs_expansion_triggered` — `reason`(`no_legs`/**`mapping_failed`**), 원 leg 수.
  `mapping_failed` 에는 `unresolved`(canonical 을 못 낸 앵커 텍스트)를 함께 싣는다 —
  하류 `category_distance_rejected`·`category_select_null`(DESIGN-59 §11)의 `distance`·`margin` 과
  조인하면 임계 재튜닝 표본이 된다
- **`needs_expansion_union`**(#217 신규) — 원 leg 수 · 전개 leg 수 · dedup·절단 후 최종 수.
  절단(`category_fanout_max`)으로 전개분이 잘린 빈도를 본다
- `needs_expanded` — `items`(전개된 상품명), 개수, 소요 ms
- `needs_expansion_failed` — `reason`, 원 매핑 결과 유지했음
- `needs_expansion_skipped` — `reason`(`disabled`/`llm_unavailable`)
- **`case`(§4.1·§4.2)** — 매 recommend 턴의 `decompose` 산출 `case` 를 남긴다. **트리거로는 쓰지
  않지만**(감지는 §4) **게이트로는 쓴다**(`case != 3` 이면 전개 안 함) — 로그가 게이트 판정의
  유일한 사후 검증 수단이다. 하류 Case 3 기능(#168 `groups`·#163 `budget`)이 참조할 근거도 된다.
  `case==3` 인데 전개 실패한 턴의 빈도가 이 이슈의 핵심 지표다.

> **#217 소멸**: `utterance_copy`·`purpose_marker` reason 값 — 집계 쿼리·대시보드에 이 값을 쓰는
> 곳이 있으면 함께 갱신해야 한다.
- **모델 호출 기록**(PR #203 리뷰) — 전개 LLM 호출은 `observer.record_model_call(resolve_model_id(
  settings, needs_expansion_tier))` 로 `chat_request`(api-spec §6.3)의 `model`·토큰 합산에 싣는다.
  정본 `SPEC-RECOMMEND-001` AC-REC-37·§비기능이 **`2 + 1` 호출**이라고 명시하므로, 빠지면 그 주장을
  운영 로그로 검증할 수 없고 OPEN-2(tier 실측)의 근거도 사라진다. 기록 위치는 호출부가 아니라
  **`_llm_expand` 안** — `expand` 는 주입형 seam 이라(§3.2) 호출부에 두면 LLM 을 쓰지 않는 방식 B·C
  전개기에도 유령 모델 호출이 남는다(`llm is None` 가드와 동일한 원칙). `decompose`·rerank 와 같이
  **호출 전** 기록한다(실패한 호출도 비용이 발생한다).

`reason` 분포로 (a) **거리·마진 임계 재튜닝**(#217 이후 — 종전 "D3 marker 튜닝"을 대체), (b) `tier`
승격 판단, (c) C 캐시 도입 시점(같은 목적 표현 반복 빈도)을 데이터로 정한다. 하류 관측
(`category_distance_rejected` 등, DESIGN-59 §11)과 조합하면 "매핑 실패 → 전개 → 재매핑 채택"
전환율을 볼 수 있다.

### 15.1 라이브 실측 (실 LLM decompose+전개 ×3회, 발화 7종)

**전개된 회차는 전부 정확했다** — 이 이슈의 목표 달성:

```
"캠핑 처음 가는데 뭐 사야해" → 텐트·랜턴·매트        → 캠핑 > 텐트 / 캠핑랜턴
"집들이 선물로 뭐 사갈까"    → 와인잔 세트·디퓨저·커피 드리퍼·티 세트
                             → 주방용품 > 잔/컵 / 인테리어소품 > 디퓨저 / 주방용품 > 커피용품
"부모님 환갑 선물"          → 안마의자·안마기·안마볼   → 안마용품 > 대형 안마의자
"돌잔치 답례품 뭐가 좋을까"  → 다기세트·타월 세트·향초  → 주방용품 > 식기/홈세트 / 욕실용품 > 수건/타월
```

**대조군 오탐 0** — `"청바지"` 3/3 미전개, `"무선 이어폰 추천해줘"` 3/3 미전개.

### 15.2 프롬프트 예시 과적합 (발견·수정)

첫 측정에서 전개 결과가 발화와 무관하게 `['디퓨저','식기 세트','홍삼','전자레인지','방한 부츠']` 로
고정돼 나왔다(집들이 선물에 방한 부츠). 프롬프트의 "좋음" 예시 목록을 LLM 이 **그대로 베낀** 것이다.
§2 의 F5 실패와 같은 부류이며, 상품 목록 예시를 **다른 발화("이사 갈 때 필요한 것들")의 완결 예시
하나**로 바꿔 변환 방법만 가르치고 "예시 상품을 그대로 쓰지 말 것"을 명시해 해소했다.

> **교훈**: 전개처럼 **출력이 자유 목록**인 작업에서 "좋은 예시 나열"은 그대로 복사된다. 예시는
> **다른 입력의 완결 사례**로 주어 "변환 방법"만 보이고, 목록 자체는 못 베끼게 해야 한다.

### 15.3 알려진 한계 — 전개율 7/21 (초판) · **#217 로 해소**

> **이 절은 초판(marker 열거) 시점의 기록이다.** 여기 적힌 미검출 사례가 곧 #217 의 출발점이고,
> 매핑 실패 트리거로 회수된다(§4.5 ②: `집들이 선물 아이디어` 0.3156/0.0133 → 전개). 절 끝의
> "leg 용 marker 와 발화용 marker 를 분리" 제안은 **채택되지 않았다** — 열거를 더 정교하게 만드는
> 방향 자체를 폐기했다.

감지가 놓치는 회차가 남는다. `D3` 의 "모든 leg" 조건 + marker 목록 부족이 원인:

```
['집들이 선물 아이디어', '주방 선물 추천', '데코 아이템 선물']   → '아이디어' 가 marker 아님 → 미전개
['발 보습 제품', '발 관리 용품', '보온 양말']                 → '제품'·'양말' 이 marker 아님 → 미전개
['캠핑 초보자 물품', '초보자cam핑 필수 아이템', '캠핑 전자기기 필수품'] → '필수품' 이 marker 아님
```

marker 를 계속 늘리는 것(`아이디어`·`제품`·`필수품`·`세트`…)은 끝이 없다. 실측에서 보이는 **더 강한
신호**는 leg 들이 **발화 조각을 공통 접두로 반복**하는 것이다:

```
['집들이 선물 추천', '집들이 선물 주방 용품', '집들이 선물 간식 세트', ...]   ← 전부 "집들이 선물" 접두
```

다만 그대로 규칙화하면 `"청바지"` → `['청바지 데님']` 도 같은 패턴이라 **오탐**한다. 차이는 **발화
자체가 목적 표현인지**이므로, 발화 쪽 marker 검사(`in`)와 조합해야 한다 — 그런데 `'추천'` 을 발화
marker 로 쓰면 `"무선 이어폰 추천해줘"` 가 걸린다. **leg 용 marker 와 발화용 marker 를 분리**해야 할
가능성이 있어 추가 실측이 필요하다(OPEN-1).

**미전개는 후퇴가 아니다** — 종전과 동일 경로이며, 그때 나오는 엉뚱한 카테고리(`취미 > 수집용품`·
`공구 > 소형기계`)는 **#115(PR #188)의 거리컷·택일이 걸러낸다**. 두 작업이 합쳐진 뒤 재측정해야
전개율·품질을 정확히 판단할 수 있다.

  `priority`(1 필수/2 권장/3 선택, 결정 14-H)는 #168·#60·#163 소관.

### 15.5 #217 라이브 재검증 — #115 회귀 6건 (2026-08-02)

`DESIGN-CATEGORY-HYBRID-59` §4.0.1 이 "회귀 타깃 6/6 재현 안 됨"을 기록한 그 6건을, #217 로 바뀐

배선 순서가 뒤집혔으니 실측으로 확인했다.

**부수 — 새 배선이 실 트래픽 경로에서 작동함이 로그로 확인됐다:**


  잡히지 않는 구간이라 ② 를 포함한 판단이 실측으로 뒷받침됐다.
- **D1(`no_legs`)이 여전히 필요**하다 — 12회 중 2회가 이 경로였다(legs 가 비어 매핑할 것이 없다).
- **§4.5 마진 예외가 그대로 작동**한다 — `홍삼`·`주전자/티포트` 를 거리컷에서 살렸다.

> **실행 환경 주의**: Windows 에서 스크립트를 직접 돌리면 상단에 `Psycopg cannot use the
> 'ProactorEventLoop'` 경고가 뜬다(pg-profile 비동기 풀). 카테고리 매핑은 pg-catalog 를 동기 경로
> (`asyncio.to_thread`)로 쓰므로 위 결과에 영향이 없다. 서버는 uvicorn 루프에서 돈다.
