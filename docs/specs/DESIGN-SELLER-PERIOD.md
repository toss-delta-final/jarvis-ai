## 1. 문제 — #269 P1 이 유실된 경위

#269 는 P0(침묵 폴백 제거)·P1(어휘 확장 + 확인 흐름)·P2(비교 기간 + 레인 통일)로 범위가
나뉘어 있었는데, 이를 닫은 PR #284 는 P0 만 구현한 채 이슈가 닫혔다(2026-08-04). 그 결과
`이번 달`·`올해`·`최근 3개월` 같은 일상 어휘가 전부 되묻기로 떨어지는 상태가 남았다.

### 1.1 차단 지점은 세 겹이다

이슈 #345 본문은 "차단 지점이 calc 이 아니라 planner"라고 진단했는데, 실측하면 게이트가 셋이다.

| # | 지점 | 내용 |
|---|---|---|
| ① | `prompts.py` PLANNER_PROMPT `[기간 — period_expr]` | 정규 어휘 4종만 허용, 그 외는 clarification 으로 되물으라고 지시 |
| ② | `schemas.py` `AnalysisPlan.period_expr` Field description | **같은 4종이 또 박혀 있다.** 구조화 출력이라 LLM 이 이 설명도 읽는다 |
| ③ | `calc.normalize_period` | `_NON_DAY_UNIT_PATTERN` 분기가 `최근 3개월` 을 명시 거절 |

②를 빼고 ①만 고치면 프롬프트와 스키마 설명이 서로 반대를 지시해 planner 산출이
비결정적이 된다. **①②는 같은 커밋에서 함께 고친다**(이슈 본문의 「관련 파일」에는 ②가 빠져 있었다).

## 2. 어휘표 (정본)

`today` 는 요청 시점 서버 날짜, `어제` = `today - 1일`.

### 2.1 확인 없이 통과 (기존 — 회귀 금지)

| 표현 | 환산 |
|---|---|
| `지난달` / `지난 달` | 전월 1일 ~ 전월 말일 (연 경계 롤오버) |
| `어제` | 어제 ~ 어제 |
| `최근` (정확히 두 글자) | (today − `seller_recent_days_default`) ~ 어제 |
| `최근 N일` | (today − N) ~ 어제 |
| `YYYY-MM-DD~YYYY-MM-DD` | 그대로 |

`최근`(단독)은 코드가 기본 일수를 보충하는 케이스라 원칙상 확인 대상이지만 **예외로 둔다** —
"최근 매출 어때?" 는 가장 흔한 발화이고, 매 턴 확인을 요구하면 대화가 두 배로 길어진다.
기본 일수는 §3 확인 문구가 아니라 보고서 본문의 분석 기간 표기로 판매자에게 노출된다.

### 2.2 확인 후 통과 (신규 — 이 이슈)

| 표현 | 환산 | 비고 |
|---|---|---|
| `이번 달` / `이번달` / `금월` | 당월 1일 ~ 어제 | 오늘 제외(R1) |
| `올해` / `금년` | 1월 1일 ~ 어제 | |
| `상반기` / `하반기` | 1/1~6/30 · 7/1~12/31 | 미래는 절단(R2) |
| `N분기` / `N/4분기` (N=1~4) | 해당 분기 시작 ~ 종료 | 미래는 절단(R2) |
| `최근 N주` / `최근 N주일` | (today − 7N) ~ 어제 | |
| `최근 N개월` | (today − N달, 달력 기준) ~ 어제 | §2.4 |
| `M월 D일~M월 D일` (연도 없음) | 연도 추론(R5) 후 그 범위 | |

`올해`·`상반기`·`N분기` 처럼 연도가 생략된 표현은 **올해**로 읽는다(R5 는 적용하지 않는다 — §2.3).

### 2.3 여전히 되묻기

경계가 합의되지 않았거나 코드가 값을 지어내야 하는 표현:

`작년 여름` · `최근 반년` · `최근 한 달` · `최근 며칠` · `최근에` · `최근 -3일` ·
`최근 0일` · `이번 달 들어 최근 7일`(지원·미지원 혼합) · 상한 초과 · 완전 미래(R3).

`최근 한 달` 을 `최근 1개월` 로 흡수하지 않는 이유: 한글 수사(`한`·`두`·`세`)를 열면
`두어 달`·`서너 주` 까지 경계가 흐려진다. 숫자 표기만 받고, 판매자에게는 되묻기 문구가
`최근 1개월` 이라는 표현법을 알려준다.

### 2.4 `최근 N개월` 은 달력 기준이다

`N×30일` 이 아니라 **같은 일자에서 N달 뺀 날**이다(`2026-08-06` 에서 3개월 = `2026-05-06`).
30일 근사는 판매자가 월 단위로 생각하는 것과 어긋나고, 월별 비교를 하면 경계가 미끄러진다.
빼는 달에 그 일자가 없으면(3/31 → 2월) 그 달의 **말일**로 맞춘다.

## 3. 경계 규칙

| 규칙 | 적용 대상 | 내용 | 근거 |
|---|---|---|---|
| **R1 오늘 제외** | 상대 어휘 전부 | `date_to` 상한은 어제 | 당일 집계 미완결(SPEC-SELLER-001 §10-④) |
| **R2 미래 절단** | §2.2 확인 어휘만 | `date_to` 가 어제보다 뒤면 어제로 자른다 | `올해`·`이번 달` 은 정의상 끝이 미래다 |
| **R3 완전 미래 거절** | §2.2 확인 어휘만 | `date_from` 이 어제보다 뒤면 되묻기 | 오늘이 8월일 때 `4분기` — 자를 구간 자체가 없다 |
| **R4 상한** | 전부 | `(to − from) + 1 > seller_period_max_days` 면 되묻기 | 기존 P0 규칙 승계 |
| **R5 연도 추론** | 연도 없는 날짜만 | 올해로 읽고, 그 결과가 R3 이면 작년으로 재시도 | `6월 1일~6월 30일` 은 통상 지나간 날을 가리킨다 |

R2·R3 을 **명시 범위(`YYYY-MM-DD~YYYY-MM-DD`)에 적용하지 않는 이유**: 판매자가 날짜를
직접 지정한 값이라 코드가 말없이 자르면 안 된다. 미래 범위를 물으면 빈 결과가 나오고
그게 정확한 답이다 — 기존 P0 동작을 그대로 둔다는 뜻이기도 하다(회귀 방지).
§2.1 의 나머지 어휘(`지난달`·`어제`·`최근 N일`)는 정의상 이미 어제 이하라 R2 가 걸릴
일이 없다 — R1 이 환산 단계에서 지켜진다.

R2 와 R3 의 경계도 짚어 둔다: 8월의 `하반기`(7~12월)는 7월이 이미 지났으므로 **절단**
대상이고(R2), `4분기`(10~12월)는 시작조차 오지 않아 **거절**이다(R3). 이 경계를 잘못
잡으면 "하반기 매출" 같은 정상 질문이 통째로 막힌다.

R5 를 `N분기`·`상반기`·`올해` 에 적용하지 않는 이유: 이 표현들은 어휘 자체가 "올해의"를
뜻한다. 8월에 `4분기` 라고 말한 판매자에게 작년 4분기를 조용히 보여주는 것은 어휘 확장이
아니라 **다른 질문에 답하는 것**이다 — 되묻는 편이 맞다.

R2 로 잘렸다는 사실은 §4 확인 문구에 반드시 드러난다. 자르고 말하지 않으면 P0 가 없앤
"조용한 대체"가 형태만 바꿔 돌아온다.

## 4. 확인 문구 — 소유권은 코드 한 곳

### 4.1 문제였던 것 (#345 §3)

되묻기 문구 생성 지점이 **두 곳**이었다.

- `pipeline.resolve_plan` 첫 줄 `raise ValueError(plan.clarification)` ← planner LLM 이 쓴 자유 문장
- `calc.normalize_period` 의 `ValueError` ← 코드 원문

둘 다 `orchestrator` 에서 `PipelineResult(kind="clarification", text=str(exc))` 로 합류하고,
그 뒤 `api/seller.py` 는 `mask_output`(마스킹만, 재작성 아님)을 거쳐 그대로 token 으로 흘린다.
**하류 LLM 재작성 경로는 없다** — 코드 경로 추적으로 확인했다. 그런데 dev 실측 문구
("'최근 0일'은 조회할 수 없는 기간입니다…")가 `calc.py` 원문("기간 일수는 1일 이상이어야
합니다…")과 달랐다. 남는 설명은 하나뿐이다: **planner 가 선수를 쳐서 자기 clarification 을
썼다.** `최근 0일` 은 정규 어휘 형태(`최근 N일`)라 프롬프트상 통과시켜야 했지만 LLM 이
"0일은 말이 안 된다"로 일반화한 것이다.

그러므로 P0 가 보장했다고 믿은 "예외 메시지 = 사용자 문구"는 **planner 가 통과시켰을
때만** 성립하는 조건부였고, 그 조건이 어디에도 적혀 있지 않았다.

> **주의 — 이 결론은 dev 재현으로 확정하지 않았다(2026-08-06).** 코드 경로 추적으로
> 후보를 하나로 좁힌 상태다. 다만 §4.2 의 해결은 "어느 쪽이 썼는지" 에 의존하지 않는다 —
> 생성 지점을 하나로 만들어 버리므로, 이 추정이 틀렸더라도 결과는 같다. dev 접근이
> 가능해지면 `plan.clarification` 을 1회 로깅해 확인하고 이 주석을 지운다.

### 4.2 해결 — 측정이 아니라 구조로 닫는다

어느 쪽이 문구를 썼는지 실측해서 맞춰가는 대신, **기간 문구의 생성 지점을 하나로 만든다.**

- planner 는 **기간을 이유로 clarification 을 쓰지 않는다.** 이해하기 어려운 기간
  표현이어도 원문을 그대로 `period_expr` 에 옮겨적는다. (프롬프트 ①·스키마 description ② 양쪽에 명시)
- `clarification` 은 **"어떤 분석을 원하는지 모를 때"** 에만 쓴다.
- 기간 관련 사용자 대면 문구(되묻기·확인)는 전부 `period.py` 가 만든다.

부수 효과가 하나 더 있다 — 어휘를 확장해도 planner 가 계속 `이번 달` 을 clarification 으로
끊으면 `period.py` 는 **한 번도 호출되지 않는다.** ①②를 고치는 것이 이 이슈에서
부수 작업이 아니라 주 작업인 이유다.

### 4.3 확인 문구 형식

```
'이번 달' 을 2026-08-01 ~ 2026-08-05 기간으로 보고 분석하겠습니다.
(오늘은 집계가 끝나지 않아 제외합니다.)
이대로 진행할까요? 맞으면 "응" 이라고 답해 주시고,
다른 기간이면 원하시는 기간을 말씀해 주세요.
```

환산 결과(`date_from`~`date_to`)를 **날짜로** 보여준다 — 어휘를 되풀이하면 판매자는
코드가 무엇으로 해석했는지 알 수 없다. R2 로 잘렸으면 그 사실을 괄호 줄에 덧붙인다.

## 5. 확인 흐름

### 5.1 상태기계 — 3경로

이슈 원안은 4경로(승인·수정·새 질문·TTL)였으나 **수정은 새 질문으로 흡수한다**.

| 경로 | 판정 | 동작 |
|---|---|---|
| **승인** | `period.parse_period_approval(message)` → True | 저장된 `ResolvedPlan` 으로 즉시 실행. **planner 재호출 0회** |
| **새 질문** | 승인이 아닌 모든 발화 | pending 폐기 후 일반 라우팅(②③)으로 흘림 |
| **TTL 만료** | `created_at + seller_period_confirm_ttl_minutes < now` | pending 폐기, 발화는 신규 질문으로 처리 |

`아니 7월로` 같은 수정 발화가 별도 구현 없이 동작하는 이유: 확인 문구가 이미
`record_turn` 으로 대화 스레드에 기록돼 있어(`api/seller.py` `_analysis_stream`)
planner 가 그 맥락을 읽고 새 계획을 세운다. 수정 전용 기간 파서를 따로 두면
**어휘 정의가 두 곳으로 갈라진다** — `period.py` 하나만 어휘를 안다는 원칙을 지킨다.

### 5.2 승인 신호 — 쓰기와 읽기의 경계 [중요]

이 저장소는 **"발화 ≠ 동의" [HARD]**(`app/schemas/seller.py`)를 지켜, HITL 상품 쓰기 승인을
자유 텍스트가 아니라 최상위 `action:"confirm"` 구조화 필드로만 받는다(FE 계약 A-2, 2026-07-22).
기간 확인은 이 원칙의 **명시적 예외**다.

| | 쓰기(HITL draft) | 읽기(기간 확인) |
|---|---|---|
| 승인 신호 | 최상위 `action`/`draftId` 구조화 필드 | 자유 텍스트 + 코드 선판정 |
| 근거 | 실행하면 상품·주문이 바뀌고 되돌릴 수 없다 | 상태를 바꾸지 않는다. 오해석돼도 조회 결과가 하나 더 나올 뿐이고 판매자가 즉시 정정할 수 있다 |
| 와이어 | 계약 필드 존재 | **계약 변경 없음** — api-spec 개정 불필요, FE 무작업 |

**이 예외를 쓰기 쪽으로 확장하지 않는다.** 새로운 확인 흐름을 만들 때 "기간 확인도
자유 텍스트인데" 를 근거로 쓰면 안 된다 — 갈림길은 "자유 텍스트냐"가 아니라
**"승인이 되돌릴 수 없는 부작용을 일으키는가"** 다.

### 5.3 승인 판정 — 전 토큰 긍정 어휘

정규식 한 덩어리 대신, 공백으로 나눈 **모든 토큰이 긍정 어휘 집합에 속할 때만** 승인이다.

- `응` · `네 맞아` · `ㅇㅇ 좋아` · `응 그래 해줘` → 승인
- `네 7월로 해줘` → `7월로` 가 집합 밖 → **새 질문** (수정 경로가 이렇게 동작한다)
- `응 아니야` → `아니야` 가 집합 밖 → 새 질문

정규식 누적보다 오탐이 예측 가능하고, 부정어가 섞이면 자동으로 승인에서 빠진다.
판정은 pending 이 있을 때만 수행되므로 `어`·`네` 같은 짧은 토큰의 위험도 그 턴으로 한정된다.

### 5.4 저장

`seller-period:{seller_id}:{threadId}` 네임스페이스의 공용 checkpoint(pg-profile).
`thread.py` 의 recorder 그래프 패턴을 따른다(no-op 1노드 + `aget_state`/`aupdate_state`).

- **키가 threadId 인 이유**: 승인 발화에는 식별자가 실리지 않는다(§5.2 — 와이어 무변경).
  후속 요청에서 복원할 수 있는 키는 `(seller_id, threadId)` 뿐이다. `seller_id` 접두가
  곧 IDOR 차단이다(`thread.py` 와 동일 규약 — 신원은 검증된 JWT 에서만 온다).
- 스레드당 pending 은 최대 1건 — 새 확인은 이전 것을 덮어쓴다.
- **저장 실패는 degrade**: 확인 문구는 그대로 나가고, 후속 `"응"` 은 pending 이 없어
  새 질문으로 처리된다(planner 가 대화 맥락으로 재계획). 응답을 죽이지 않는다 —
  대화 스레드·분석 이력의 degrade 원칙과 같다.

### 5.5 입구 판정 순서

`api/seller.py` `_seller_stream` 에 **①.7** 로 들어간다.

```
⓪ 신원 캐스팅
① confirm 필드 선판정 (HITL 쓰기 승인)
①.5 "N번 적용해줘" 선판정
①.7 기간 확인 pending 선판정   ← 신규
②  scope 선차단
③  supervisor 라우팅
```

②(scope)보다 **앞**이어야 한다 — `"응"` 은 판매 도메인 어휘가 아니라 scope 필터에
걸릴 수 있다. ①·①.5 보다 뒤인 이유는 그 둘이 더 명시적인 신호(구조화 필드·정형 발화)라
기간 확인이 그것들을 가로채면 안 되기 때문이다.

## 6. 실행 재개 — planner 재호출 0회

`run_analysis_pipeline` 의 planner 이후 구간을 `_run_resolved(question, resolved, ...)` 로
분리하고, 신규 진입과 승인 재개가 **같은 함수**를 부른다.

```
신규:  question → planner → resolve_plan → [확인 필요?] → _run_resolved
승인:  저장된 ResolvedPlan                              → _run_resolved
```

승인 경로에 planner 호출이 없다는 것이 조건문이 아니라 **호출 그래프**로 보장된다.
테스트는 planner 빌더 호출 횟수를 세어 0 을 단언한다(#269 완료 조건).

`PipelineResult.kind` 에 `period_confirmation` 을 추가한다. 패널 조치는 `keep` —
확인 질문은 대화이지 보고서가 아니다(`kind=="report"` 만 `replace`, 기존 규칙 그대로).

## 7. general 레인 통일 (#346 — 해소)

**#345 시점의 상태(불일치).** `prompts.py` `GENERAL_PROMPT_TEMPLATE` 이 **`이번 달` =
당월 1일 ~ 오늘**이라는 general 레인 전용 정의를 산문으로 갖고 있었다(2026-07-18 확정 —
당시 분석 레인은 이 어휘를 되물었으므로 충돌이 없었다). #345 가 분석 레인에서 `이번 달` 을
**당월 1일 ~ 어제**(R1)로 지원하기 시작하면서 같은 질문이 레인에 따라 하루 다른 기간을
쓰게 됐고, 더 나쁘게는 general 레인의 환산이 `period.py` 를 타지 않아 상한(R4)·0/음수·
자릿수 가드가 **전부 비켜갔다**.

**#346 이 닫은 방식.** 환산을 프롬프트에서 코드로 옮겼다. 어려운 지점은 하나다 —
분석 레인은 planner 가 기간 표현을 옮겨적어 주지만 **general 레인에는 planner 가 없다.**
이 레인에 planner 를 붙이면 가장 싼 레인에 LLM 왕복이 하나 늘어나므로, 어휘표가
폐집합이라는 점을 이용해 **코드로 훑는다**(`period.find_period_mentions`, LLM 0회).

```
발화 → find_period_mentions → resolve_period → format_general_input → general_agent
        (표현 추출)             (환산·판정·문구)   ([조회 기간] 주입)
```

| 상황 | 동작 |
|---|---|
| 어휘표 안의 표현 1개 | 환산해 `[조회 기간] from=… to=…` 로 주입 |
| 기간 표현 없음 | `최근`(기본 일수) — planner 의 `[기간]` 절과 **같은 규약** |
| 어휘표 밖(`오늘`·`이번 주`·`7월`) | 되묻기. LLM·도구 호출 **전에** 끝난다 |
| 표현 2개 이상(`이번 달 들어 최근 7일`) | 되묻기 — 코드가 하나를 고르면 그게 조용한 대체다 |

### 7.1 미지원 어휘를 **일부러 잡는** 이유

스캐너가 `오늘`·`이번 주`·`작년`·`7월` 같은 미지원 표현까지 잡는 것은 실수가 아니다.
안 잡으면 "기간 언급 없음"으로 읽혀 기본 7일이 적용되고, 판매자는 자기가 물은 기간과
다른 답을 받고도 알 방법이 없다 — **#269 가 분석 레인에서 없앤 침묵 대체가 general
레인에서 형태만 바꿔 되살아난다.** 잡아서 `resolve_period` 로 넘겨야 되묻기 문구가 나간다.

스캐너 패턴은 §2 어휘표의 **두 번째 사본**이다(`resolve_period` 의 패턴은 문자열 전체
매칭 `^…$` 이라 문장 속에서 못 쓴다). 사본이 갈라지면 "분석 레인은 아는데 general 은 못
잡는" 어휘가 생기므로, 어휘표 전 항목을 두 경로에 통과시키는 대조 테스트로 묶어 둔다
(`tests/unit/test_seller_period_lane_parity.py`).

### 7.2 확인이 아니라 **고지** — 레인 간 의도된 비대칭

`needs_confirmation` 인 해석(`이번 달`·`최근 3개월`)을 general 레인은 확인 없이 실행하고
`period.disclosure_text` 로 **무엇으로 봤는지 먼저 밝힌다.** 오해석 비용이 비대칭이기
때문이다 — 분석 레인은 잘못 해석한 기간으로 워커 팬아웃·검증 루프·추천까지 돌지만,
general 은 조회 한두 번이고 판매자가 곧바로 정정하면 그만이다. 확인 상태기계(§5)를
레인마다 두는 대신 해석을 밝혀 "조용한 대체"를 막는다.

정합의 기준은 **`(from, to)` 와 되묻기 문구**이지 확인 왕복의 유무가 아니다 —
전자는 대조 테스트가 문구까지 동일성을 단언하고, 후자는 여기 적은 대로 다르다.

### 7.3 백스톱 — 도구 인자 재검증

두 레인 모두 기간을 코드가 환산해 주지만, 그 값을 실제 도구 인자로 옮기는 것은 LLM 이다.
주어진 from/to 를 무시하고 날짜를 지어내면 R4 상한이 다시 비켜가므로, 기간을 받는 조회
도구 9종에 `tools._guard_period_args` 를 걸어 형식·역전·상한을 호출 경계에서 한 번 더
막는다. 되묻기가 아니라 `"Error:"` 인 이유는 이 시점이 이미 스트림 안이라 되묻기로
되돌아갈 수 없고, 도구 실패 문자열은 프롬프트의 degrade 규약이 이미 다루는 어휘여서다.
