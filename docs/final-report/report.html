Executive Summary

요약

Jarvis는 검색어를 입력하고 결과를 고르는 기존 쇼핑 흐름을, 사용자의 상황과 조건을 이해하고 후속 행동까지 수행하는 대화형 흐름으로 확장한 AI 에이전트 서버다. 구매자 Agent는 추천·장바구니·찜·주문 조회를, 판매자 Agent는 통계 조회·분석·상품 변경 draft를 담당한다. 개인화 파이프라인은 대화와 구매 이력에서 장기적으로 유효한 취향만 선별해 다음 추천에 활용한다.

1. 프로젝트 개요

검색 결과를 나열하는 서버가 아니라, 사용자의 의도를 이해하고 안전하게 행동까지 이어 주는 AI 조율 계층을 구축했다.

1.1 프로젝트 소개

Jarvis는 자연어 대화로 상품을 찾고, 조건을 좁히고, 개인 취향에 맞게 순서를 조정한 뒤, 장바구니·찜·주문 조회 같은 후속 행동까지 연결하는 에이전틱 커머스 AI다. 일반적인 상품 검색이 “검정 파우치”처럼 짧은 키워드에 최적화되어 있다면 Jarvis는 “유럽 여행에서 기내에 들고 갈 파우치와 어댑터를 총 8만 원 아래로 추천해 줘” 같은 상황·복수 니즈·예산이 섞인 요청을 다룬다.

시스템의 목표는 LLM을 쇼핑 데이터의 새로운 권위자로 만드는 것이 아니다. LLM은 문장의 의미와 선호 신호를 해석하고, 최신 가격·재고·주문 상태와 실제 변경 권한은 기존 커머스 시스템이 유지한다. 이 원칙은 추천 품질뿐 아니라 보안, 장애 격리, 팀 간 협업을 동시에 만족시키기 위한 출발점이다.

1.2 추진 배경과 목적

기존 경험

  • 상황을 여러 키워드로 다시 번역해야 한다.
  • 이전 조건을 검색할 때마다 반복한다.
  • 추천 이유와 실제 상품 데이터가 분리될 수 있다.
  • 추천 뒤 행동을 화면에서 다시 수행한다.

Jarvis의 목표

  • 상황을 조건·니즈·semantic query로 구조화한다.
  • 멀티턴 상태와 장기 프로필을 분리한다.
  • 후보·제약·근거를 코드로 재검증한다.
  • 대화를 실제 커머스 Tool 호출로 연결한다.

2. 문제 정의 및 요구사항

자연어의 유연함을 살리면서도 상품·권한·수치의 경계는 결정론적으로 지켜야 한다.

2.1 해결해야 할 다섯 가지 문제

문제실패 예시필요한 대응
상황 중심 탐색“여행 준비물”이 하나의 카테고리로 축소됨복수 니즈 분해와 category fan-out

2.2 기능 요구사항

구매자 기능

  1. 자연어를 카테고리·가격·브랜드·색상·속성과 semantic query로 분해한다.
  2. 정확 조건은 검색·사후필터에서 강제하고 의미 적합성은 rerank한다.
  3. 추천 결과와 화면 상태를 이용해 장바구니·찜 대상과 옵션을 확인한다.
  4. 주문 상태와 일반 질의를 별도 lane으로 안전하게 분리한다.

판매자·프로필 기능

  1. 판매자 범위 안의 통계와 저장된 보고서를 조회한다.
  2. 상품 변경은 바로 실행하지 않고 검토 가능한 draft로 제안한다.
  3. 반복성·현저성·명시성 gate를 통과한 취향만 장기 프로필에 승격한다.
  4. 명시적 session-end와 비활동 종료를 공통 finalizer로 처리한다.

2.3 비기능 요구사항

Security

JWT sub에서만 신원을 도출하고 seller scope와 내부 토큰을 검증한다.

Reliability

LLM·검색·push 실패를 명시적 error 또는 degrade로 전환하고 취소를 전파한다.

Reproducibility

고정 fixture, dataset hash, prompt hash, run manifest로 실험 조건을 보존한다.

Streaming

SSE로 진행 상태와 token을 보내며 thread별 활성 스트림 수명을 제어한다.

Contract

Pydantic camelCase 모델과 API 명세로 FE·AI·BE 와이어 형식을 고정한다.

Observability

lane, provider, latency, success/degrade를 구조화 trace와 artifact에 남긴다.

성공 기준의 분리 “응답이 생성됨”, “규칙 위반이 없음”, “추천 순위가 좋음”, “사용자가 만족함”은 서로 다른 기준이다. 본 프로젝트는 회귀·제약·근거·지연을 각각 측정하며, 실제 사용자 만족도는 향후 검증 과제로 남긴다.

3.2 요청에서 화면까지의 서비스 흐름

① 인증FE가 JWT와 요청을 전송
② 라우팅의도·화면·스레드 상태 해석
③ Tool 호출Spring 조회와 AI 검색 수행

⑤ 스트리밍SSE와 products.ready 전송
⑥ 표시FE가 Spring 최신 카드 조회

FE는 Spring에서 발급받은 토큰으로 AI 서버를 직접 호출한다. AI는 요청 본문의 사용자 ID를 신뢰하지 않고 검증된 sub에서 신원을 도출한다. 추천이 끝나면 AI는 순위 목록을 Spring에 push하고 products.ready를 보낸다. FE는 이 신호를 받아 Spring에서 최신 가격·재고·이미지를 조회한다. 이 “경로 B”는 SSE 페이로드 중복을 줄이고 표시 데이터의 권위를 한곳에 둔다.

데이터 소유 원칙 Spring은 커머스 원본을, AI PostgreSQL은 search document·embedding·profile·checkpoint 같은 AI 산출물을 소유한다.

4. AI Agent 설계

하나의 거대 프롬프트 대신 의도별 서브그래프와 결정론적 검증 계층으로 역할을 나눴다.

4.1 Buyer Agent

Buyer Agent는 현재 발화만 보지 않는다. 검증된 신원 범위의 thread filter, 최근 추천 상태, 화면 상품, pending option, 개인화 요약을 함께 읽은 뒤 의도를 분류한다. 추천 요청은 카테고리 매핑과 복수 니즈 전개를 거쳐 recommendation subgraph로, 실행 요청은 cart·wishlist 전용 경로로 보낸다. 주문 조회는 회원 신원이 확인된 경우에만 수행하고 일반 대화는 fallback으로 격리한다.

LLM과 코드의 분업 LLM은 “무엇을 원하는가”와 “어떤 후보가 의미상 적합한가”를 판단한다. 코드는 가격·평점 경계, 후보 ID, 중복, 근거의 지원 여부, 출력 스키마를 다시 검사한다.

4.3 Seller Agent

판매자 채팅은 조회·분석·변경 요청의 위험도가 다르다는 전제에서 설계했다. 일반 통계와 저장된 보고서는 검색 Tool을 이용해 답하고, 차트 요청은 분석 레인에서 report payload를 만든다. 상품명·설명·옵션 같은 변경 요청은 즉시 원본에 쓰지 않고 검증 가능한 draft를 생성한다. 적용은 자연어 “네”가 아니라 구조화된 action=confirm과 draftId로만 진행한다.

프로필 pipeline은 모든 발화를 저장하지 않는다. 현재 명시 조건이 장기 취향보다 우선하며, session-end 또는 inactivity checkpoint가 발생하면 공통 finalizer가 델타 추출과 consolidation을 수행한다. 이벤트는 멱등 처리되고 idle 이후 같은 session이 다시 활동할 수 있으므로, 비활동은 영구 종료가 아니라 복구 가능한 checkpoint로 취급한다.

4.5 fast/smart LLM tier

라우팅·구조화 추출처럼 빈도가 높고 형식이 명확한 작업은 fast tier, 추천 순위·자연어 설명처럼 의미 판단이 중요한 작업은 smart tier에 배치한다. 호출부는 provider가 아니라 tier를 요청하고, 설정 계층이 OpenAI 또는 Anthropic 모델로 해석한다. 이 추상화는 비용·지연과 품질을 독립적으로 조정하고, 키 부재나 provider 장애를 공통 LLM_UNAVAILABLE 경로로 처리하게 한다.

5. 핵심 기능 구현

추천, 행동 실행, 개인화, 판매자 분석을 각각 검증 가능한 데이터 흐름으로 구현했다.

5.1 대화형 상품 추천

추천은 “LLM에게 상품을 골라 달라”는 단일 호출이 아니다. 먼저 현재 발화와 prior filter를 이용해 구조화 조건을 만든다. 여러 준비물이 섞인 요청은 category leg로 전개하고 Spring에 질의한다. 정확 가격·평점처럼 위반 여부를 계산할 수 있는 조건은 코드가 적용하며, 남은 후보는 의미 적합성과 개인화 신호로 rerank한다. 마지막으로 candidate ID, duplicate, 근거 구조를 검증해 목록을 push한다.

“유럽 여행 준비물 추천해 줘. 파우치와 어댑터를 합쳐 8만 원 아래로.”
복수 니즈파우치 / 어댑터 분리

후보니즈별 검색 후 round-robin 병합
순위적합성·취향·근거 구조화
결과목록 push와 products.ready

Hard constraint

가격, 명시적 평점 하한, 제외 상품처럼 위반을 계산할 수 있는 조건은 검색·사후필터로 강제한다.

Soft preference

스타일, 상황 적합성, 장기 취향은 후보를 제거하기보다 의미 기반 순위 신호로 사용한다.

5.3 개인화

개인화는 현재 요청을 덮는 자동 필터가 아니라 순위를 보조하는 장기 신호다. 대화·구매 이력에서 추출한 후보 fact는 현저성과 명시성 또는 반복성을 만족해야 승격된다. “기억해 줘” 명령은 명시적 hot path로 처리하고, 일반 발화는 session buffer에 모은 뒤 종료 시점에 delta와 profile summary를 갱신한다. 현재 턴의 가격·브랜드·색상 조건은 항상 프로필보다 우선한다.

5.4 판매자 분석과 변경 draft

판매자 기능은 질문에 자연어로 답하는 범위를 넘어 통계 계산과 변경 제안까지 포함한다. 분석 SOP는 기간을 코드로 환산하고, 집계 응답에서 funnel·conversion·고객·상품 세그먼트를 계산하며, 검증 가능한 finding과 action candidate를 만든다. 차트 좌표는 ASCII 텍스트가 아니라 구조화된 report payload로 전송한다. 상품 변경은 draft lifecycle을 거쳐 명시적 confirm 이전에는 적용되지 않는다.

Statistics

매출, 전환, 이탈, 재구매, 고객·상품 세그먼트를 계산한다.

Verification

표본·유의성·hold 조건과 finding의 수치 일관성을 확인한다.

Human Control

변경은 draft로 제안하고 소유권·TTL·멱등성을 통과한 confirm만 실행한다.

5.5 SSE와 degrade

장시간 LLM·검색 요청에서 사용자가 진행 상황을 알 수 있도록 token뿐 아니라 conditions, action, progress, report, products.ready를 전송한다. 클라이언트 취소는 하위 작업으로 전파해 불필요한 토큰 비용을 줄이고, 제한 시간을 넘긴 provider 호출은 lane별 오류로 변환한다. recommendation push가 실패해도 생성된 설명을 무조건 성공으로 표시하지 않고, 화면 카드가 준비되지 않았음을 명시한다.

6.2 Embedding과 pgvector

Spring에서 가져온 상품 변경분은 AI pipeline에서 검색용 search_doc와 부가 속성을 만들고, Google gemini-embedding-001을 이용해 1,536차원 벡터로 변환한다. 벡터는 수동 L2 정규화 후 pgvector 컬럼에 저장하며 모델 ID를 함께 기록해 모델·차원 변경 시 재생성 여부를 판단한다. pgvector는 구조화 필터를 대체하지 않고, Spring 후보를 의미상 가까운 집합으로 압축하거나 카테고리·색상 동의어를 해소하는 보조 계층으로 사용한다.

검색 단계의 역할 구조화 필터는 “조건을 지켰는가”, embedding은 “의미가 가까운가”, rerank는 “현재 상황과 취향에 더 적합한가”를 담당한다.

6.3 데이터 동기화

상품 원본을 AI DB에 완전 복제하지 않는다. AI가 GET /products/changes를 주기적으로 pull해 변경분을 enrichment·embedding한 뒤 AI artifact만 upsert한다. pull 방식은 이벤트 유실 시 다음 주기가 자연스럽게 복구하고 Spring의 push 재시도 책임을 줄인다. 질의 시점 가격·재고는 여전히 Spring 검색을 통해 확인하므로 배치 지연이 표시 데이터의 권위를 바꾸지 않는다.

7.2 Adversarial recommendation dataset

추천 품질은 정상 문장만으로 검증하면 결측·경계·충돌·주입 공격에 취약하다. 이를 막기 위해 210개 family를 기준으로 한 축만 바꾼 450개 minimal-mutation case를 구성했다. category별 20%인 42 family는 failure mode, atomicity, evidence sufficiency, non-triviality 네 기준으로 직접 검토했다.

프로필 편향 가능성과거 선호가 현재 탐색의 다양성을 줄일 수 있음현재 명시 조건 우선, gate와 편집·삭제 경계

8.3 향후 발전 방향

  1. 실사용자 기반 검색 평가 — holdout query와 click·cart·purchase 행동을 연결하되 노출 편향을 교정한다.
  2. 근거 검증 범위 확장 — 현재 숫자·tier 기반 검증에서 호환성·용도·안전 주장까지 entailment 평가를 넓힌다.
  3. 개인화 통제 강화 — 사용자별 기억 조회·수정·삭제와 profile 영향 설명을 제품 경험에 포함한다.
  4. 운영 관측성 고도화 — lane별 TTFT·total·cost·degrade와 Spring 의존 구간을 하나의 trace로 연결한다.
  5. 판매자 온라인 검증 — 실제 브랜드의 계절성·프로모션을 반영한 shadow run으로 trigger와 추천 action을 보정한다.
Jarvis의 핵심은 “LLM이 답한다”가 아니라, “LLM의 해석을 검증 가능한 데이터와 권한 경계 안에서 실제 행동으로 연결한다”는 데 있다.

8.4 결론

본 프로젝트는 자연어 추천, 장바구니 실행, 개인화, 판매자 분석을 하나의 대화형 AI 서버로 연결했다. 그 과정에서 데이터 소유권, 멀티턴 상태, Tool 권한, 추천 근거, 평가 재현성을 독립된 설계 문제로 다뤘다. 결과적으로 확률적인 LLM을 그대로 신뢰하는 대신 코드·계약·평가가 둘러싼 Agent 구조를 구현했다. 향후 실제 사용자와 운영 데이터 기반 검증을 더하면 검색 품질뿐 아니라 설명 가능성과 행동 안전성을 함께 개선하는 커머스 AI 플랫폼으로 발전할 수 있다.
