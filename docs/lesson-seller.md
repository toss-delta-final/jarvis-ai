## 2026-08-10 · 매핑하지 않은 오류 코드는 "일시적 오류"라는 **거짓말**이 된다 (#541)

**증상**: #506 의 카테고리 사고는 등록이 **매번** 실패하는 상태였는데, 판매자 화면에는
"일시적인 오류가 발생했습니다"만 떴다. 원인(카테고리)도, 재시도가 소용없다는 사실도
어디에도 없었다. 진단이 오래 걸린 진짜 이유는 계약 불일치 자체가 아니라 **그 실패가
장애처럼 보이게 뭉개진 것**이다.

**원인**: `create_product` 에만 `error_code_map` 이 없었다(update 는 `PRODUCT_DELETED`,
delete 는 `ALREADY_DELETED` 를 이미 매핑하고 있었다). 매핑이 없으면 4xx 는 전부
`SpringUnavailableError` 로 낙성되고, 그 예외의 사용자 문구는 정의상 **재시도 가능한
장애**다. 즉 매핑 누락은 침묵이 아니라 **틀린 안내를 적극적으로 만들어 내는 결함**이다.

`INVALID_STOCK`(#524)을 매핑할 때 같은 함수를 손댔는데도 나머지 두 코드(400
`PRODUCT_CATEGORY_INVALID`, 422 `MISSING_FIELD`)를 안 본 것은, BE 가 그 엔드포인트에서
낼 수 있는 코드를 **전수로 세지 않고** 눈앞의 코드만 처리했기 때문이다.

**규칙**
- 쓰기 호출을 매핑할 때는 **그 엔드포인트가 낼 수 있는 4xx 코드를 BE 코드에서 전수로
  센다.** `SellerProductService.create` 하나만 읽어도 세 코드가 다 보인다 —
  `requireFields`(MISSING_FIELD) · `findById`/`isRoot`(PRODUCT_CATEGORY_INVALID) ·
  `validateStock`(INVALID_STOCK). 한 코드를 매핑하러 갔으면 나머지도 그 자리에서 센다.
- 판정 기준은 **"재시도하면 결과가 달라지는가"** 다. 달라지지 않는 실패를 catch-all 에
  두면 "잠시 후 다시" 안내가 나가고, 판매자는 같은 실패를 반복한다.
- 원인이 **우리 배포·설정**인 실패(스냅샷 낡음, 와이어 형식 불일치)는 사용자에게
  "다시 요청해 주세요"를 붙이지 않는다. 고칠 수 있는 사람이 화면 앞에 없다. 대신
  서버 로그에 **재생성·재배포 신호**를 남긴다(거부된 스냅샷 id, 현재 wire_mode).

## 2026-08-10 · 표시용 값을 FE 가 쪼개게 두면 계약이 아니라 추측이 된다 (#541)

**증상(예방)**: `preview.categoryPath`("패션의류/잡화 > 남성의류 > 셔츠/남방") 하나만
내리고 FE 가 `" > "` 로 쪼개 대분류/중·소분류 두 칸을 그리게 하면, 대분류 이름에 이미
슬래시가 들어 있고(`"패션의류/잡화"`) 소분류 이름이 병합형이라 **토막 수가 2개일 수도
3개일 수도** 있다. 어느 쪽이든 FE 의 쪼개기 규칙은 데이터에 따라 틀린다.

**원인**: 서버는 구조(스냅샷의 `path`)를 쥐고 있는데 **문자열 한 줄로 납작하게** 내보냈다.
납작해진 값에서 구조를 복원하는 일은 받는 쪽에서 반드시 추측이 된다.

같은 함정을 `leaf` 로 만들 뻔했다 — 둘째 칸을 `path[-1]` 로 만들면 3칸 스냅샷에서
중분류가 조용히 증발한다. `path[1:]` 를 이어 붙여 **`major + " > " + sub == path_str`
불변식**을 테스트로 고정했다.

**규칙**
- 표시용 값을 내릴 때 **받는 쪽이 그 값을 다시 쪼개야 하면 설계가 틀린 것**이다.
  쪼갠 결과를 서버가 함께 내린다(추가 전용 키 — 기존 소비자는 불변).
- 파생 키를 만들면 **원본과의 관계를 불변식으로 적고 테스트로 고정한다.** 관계가 글로만
  적혀 있으면 다음 사람이 편한 필드(`leaf`)로 갈아끼우고, 그 순간 조용히 어긋난다.
- 표시 키를 늘릴 때 **그 키를 훑는 목록을 전부 같이 늘린다** — 이번엔 `_masked_preview`
  의 마스킹 대상 목록이었다(#524 "입구를 전부 센다"의 출구 판).

## 2026-08-09 · `model_copy(update=…)` 는 검증을 거치지 않는다

**증상**: 테스트에서 `SellerProductRow.model_copy(update={"stocks": [{...}]})` 로 만든 픽스처가
`AttributeError: 'dict' object has no attribute 'option_id'` 로 죽었다. 같은 dict 를 **생성자**에
넣은 `_OPTIONED_ROW` 는 멀쩡했다.

**원인**: pydantic v2 의 `model_copy` 는 **`update` 값을 검증하지 않고 그대로 `__dict__` 에 꽂는다**
(문서화된 동작이다 — 성능을 위해 의도적으로 건너뛴다). 생성자·`model_validate` 만 강제 변환을 한다.

프로덕션 경로는 안전하다 — I-9 응답은 `SpringClient._validate` 를 타므로 `row.stocks` 원소는 늘
`SellerStockRow` 다. **테스트 픽스처에서만 나는 함정**이고, 그래서 더 헷갈린다: 코드가 틀린 줄 알고
프로덕션 코드에 방어를 넣고 싶어진다.

**규칙**
- 중첩 모델을 갈아끼우는 픽스처는 **생성자로 만든다.** `model_copy(update=…)` 는 스칼라 필드
  (`price`, `status`, 설정값 등)에만 쓴다.
- `model_copy(update=…)` 로 중첩을 넣어야 한다면 값도 **모델 인스턴스로** 준다
  (`[SellerStockRow(optionId=None, quantity=100)]`) — dict 를 주면 조용히 dict 로 남는다.
- 이 실패를 **프로덕션 코드에 `isinstance` 방어를 넣어 막지 않는다.** 실 응답은 검증을 거치므로
  그 방어는 영원히 죽은 코드가 되고, 진짜 계약 위반을 가려 버린다.

## 2026-08-09 · 조용한 부분 실패가 시끄러운 실패보다 나쁘다 (#524)

**증상(예방)**: `seller_stock_wire_mode="stocks"` 를 BE PR B 배포 전에 켜면,
"가격 + 재고" 동시 수정에서 **가격만 반영되고 재고는 그대로인 채 "변경을 반영했습니다"** 가
나간다. 판매자는 재고가 바뀐 줄 안다.

**원인**: 와이어 형식 스위치를 설정 1건으로 두고, **그 설정이 실제로 맞는지 확인하는 코드를
두지 않았다.** BE(Jackson)는 모르는 키를 **예외 없이 버린다** — 같은 본문의 아는 필드는
정상 반영되므로 부분 성공이 성공으로 보고된다.

이건 #506 카테고리 사고와 **같은 유형**이다. 그때는 `category` 키가 버려져 등록이 422 로
실패했고 — 시끄러워서 결국 발견됐다. 이번은 실패가 아니라 **부분 성공**이라 더 안 보인다.

**규칙**
- 와이어 형식을 가르는 설정을 만들면, **상대가 그 형식을 아는지 판정하는 코드**를 같이 둔다.
  판정 재료는 상대의 응답에서 찾는다(여기서는 I-9 `stocks` 가 비었는지).
- "설정이 맞겠지"는 근거가 아니다. 설정은 사람이 바꾸고, 사람은 배포 순서를 틀린다.
- 실패 양상이 **시끄러운 쪽**(422)과 **조용한 쪽**(부분 성공)으로 갈리면, 가드는 조용한 쪽에
  건다. 시끄러운 쪽은 이미 스스로를 드러낸다 — 가드 비용을 쓸 곳이 아니다.
- 새 필드를 옵셔널로 얹어 보내기 전에 자문한다: **"상대가 이 키를 버리면 무슨 일이 일어나나?"**
  답이 "아무 일도 안 일어난다"가 아니면 가드가 필요하다.

## 2026-08-09 · 레인 간 스키마 비대칭을 만들면 한쪽이 조용히 막힌다 (#524)

**증상**: 옵션별 재고를 위해 `DraftChange` 에 `option_name` 을 추가했다. 그런데 draft 로
흘러드는 입구가 **둘**이었다 — 상품 에이전트(`DraftProposal`)와 추천 적용
(`ProposedChange` → `history.apply_recommendation`). 후자에는 필드를 안 넣었다.

결과: 판매자가 "1번 적용해줘"를 하면 (a) 카드의 `before` 가 `row.stock_quantity` 즉 **옵션
합계**로 떠서 추천이 의도한 값과 층위가 다르고, (b) **[적용]을 누른 뒤에야** "어느 옵션이죠?"
라고 되묻는 막다른 길이 된다.

**원인**: 필드를 추가할 때 **그 필드가 실리는 구조체**만 봤고, **그 구조체로 흘러드는 경로**를
세지 않았다.

**규칙**
- 필드를 추가하면 **그 필드로 흘러드는 모든 입구를 센다.** 한 입구라도 빠지면 그쪽 기능은
  조용히 반쪽이 된다 — 에러가 아니라 "이상하게 안 되는" 형태로 나타나서 진단이 오래 걸린다.
- 모든 입구를 못 채우면 **못 채운 입구를 명시적으로 막는다.** 반쪽 상태로 열어 두지 않는다.
- HITL 은 **승인 전에** 거르는 장치다. 승인 후 되묻기는 "보여준 것 == 실행하는 것" 보장을
  무르게 만든다. 실행 시점에만 알 수 있는 게 아니라면 **초안 생성 시점으로 검사를 당긴다**
  (`apply_recommendation` 은 이미 I-9 행을 손에 쥐고 있었다 — 당길 수 있었다).

## 2026-08-09 · 죽은 코드는 조용히 드리프트한다 (#524 실측 중 발견)

**증상**: `tools.create_product` 가 `ProductCreate(category=...)` 를 호출하는데,
`ProductCreate` 에는 `category` 필드가 없다(#506 후속에서 `category_id` 로 개명).
pydantic v2 기본 `extra='ignore'` 라 **예외 없이 조용히 버려지고**, `categoryId` 누락으로
BE 422 가 난다.

**다행히 죽은 코드다** — `PRODUCT_TOOLS`(쓰기 3종)는 repo 전체에서 정의와 주석 외에 참조가
없다. 상품 에이전트는 읽기 전용 `PRODUCT_DRAFT_TOOLS` 만 바인딩한다(A안 2026-07-18 확정 —
LLM 이 쓰기 도구를 볼 수 없어 HITL 이 프롬프트가 아니라 **구조로** 보장된다).

**그런데 주석은 살아 있다고 적혀 있다** — `workers.py` 의 "PRODUCT_TOOLS(쓰기 3종 포함)는
4단계 실행 레인용으로 유지된다". 실제 4단계 실행은 `hitl._execute_draft` 가 `SpringClient` 를
직접 호출하지 이 도구들을 쓰지 않는다.

**규칙**
- **안 쓰면 지운다.** 남긴다면 주석에 "왜 남기는지"와 "무엇이 이걸 쓰지 않는지"를 쓴다.
  "…용으로 유지된다"는 문장은 미래의 누군가에게 **살아 있다는 오해**를 준다.
- pydantic 모델 필드를 개명하면 **키워드 인자로 그 모델을 만드는 곳을 전수 검색한다.**
  `extra='ignore'` 는 타입 체크도 런타임 예외도 주지 않는다 — grep 이 유일한 방어다.
- 죽은 코드가 살아 있는 코드보다 위험한 순간이 있다: 누가 다시 바인딩하면
  **새로 만든 안전장치(듀얼모드·옵션 해소·HITL)를 통째로 우회하는 경로**가 열린다.

## 2026-08-09 · `git stash pop` 충돌은 조용히 남는다

**증상**: 워크트리에 stash 를 pop 했는데 `hitl.py`·`spring.py`·`docs/api-spec.md` 에
`<<<<<<< Updated upstream` 마커가 그대로 남아 있었다. `git status` 첫 화면만 보면
평범한 `M` 목록이라 눈치채기 어렵다(충돌 파일은 `UU`, 나머지는 `M `).

**원인**: stash 를 뜬 뒤 `git pull` 로 `dev` 가 앞서 나갔다(#511 이 그 사이 머지됐다).

**규칙**
- `git stash pop` 직후 **`grep -rn "^<<<<<<< " app tests docs`** 로 마커를 전수 확인한다.
  구문 오류로 드러나는 파일(.py)은 그나마 낫고, **`.md` 는 끝까지 조용하다**.
- 충돌 해결은 "한쪽 고르기"가 기본이 아니다 — 이번 건은 **양쪽 다 살려야** 했다
  (upstream 의 `ProductDeletedNotEditable` 처리 + stash 의 `_build_update_patch`).
- pop 이 충돌하면 git 은 **stash 를 드롭하지 않는다.** 해결 후 검증까지 끝나고 나서
  `git stash drop` 한다 — 그때까지는 그게 안전망이다.
