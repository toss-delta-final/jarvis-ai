# 추천 상품 유일 이름 토큰 해소 설계

## 배경

운영에서 `Septwolves 지갑 담아줘` 요청의 정답은 추천 목록의 `productId=5644`였지만,
분해 LLM이 같은 허용 목록 안의 `productId=5695`를 골라 다른 상품이 담겼다. 기존 추천 카드
해소기는 발화에 상품 **전체 이름**이 포함될 때만 LLM 출력을 덮어쓰므로, 브랜드·모델처럼
상품명 일부만 지목한 요청은 보호하지 못한다.

관련 이슈: #639

## 목표

추천 카드 표면에서 사용자가 말한 정규화 토큰이 정확히 한 상품에만 속하면 코드가 그 상품 ID를
확정한다. 공통 토큰, 다중 상품 토큰, 부정 표현은 확정 근거로 쓰지 않는다.

## 비목표

- 임의 부분 문자열, 오타, 형태소, 초성 또는 임베딩 유사도 매칭
- 화면 `screen.products` 표면의 기존 이름 우선 규칙 변경
- 추천 검색·재랭킹 또는 분해 LLM 프롬프트 변경
- 새로운 외부 의존성 도입

## 설계

`screen_reference.resolve_screen_reference`의 추천 카드 전용 이름 확정 단계에 다음 순서를 둔다.

1. 기존 전체 상품명 포함 규칙을 먼저 유지한다.
2. 전체 이름이 확정되지 않으면 발화와 각 상품명을 NFKC 정규화하고 `casefold()`한다.
3. 유니코드 영숫자 단위로 토큰화한다. 길이 2 미만, 숫자 전용, 담기 명령, 장바구니 문맥 토큰은
   제외한다.
4. 발화와 상품명이 공유하는 토큰 중 추천 표면에서 정확히 한 상품에만 존재하는 토큰을 찾는다.
5. 유일 토큰들이 한 상품만 가리키면 그 상품을 확정한다.
6. 공통 토큰만 있거나 유일 토큰들이 서로 다른 상품을 가리키면 LLM 출력에 양보한다.
7. 기존 부정·대조 게이트가 감지되면 전체 이름과 토큰 이름 모두 확정하지 않는다.

정확한 토큰 경계를 사용하므로 `wolf`가 `septwolves`에 포함된다는 이유만으로 매칭되지 않는다.
`지갑`처럼 여러 상품에 등장하는 토큰은 문서 빈도 조건에서 제거된다. `Septwolves`와
`septwolves`는 NFKC + `casefold()`로 같은 토큰이 된다.

## 데이터 흐름

`LAST_RECOMMENDATIONS` → `last_reco[:turn_count]` 추천 표면 → `resolve_screen_reference` →
유일 이름 토큰 해소 → `CartIntent.product_id` 교체 → 기존 허용 ID 가드 → Spring 장바구니 호출

해소 결과는 추천 표면 안의 ID만 반환하므로 기존 `allowed_product_ids` 경계를 넓히지 않는다.

## 실패 처리

- 유효 토큰 없음: 기존 LLM 결과 유지
- 공통 토큰만 있음: 기존 LLM 결과 유지
- 서로 다른 상품의 유일 토큰 동시 언급: 기존 LLM 결과 유지
- 부정·대조 표현: 기존 LLM 결과 유지

이 설계는 불확실할 때 자동 선택하지 않는 기존 안전 원칙을 유지한다.

## 테스트

- 운영 재현: `Septwolves 지갑 담아줘`가 LLM의 `5695`를 덮어쓰고 `5644`를 담는다.
- 대소문자 정규화: `Septwolves` ↔ `septwolves`.
- 공통 토큰: `지갑 담아줘`만으로 임의 확정하지 않는다.
- 충돌: 서로 다른 상품의 고유 토큰을 함께 말하면 임의 확정하지 않는다.
- 경계: `wolf`는 `septwolves`에 매칭되지 않는다.
- 지시문 경계: 상품명에 `담아줘`가 들어 있어도 담기 명령 자체를 선택 근거로 쓰지 않는다.
- 부정: `Septwolves 말고 ...`는 결정론적으로 `5644`를 확정하지 않는다.
- 기존 전체 이름·순번·지시대명사 테스트를 함께 실행한다.
