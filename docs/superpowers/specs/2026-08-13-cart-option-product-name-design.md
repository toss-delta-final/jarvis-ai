# 장바구니 옵션 재질문 상품명 표시 설계

## 요약

이슈 #662는 구매자 장바구니 담기 흐름이 옵션 선택을 다시 물을 때, 사용자가 어느 상품의 옵션을 고르는지 알 수 있도록 기존 문구 앞에 대상 상품명을 표시한다.

~~~text
**상품:** 남자 메탈 남성 손목시계 명품 패션 방수 + 가죽 고급…

옵션을 선택해 주세요:
1. **올블랙**
2. **블루**
3. **블랙**

어떤 걸로 담을까요?
~~~

상품명은 기존 추천 상태와 요청의 screen.products에서만 읽는 표시 정보다. 장바구니 pending 상태나 Spring 요청에는 복제하지 않는다. 이름을 확인할 수 없거나 정제 후 비면 기존 옵션 문구를 한 글자도 바꾸지 않고 사용한다.

## 목표

- 옵션 선택을 요구하는 다섯 장바구니 재질문 경로에 대상 상품을 식별할 수 있는 머리말을 표시한다.
- 상품명은 제어 문자 등을 정제한 뒤 최대 40자로 제한하고, 40자를 초과할 때만 …를 붙인다.
- 추천 상품 이름과 FE screen.products 이름을 모두 지원한다.
- pending 전환, 옵션 선택·자동 선택, 추가금, 수량, 오류 상한과 Spring 계약은 바꾸지 않는다.
- 상품명이 없을 때의 기존 출력은 바이트 단위로 보존한다.

## 출력 계약

정제된 상품명이 존재하면 기존 옵션 재질문 앞에 아래 두 줄을 추가한다.

~~~text
**상품:** <표시 상품명>

<기존 옵션 재질문>
~~~

표시 상품명 규칙은 다음과 같다.

1. 기존 공용 _strip_unsafe로 제어 문자, 줄바꿈, zero-width·bidi 문자를 정제한다.
2. 정제 결과가 비면 상품 머리말을 생략한다.
3. 정제 결과가 40자 이하면 그대로 표시한다.
4. 40자를 초과하면 Python 문자열 기준 앞 40자 뒤에 단일 유니코드 말줄임표 …를 붙인다.
5. 굵은 표시는 상품: 레이블에만 적용한다. 상품명 자체에는 새 Markdown 장식을 추가하지 않는다.

40자 제한은 Unicode code point 기준이다. grapheme 단위 절단은 이 이슈 범위가 아니다.

## 적용 경로

app/agents/buyer/cart/graph.py의 다음 다섯 사용자 입력 요구 경로가 대상이다.

1. 기본 CART_OPTION_REQUIRED 재질문
2. 누적 조건으로 후보를 좁힌 재질문
3. 요청한 색상 조건을 찾지 못해 전체 후보를 다시 보여주는 재질문
4. I-2 옵션 목록이 비어 I-1 힌트 이름으로 대체하는 재질문
5. CART_OPTION_INVALID 뒤 다시 고르게 하는 재질문

고를 옵션이 전혀 없어 품절로 degrade 하는 문장은 입력을 요구하는 옵션 재질문이 아니므로 상품 머리말을 붙이지 않는다. 담기 성공·실패 action, 장바구니 조회, 삭제, 수량 변경, 찜 흐름도 변경하지 않는다.

## 데이터 흐름

app/agents/buyer/graph.py는 이미 한 턴에서 다음 두 이름 출처를 모두 갖는다.

- last_reco: 추천 상태의 product_id와 name 목록
- screen_products: FE가 보낸 현재 화면의 product_id와 name 목록

호출부에서 두 출처를 productId → name 표시용 맵으로 합친다. 추천 이름을 먼저 넣고 현재 screen.products 이름으로 같은 ID를 덮어써, 사용자가 현재 보는 화면의 이름을 우선한다. 빈 이름은 넣지 않는다.

stream_cart_add는 이 맵을 선택적 인자로 받고, 기존 pending 전환·해소 로직이 최종 product_id를 확정한 뒤 그 ID의 이름만 조회한다. 따라서 옵션 답변 턴에서 LLM이 product_id를 주지 않아도 pending 상품의 이름을 찾을 수 있고, 다른 상품으로 전환되면 새 상품 이름을 잘못 붙이지 않는다.

이 맵은 표시 전용이며 저장하지 않는다. PendingAdd에 상품명을 넣지 않는 이유는 다음과 같다.

- pending은 상품 원본 사본을 보관하지 않는 현재 상태 계약을 유지해야 한다.
- 상품명은 변할 수 있고 장바구니 권위 데이터가 아니다.
- 재시작·다중 인스턴스 등으로 이름을 잃어도 기존 문구로 안전하게 degrade 할 수 있다.

## 코드 경계

- _option_product_heading(product_name): 정제·40자 축약·머리말 조립만 담당한다.
- _prepend_option_product_heading(prompt, product_name): 머리말이 있으면 빈 줄과 함께 기존 prompt 앞에 붙이고, 없으면 prompt를 그대로 반환한다.
- _options_prompt는 기존 호출 호환성을 지키는 keyword-only product_name 인자를 받아 공용 prepend helper를 사용한다.
- _cart_option_required_text는 REQUIRED의 실제 옵션 입력 경로와 I-1 힌트 폴백에 같은 이름을 전달한다.
- stream_cart_add는 선택적인 product_names 맵을 받고 최종 확정된 상품 ID로 이름을 고른다.

기존 직접 호출과 테스트는 새 인자를 생략할 수 있고, 그 경우 출력은 현재와 정확히 같다.

## 대안 검토

### 채택: 표시용 이름 맵을 전달하고 확정 상품 ID로 조회

추천과 화면 출처를 모두 지원하면서 pending이 실제로 선택한 상품과 이름을 결합할 수 있다. 상태 스키마나 외부 계약을 바꾸지 않는다.

### 기각: PendingAdd에 상품명 저장

상품 원본 사본 금지 원칙을 깨고 stale 이름을 영속한다. 사용자 식별에 필수인 권위 데이터가 아니므로 비용이 더 크다.

### 기각: LLM에게 상품명을 다시 작성하게 함

이미 결정론적으로 보유한 이름을 생성 모델에 맡기면 누락·환각·표기 변경 가능성만 늘어난다. 이 변경은 출력 조립 경계에서 처리해야 한다.

### 기각: FE가 옵션 재질문 상품을 추론

AI 서버가 pending과 최종 product_id를 알고 있으므로 FE가 추천 목록으로 역추론하면 출처 불일치가 생긴다. 현재 token.text 안에서 대상 이름을 함께 보내는 것이 가장 작은 변경이다.

## 호환성과 실패 처리

- product_names가 없거나 ID가 없거나 이름이 빈 경우 기존 문구를 그대로 반환한다.
- 상품명 정제는 옵션명과 같은 _strip_unsafe 정책을 재사용한다.
- 추천 이름과 화면 이름의 순서·내용은 상품 선택에 관여하지 않는다.
- 상품 ID 허용 목록, 화면 좌표 해소, pending 전환, optionId 선택, I-1 힌트, I-2 호출은 기존 로직을 유지한다.
- SSE 이벤트 종류와 JSON 스키마는 바뀌지 않는다. token.data.text 내용만 조건부로 확장된다.
- Spring API, FE 요청 스키마, DB 스키마, 환경 설정과 새 의존성은 바뀌지 않는다.

## 테스트 전략

1. 정제 후 40자 이하, 정확히 40자, 40자 초과, 정제 후 빈 이름의 머리말 단위 테스트
2. 긴 추천 상품명이 기본 REQUIRED 문구에 40자와 …로 표시되는 통합 단위 테스트
3. screen.products에만 있는 상품명이 구매자 그래프를 거쳐 REQUIRED 문구에 표시되는 배선 테스트
4. 조건 좁힘, 색상 미충족, I-1 힌트 폴백, INVALID 재질문이 같은 상품 머리말을 쓰는 회귀 테스트
5. 이름 맵을 생략하거나 대상 ID 이름이 없으면 기존 리터럴 문구와 정확히 같은지 검증
6. 옵션 선택·자동 선택·pending·추가금의 기존 테스트 전체 실행
7. Ruff와 pre-commit 전체 실행
8. 로컬 FE·BE·AI·DB 환경에서 추천 상품 담기 → 옵션 재질문을 Chrome으로 실행하고 상품명·축약·기존 옵션 목록을 확인

## 위험과 완화

- pending 상품과 새 상품 이름 혼선: 호출 시 이름 하나를 고르지 않고 맵을 넘긴 뒤 최종 확정 product_id로 선택한다.
- 판매자 입력의 줄바꿈·제어 문자: 머리말 조립 전에 _strip_unsafe를 적용하고 정제 후 빈 값은 생략한다.
- 긴 이름이 옵션을 밀어냄: 표시 이름을 40자로 제한하고 초과 시에만 말줄임표를 붙인다.
- 기존 정확 문자열 회귀: 이름 미제공 테스트의 기존 리터럴을 유지하고 새 동작은 명시적으로 이름 맵을 준 테스트로 분리한다.
- 추천과 화면 이름 불일치: 현재 사용자가 보는 screen.products 이름을 우선하되 ID가 같은 경우에만 사용한다.
- 재시작 뒤 이름 캐시 미스: 실패하지 않고 기존 상품명 없는 재질문으로 degrade 한다.

## 범위 밖

- 추천 화면의 columns, 행·열 좌표 계산 또는 상품 선택 규칙 변경
- AI 추천 목록과 BE 응답 상품 목록 동기화 문제 해결
- 상품명 Markdown escaping 정책 신규 도입
- 옵션 답변 자연어 해석 또는 optionId 매핑 변경
- PendingAdd, FE/BE 요청, Spring API, DB 스키마 변경
- 상품 카드 또는 장바구니 UI 변경

## 완료 조건

다섯 옵션 재질문 경로가 확인 가능한 상품명에는 동일한 머리말을 표시하고, 40자 축약·정제·출처 우선순위·이름 없음 폴백이 테스트로 고정되며, 기존 장바구니 단위 테스트와 정적 검사·pre-commit·Chrome E2E가 통과해야 한다.

## 자체 검토

- 미결정 항목이나 임시 표시는 없다.
- 사용자가 승인한 40자 축약과 긴 예시를 출력 계약에 반영했다.
- 상품명 출처, 우선순위, pending 턴 결합 시점을 명시했다.
- 외부 스키마와 장바구니 상태를 늘리지 않는 최소 변경으로 제한했다.
- 이름을 확인할 수 없는 경우의 기존 문구 보존을 명시했다.
