# Jarvis AI 최종 보고서 제작 설계

## 1. 목표

기존 2페이지짜리 목차 초안을 실제 저장소의 구현, 테스트, 평가 결과로 채워 제출 가능한
한국어 정식 보고서로 완성한다. 보고서는 Jarvis가 자연어 상품 탐색부터 개인화 추천과
장바구니 실행까지 연결하는 에이전틱 커머스 AI임을 설명하고, 구매자·판매자 Agent와
검색·평가 체계의 설계 근거를 재현 가능한 자료로 제시한다.

## 2. 산출물

- 원본 PDF는 수정하지 않고 보존한다.
- 편집 가능한 보고서 원본을 `docs/final-report/` 아래에 저장한다.
- 최종 PDF는 원본 폴더에 `최종_보고서_완성본.pdf`라는 이름으로 생성한다.
- 저장소의 `docs/final-report/최종_보고서_완성본.pdf`에도 동일한 사본을 두어 편집
  원본과 결과물의 이력을 함께 관리한다.
- PDF는 A4 세로형, 한국어 본문, 약 12~15페이지를 목표로 한다. 내용의 자연스러운
  페이지 흐름을 위해 최종 페이지 수는 이 범위에서 소폭 달라질 수 있다.

## 3. 독자와 문체

주 독자는 프로젝트 평가자와 기술 면접관이다. 문체는 기술적으로 정확하되 저장소 내부
용어를 모르는 독자도 이해할 수 있는 공식 보고서체를 사용한다. 기능 나열보다 문제,
설계 결정, 구현, 검증, 한계의 연결을 우선한다.

## 4. 근거와 주장 규칙

1. 구현 설명은 현재 저장소의 코드, `README.md`, API 명세, 테스트와 평가 artifact를
   근거로 작성한다.
2. 측정값은 실행 조건과 범위를 함께 표기한다. 서로 다른 평가셋의 수치를 한 지표처럼
   합치지 않는다.
3. 실제 평가가 없는 항목은 성과로 단정하지 않는다.
4. 판매자 기능과 구매자 기능의 평가 범위를 구분한다.
5. `validated` rerank 근거 검증 결과는 평점·리뷰·후보군 상대가격 및 정확한 숫자 근거에
   한정된다는 제한을 명시한다.
6. REES46 통계는 서비스 운영 데이터가 아니라 데이터셋 구성 근거로만 사용한다.

## 5. 문서 구성

### 표지·요약·목차

- 프로젝트명과 한 문장 소개
- 핵심 성과와 기술 스택 요약
- 8개 본문 장의 목차

### 1장. 프로젝트 개요

- 프로젝트 소개: 에이전틱 커머스 AI 서버
- 배경: 키워드 중심 쇼핑 경험의 한계
- 목적: 자연어 의도 해석, 개인화 추천, 후속 행동 연결
- AI 서버, React 프론트엔드, Spring 백엔드의 책임 경계

### 2장. 문제 정의 및 요구사항

- 상황 중심 요청을 구조화 조건으로 바꾸는 문제
- 멀티턴 조건 유지와 현재 의도 우선순위
- 추천 근거의 환각과 화면 밖 상품 참조 위험
- 검색 이후 장바구니·찜·주문 조회로 이어지는 실행 요구
- 정확성, 안전성, 스트리밍, 인증, 장애 격리 요구사항

### 3장. 서비스·시스템 설계

- 사용자 요청부터 SSE 응답과 상품 카드 조회까지의 서비스 흐름
- React–AI–Spring 3-tier 아키텍처
- 원본 데이터와 AI 산출물의 소유권 분리
- Python 3.12, FastAPI, LangGraph, PostgreSQL·pgvector, Pydantic, pytest의
  선택 이유
- JWT/JWKS 인증과 Spring 역호출 경계

### 4장. AI Agent 설계

- Buyer intent router와 recommendation, cart, order, fallback 서브그래프
- Seller Agent의 통계 질의와 수정 draft 생성 흐름
- fast/smart LLM tier의 역할 분리
- 멀티턴 상태, 세션 버퍼, 장기 프로필의 분리
- LLM 의미 판단과 결정론적 코드 검증의 결합

### 5장. 핵심 기능 구현

- 자연어 추천: 의도 분해, 후보 검색, hard filter, rerank, 근거 생성
- 장바구니·찜: 지시 대상 해소, 옵션 확인, Spring 트랜잭션 호출
- 개인화: 대화·구매 이력 신호, 승격 gate, 프로필 consolidation
- 판매자: 매출·상품 분석 질의와 검토 가능한 변경 draft
- SSE 이벤트, 취소, 타임아웃, degrade 처리

### 6장. 데이터 및 검색 시스템

- Spring 원본 상품과 AI 생성물의 분리
- 구조화 필터와 semantic query의 역할
- 임베딩, pgvector, 후보 압축, reranking 파이프라인
- pull 기반 상품 변경 동기화
- REES46 전수 통계와 더미 데이터 설계의 근거 및 한계

### 7장. 테스트 및 결과

- unit, integration, eval 계층의 목적
- HTTP 경계 기반 구매자·프로필·배치·인증 E2E 검증
- adversarial recommendation 데이터셋 210 family·450 case와 20% 직접 검토
- rerank grounding의 screening 및 독립 confirmation 결과
- 성능·지연 측정값은 저장된 artifact에서 조건과 함께 인용
- 결정론 CI와 실 LLM 수동 평가를 분리한 재현성 전략

### 8장. 결론 및 향후 개선

- LLM과 결정론적 검증의 역할 분리라는 핵심 성과
- 외부 Spring·LLM 의존, 평가 범위, 실제 사용자 실험 부재 등의 한계
- 검색 품질 holdout, 사용자 행동 기반 평가, 비용·지연 최적화,
  운영 관측성 고도화 계획

## 6. 시각 설계

- 표지는 짙은 남색과 청록 계열을 사용한 단정한 기술 보고서 스타일로 구성한다.
- 본문은 한글 가독성이 높은 sans-serif 글꼴과 충분한 행간을 사용한다.
- 각 장은 번호, 제목, 한 문장 요약으로 시작한다.
- 전체 시스템 아키텍처, Buyer 처리 흐름, 검색·rerank 파이프라인을 벡터 도식으로 넣는다.
- 구현·평가 수치는 표와 강조 상자로 요약한다.
- 코드 캡처 대신 짧은 의사 흐름과 파일 경로를 사용해 PDF의 가독성을 유지한다.

## 7. 제작 방식

외부 편집 도구에 종속되지 않도록 저장소 안의 텍스트 기반 원본에서 HTML을 생성하고,
로컬에서 사용 가능한 PDF 렌더러로 변환한다. 필요한 스타일과 도식은 보고서 전용 파일에
한정하고 애플리케이션 코드나 의존성에는 변경을 가하지 않는다. 시스템에 이미 설치된
도구를 우선 사용하며 새 프로젝트 의존성은 추가하지 않는다.

## 8. 검증 기준

- 보고서에 미작성 항목, 대괄호형 이름·수치 표식 같은 임시 문구가 없어야 한다.
- 기존 8개 장과 각 하위 주제가 모두 실제 본문으로 채워져야 한다.
- 모든 정량 주장은 출처 파일 또는 평가 artifact와 대조되어야 한다.
- PDF에서 한국어 텍스트가 추출 가능해야 한다.
- 모든 페이지를 이미지로 렌더링해 잘림, 겹침, 빈 페이지, 깨진 글꼴이 없는지 확인한다.
- 표와 도식이 페이지 경계를 넘어가지 않아야 한다.
- 원본 PDF와 기존 작업 트리 변경 사항을 수정하지 않아야 한다.

## 9. 범위 제외

- React 프론트엔드와 Spring 백엔드의 내부 구현을 AI 저장소가 구현한 것처럼 설명하지 않는다.
- 저장소에 없는 팀원 이름, 역할, 학교·기관명, 영상 링크는 임의로 만들지 않는다.
- 새 기능 개발, 애플리케이션 리팩터링, 신규 런타임 의존성 추가는 수행하지 않는다.
- 실제 서비스 사용자 성과나 매출 개선 효과를 추정하지 않는다.
